# VBIOS：结构、版本与 DEVINIT

**本页涵盖：** CMP 170HX SPI ROM 镜像的布局、如何不砖卡地转储它、每个区域里有什么、哪些部分受密码学保护哪些不受、DEVINIT 是什么以及它（不）控制什么、按批次的版本清单，以及一份"能改什么、不能改什么"的排序表。

**头条结论：社区解锁完全不碰 VBIOS。** 正式发布的 `cmpunlocker` 工具从不读、写、刷或解析 ROM。仓库里没有任何地方有 `nvflash`、SPI 访问或镜像处理；整个工具就是六个内核模块补丁加 `install.sh` 和 `remove.sh`。对正式发布树做整词搜索 *flash*、*nvflash*、*spi*、*rom* 和 *vbios*，一无所获；唯一命中的子串都是偶然的，比如 `remove.sh` 完成横幅里的 "from"。解锁发生在运行时，在打过补丁的 GSP 引导路径内部。见[解锁原理](../unlock/how-it-works.md)。

第二个头条：**这张卡上整个刻意的 VBIOS 级限制就是七个字节。** 两字节的 CFG1 strap-4 寻址（档位 `44` 到 `66`，控制 HBM 地址深度、12 对 14 个行位、每个 HBM2 堆栈可寻址 2 对 8 GB）加分布在三个位置的五字节 PCIe 速率 DEVINIT。两者都在 MAC 验证范围内，因此都需要一把没人有的钥匙。170HX ROM 与 A100 ROM 之间其他一切差异都是零散的设备 ID 引用和逐构建的训练校准，与限制无关。

## 快速定位

| 问题 | 答案 |
|---|---|
| 生产 ROM 大小 | 每个 GA100 生产转储都是 1,044,480 字节（1020 KB） |
| 偏移 0 处的魔数 | `NVGI` |
| 运行时读取窗口 | NV_PROM 位于 BAR0 + `0x300000` |
| 密码学保护范围（170HX 250 W） | `0x2200`–`0x43A00` |
| 保护类型 | 对称 MAC（Davies-Meyer 哈希 + AES-KDF），密钥 csecret(2)，**不是** RSA 镜像签名 |
| 自由可改 | `0x43A00` 到镜像末尾（未签名 FwSec 尾部、填充、备份镜像、InfoROM） |
| VBIOS 版本影响解锁吗？ | 不影响 |
| 修改过的镜像能刷吗？ | `nvflash`/`omgvflash`/`nvflashk` 不行。未签名尾部编辑需要 CH341A |

## 转储 VBIOS

> [!CAUTION]
> **动任何东西之前先转储**
>
> 刷坏或坏镜像在绝大多数情况下**只有先存下原厂 ROM 才能恢复**。砖过并恢复过这些卡的人的一致建议：保留原厂转储，并在碰 NVGI 区域*之前*备好外部 SPI 编程器。一位研究者说"如果我破坏了 NVGI，就完全没有恢复路径"，随后一分钟后自我更正：硬件 SPI 编程器让它可恢复。`NV_PROM` MMIO 转储被视为足够的后备镜像。见[恢复](../procedures/recovery.md)。

有三条转储路径。它们产生不同的字节范围，也有不同的故障模式。

| 方法 | 捕获范围 | 需要 | 风险 | 备注 |
|---|---|---|---|---|
| `nvflash --save` | 1020 KB（`0x00000`–`0xFF000`） | 驱动绑定，root | 低 | 标准路线。在 170HX 上该窗口**确实**包含 `0xFE000` 的许可区域；在 A100 上不包含，因为 A100 的许可 TOC 在 `0xFF000` |
| NV_PROM MMIO 回读 | 从 BAR0 + `0x300000` 起 1,044,480 字节 | root，BAR0 映射 | 极低，只读 | 卡自己对 ROM 的视图。净室 `ga100_topology_report.py` 工具使用它。SPI 转储显示有内容的地方它可能显示 `0xFF`（见下方警告） |
| CH341A + SOIC 夹 | 整个 SPI 器件 | 拆散热器、重涂硅脂 | 物理 | 唯一能*写*编辑镜像的路径。原厂卡硬件写保护 |

### 先识别卡和它的 VBIOS

```bash
lspci -nn -d 10de: | grep -i GA100
# 0d:00.0 3D controller [0302]: NVIDIA Corporation GA100 [CMP 170HX] [10de:20c2] (rev a1)

nvidia-smi --query-gpu=vbios_version,pci.device_id,pci.sub_device_id,memory.total \
           --format=csv
```

`10de:20c2` 是 8 GB SKU，`10de:2082` 是 10 GB SKU。完整识别矩阵见[板卡与型号变体](board-and-variants.md)。

### `nvflash` 保存

```bash
sudo nvflash64 --save stock_$(date +%F)_$(hostname).rom
sha256sum stock_*.rom
```

### 经 BAR0 的 NV_PROM 回读

SPI 闪存可通过 **BAR0 + `0x300000`** 的 NV_PROM 窗口在运行时读取，1,044,480 字节，前四个字节 `NVGI`。窗口基址由 FWSEC 反汇编推导。

```python
#!/usr/bin/env python3
# 只读 NV_PROM 转储。需要 root。把 BDF 换成你的卡。
import mmap, os

BDF   = "0000:0d:00.0"
BAR0  = f"/sys/bus/pci/devices/{BDF}/resource0"
PROM  = 0x300000          # BAR0 内 NV_PROM 窗口偏移
SIZE  = 1044480           # 1020 KiB

fd = os.open(BAR0, os.O_RDONLY)
m  = mmap.mmap(fd, PROM + SIZE, mmap.MAP_SHARED, mmap.PROT_READ)
rom = m[PROM:PROM + SIZE]
assert rom[:4] == b"NVGI", f"bad magic: {rom[:4]!r}"
open("vbios_prom.rom", "wb").write(rom)
print(f"wrote {len(rom)} bytes")
```

> [!WARNING]
> **MMIO 回读不总是与 SPI 转储相同**
>
> 在 Drive A100 上，NV_PROM 回读在 `0xFE000` 和 `0xFF000` 两处都显示全 `0xFF`。该区域在那颗部件上是真的为空，还是 TOC 结构只是过不了 NV_PROM 路径，未决。任何人用 MMIO 调查许可区域，都应该先用 SPI 转储确认，再下"区域为空"的结论。

### CH341A 转储并验证

```bash
# 两次独立读取，互相比对。绝不要信单次夹读。
flashrom -p ch341a_spi -r spi_dump_1.rom
flashrom -p ch341a_spi -r spi_dump_2.rom
cmp spi_dump_1.rom spi_dump_2.rom && echo "clip contact is good"
```

原厂卡的 SPI 闪存硬件写保护：转储的状态寄存器读 `00000000 (0x00)`、`01000000 (0x40)`、`11111111 (0xFF)`。一位测试者在碰到写保护后十分钟内解除保护并完成一次刷写，所以这是障碍而不是墙。

> [!CAUTION]
> **再次上电前先恢复写保护**
>
> 刷写失败 `0xBADF3000`、板卡无法读闪存，原因是**上电前没有重新启用 SPI 写保护**。恢复方法是用芯片夹直接重刷 SOIC，然后设置写保护。相关症状是 RM init adapter 失败。这块板没有操作系统级刷写路径。

### SKU 与完整性指纹

两个对固定范围截断的 SHA-256 值充当廉价的 SKU 与完整性检查。两对在检查过的同 SKU 每个镜像上都逐字节相同，所以不匹配意味着 VBIOS 代码有差异，而不只是逐单元数据。

```bash
IFR()  { dd if="$1" iflag=skip_bytes,count_bytes skip=0        count=$((0x1000))          status=none | sha256sum | cut -c1-16; }
FW()   { dd if="$1" iflag=skip_bytes,count_bytes skip=$((0x1200)) count=$((0xC1000-0x1200)) status=none | sha256sum | cut -c1-16; }
echo "IFR      $(IFR vbios_prom.rom)"
echo "FIRMWARE $(FW  vbios_prom.rom)"
```

| SKU | IFR `0x000000`–`0x001000` | FIRMWARE `0x001200`–`0x0C1000` |
|---|---|---|
| 10 GB（`0x2082`） | `3ca3d24230d6800f` | `8c4e1344c51b0940` |
| 8 GB（`0x20C2`） | `2ff19960f9175320` | `e2c91c1808ae2759` |

上面的归属是三份报告对一份的仲裁结果；唯一的离群把 8 GB 对附到 10 GB 镜像上，被视为转录笔误。用拓扑工具一次运行把两个 SKU 的输出并排贴出就能了结。

## 区域图

已公布的分析称之为 13 区域图（仅内容区域）。这里扩展到包含填充、镜像和 InfoROM。大小取自 170HX 250 W 镜像；"signed"（签名）指位于 `0x2200`–`0x43A00` MAC 验证范围内。

| 偏移范围 | 内容 | 大小 | 签名 |
|---|---|---|---|
| `0x00000`–`0x02200` | NVGI 头部 + RFRD 清单，明文 | 8.5 KB | 否（在签名起点之下） |
| `0x02200`–`0x05E00` | PciAt 区域、BIT 令牌、PERF_PTRS | 15.0 KiB | **是** |
| `0x05E00`–`0x0C700` | FwSec 头、VN 镜像 1 和 2、NPDS/NPDE | 27 KB | **是** |
| `0x0C700`–`0x0C800` | NPDS/NPDE 头 | 256 B | **是** |
| `0x0C800`–`0x13E00` | 压缩 Falcon 代码，delta 0 处与 A100 共享 87% | 29.5 KB | **是** |
| `0x13E00`–`0x14A00` | 区域间空隙，零加头 | 3 KB | **是** |
| `0x14A00`–`0x20000` | 加密固件区域 A，AES-128-ECB | 45.5 KB | **是** |
| `0x20000`–`0x20700` | DMAP 明文空隙，`"Mar  5 2021"` 构建字符串加 Falcon fuc5 代码 | 1.8 KB | **是** |
| `0x20700`–`0x33800` | 加密固件区域 B，AES-128-ECB | 76.2 KB | **是** |
| `0x33800`–`0x41200` | 配置 / DEVINIT 类表，Shannon 熵 4.5–6.0 | 54.5 KB | **是** |
| `0x41200`–`0x42A00` | 跳线与训练表；CFG1 strap-4 档位字节在 `0x41D53` | 6 KB | **是** |
| `0x42A00`–`0x43A00` | 尾部零 | 4 KB | **是**（止于边界） |
| `0x43A00`–`0x47700` | **未签名 FwSec 尾部** | 15,616 B | 否 |
| `0x47700`–`0x60000` | `0xFF` 填充 | 100 KB | 否 |
| `0x60000`–`0xA7700` | **`0x00000`–`0x47700` 的备份镜像** | 285 KB | 否 |
| `0xA7700`–`0xC0000` | `0xFF` 填充 | 100 KB | 否 |
| `0xC0000`–镜像末尾 | InfoROM（1020 KB 转储中在 `0xFF000`，完整 1 MiB MMIO 回读中在 `0xFFFFF`） | 252–256 KB | 否 |

`+0x60000` 镜像解释了对比工作中每个重复表地址：如果一个表同时出现在 `0x41D41` 和 `0xA1D41`，那是一张表和它的备份副本，不是两张表。

> [!NOTE]
> **"NVGI 区域"有两种不同含义**
>
> 上面的区域图用 NVGI 指 `0x00000`–`0x02200`。8 GB 对 10 GB 的 diff 分析用 NVGI 指 `0x00000`–`0x05E00`，这就是为什么 `0x2CBF`、`0x38BA`、`0x595C` 和 `0x5AF8` 的四个 MAC 块虽然位于 `0x2200` 之上，却被描述为"在 NVGI 里"。

### NPDS 主体构成

NPDS 主体 `0x0C700`–`0x43A00`（226,048 字节）按熵类别划分：

| 类别 | 占比 | 详情 |
|---|---|---|
| AES-128-ECB 密文 | 121.7 KB（54%） | 两个区域，一把密钥，101 组内部重复对 |
| DEVINIT 类配置表 | 54.5 KB（24%） | 熵 4.5–6.0，结构化明文 |
| 压缩 Falcon 代码 | 29.5 KB（13%） | delta 0 处与 A100 共享 87% |
| 头、空隙、跳线表、填充 | 20.3 KB（9%） | 明文 |

那 24% 的明文配置带，正是 DEVINIT 字节能用模式搜索定位、而 FwSec 固件不能的原因。

## RFRD 清单与签名范围

MAC 验证范围不是猜的，是声明的。`0x2000` 处的清单是**镜像布局描述符**，不是功耗表。

| 偏移 | 字段 | 值 / 含义 |
|---|---|---|
| `0x2000` | 魔数 | `"RFRD"` |
| `0x2004` | u16 清单版本 | `3` |
| `0x2008` | u32 `pci_option_rom_offset` | 指向 PciAt 镜像起点 `0x5E00` |
| `0x200C` | u32 `pci_option_rom_size` | **MAC 验证范围的大小** |
| `0x200D` | （字节） | `pci_option_rom_size` 的高字节。碰它会使声明大小与真实签名内容失步，MAC 验证失败 |
| `0x201C` | u32 `secondary_base` | `0x2200` |

签名内容总是从 `0x2200` 开始。按镜像：

| 镜像 | field_0C | MAC 验证范围 |
|---|---|---|
| 170HX 8 GB 与 10 GB，250 W | `0x00041800` | `0x2200`–`0x43A00`（268,288 B） |
| 170HX 300 W | `0x00041A00` | `0x2200`–`0x43C00` |
| A100 PCIe 40 GB | `0x00042200` | `0x2200`–`0x44400` |
| Drive A100 32 GB | `0x00058A00` | `0x2200`–`0x5AC00` |

### 范围是实证界定的，不只是读出来的

2026-05-08 的四次物理 CH341A 刷写循环定案。在声明范围*之外*写 `0xFF` 填充能正常启动、驱动正常加载。在 `0x2200`–`0x43A00` 窗口*之内*改一个字节会让 Booter 卡住。GA100 上经典的坏 MAC 失败特征：

```text
GFW_BOOT = 0x401    (or 0x001)
```

单字节测试在 `0x41D53` 执行——CFG1 档位字节，正是显存解锁想改的那个字节。这就是"MAC 内编辑已关闭"的实证。

## 密码学

两把不同的密钥、两种不同的机制，经常被混为一谈。

| 机制 | 覆盖 | 密钥 | 状态 |
|---|---|---|---|
| 对称 MAC，Davies-Meyer 哈希 + AES-KDF | `0x2200` 到范围末尾的内容 | csecret(2)，存放在 SCP 硬件中 | 伪造需要密钥；据称只有 DFA 硬件攻击才能提取 |
| AES-128-ECB | 两个 FwSec 固件区域 | csecret(6) | 每个 GA100 变体同一把密钥 |
| RSA | 引导 ROM 认证 Booter 代码 | NVIDIA 生产密钥 | 独立机制，常被误认为镜像签名 |

### AES-128-ECB，三重证明

1. **跨 ROM 重新收敛。** 13 次匹配运行中，170HX 与 A100 之间 2,667 个块有 442 个相同。明文发散后 CBC 永远不可能重新收敛。
2. **内部重复块**（"ECB 企鹅"）。170HX 镜像内 24 组重复 16 字节对，A100 镜像内 28 组。这排除了 CTR。
3. **严格 16 字节对齐。** 把比较平移一个字节，匹配数从 442 掉到恰好 0。

**一把密钥加密所有 GA100 变体的 FwSec 块。** `0x14A00` 处的前四个 ECB 块在 170HX 8 GB、170HX 10 GB、170HX 300 W 和 A100 PCIe 上逐字节相同；Drive A100 于 2026-05-31 加入，30 次 ECB 预言机命中、前四个块相同，以 `b2a93eaa0300209b` 开头。一旦恢复 csecret(6)，就能解密现存的每一份 GA100 VBIOS。

### 免费的已知明文预言机

ROM 包含全 `0xFF` 明文填充块，给出：

```text
AES_ECB(key, FF x 16) = 717d1494 eaca317f f1061952 58b38377
```

重复密文块位于 `0x1F8F0` 和 `0x1FB60`（ImHex 中标记为 "end of imem_sec"），ECB 区域 A 有 21 个这样的填充块、区域 B 有 13 个，且该模式在所有 ROM 变体上复现。因此候选密钥可以在离线状态下微秒级验证，无需刷写循环——这正是 DFA 行动可行的原因。

同一个 128 位值还单独是**用平凡非机密密钥 `01234567...` 加密的调试构建 Falcon IMEM 部分**的标记。攻击 DEVINIT/FWSEC 的推荐工作流是：从公开集合拉一份 VBIOS，搜索该填充模式，用简单密钥解密那些 IMEM 部分，然后标注反汇编。这个配方是持续一致的专家建议，但频道内还没有贴出结果。

> [!NOTE]
> **开放问题**
>
> 另一条说法——"密钥就在 NVIDIA 官网上，我觉得是 debug #37"——从未被证实。密钥和解密后的生产镜像都从未被贴出。请把 `01234567...` 调试 IMEM 配方视为可操作、把 "debug #37" 说法视为未验证。

## 镜像包含的表

### 签名范围内（仅文档价值）

| 表 | 偏移 | 备注 |
|---|---|---|
| BIT 表 | `0x5EB0`，16 个令牌 | 六份生产 ROM 上偏移与令牌数相同 |
| FwSec NPDS 设备 ID | FwSec 头中 | **全部七份**镜像都声明 `0x2080`（通用 GA100），无论它们的 PciAt 设备 ID 如何 |
| CFG1 / HBM2 跳线表 | `0x41D41`（170HX 8 GB、10 GB、"16 GB"），备份 `0xA1D41` | 16 × 32 位字，**非**字对齐；次级 `strap_info` 表在 `0x6A09` |
| CFG1 strap-4 档位字节 | `0x41D53`（250 W）/ `0x41F53`（300 W） | 七字节限制的两字节那一半 |
| PCIe 速率 DEVINIT | `0x33800`–`0x41200` 内 3 处共 5 字节 | 另一半 |

各镜像的跳线表偏移：

| 镜像 | 版本 | 主 | 备份 |
|---|---|---|---|
| 170HX 8 GB 与 "16 GB" | `92.00.67` | `0x41D41` | `0xA1D41` |
| 170HX 10 GB | `92.00.66` | `0x41D41` | `0xA1D41` |
| 170HX 300 W | `92.00.6D` | `0x41F41` | `0xA1F41` |
| A100 PCIe 40 GB | `92.00.90` | `0x4285A` | `0xA285A` |
| A100 SXM4 40 GB | `92.00.45` | `0x419E5` | `0xA19E5` |
| Drive A100 32 GB | `92.00.A0` | `0x3A7D2` | 未确定 |

300 W ROM 把整组表放在比 250 W 兄弟晚恰好 `0x200` 字节处。泄露的 GA100 emu/sim ROM 使用完全不同的约 230 KB 布局，两份副本都在同一镜像内（`0x0864C` 和 `0x1AD72`），所以没有任何东西能从它们移植。

**档位字节解码。** 每个 32 位跳线字的第三个字节是档位半字节对，取值 `44`、`55`、`66`、`77`，编码每个 HBM2 堆栈可寻址 2 GB / 中间档 / 8 GB / 16 GB。大多数条目是填充模式 `00 90 66 22`。10 GB VBIOS 中只有 strap 4 被削弱到 `44`；8 GB VBIOS 中 strap 5 和 7 也被削弱。Strap 4 是 10 GB 卡的物理跳线，strap 7 是 8 GB 卡的。这正是运行时解锁写入 `0x009a0204` CFG1 的同一套档位编码；见[内存几何](../unlock/memory-geometry.md)。

> [!NOTE]
> **开放问题**
>
> 2026-07-25 间隔几小时贴出了两种互不兼容的逐 strap HBM 部件字段解码。**供应商与修订字段一致**（Micron/Samsung/Hynix，rev1/rev2/rev3/rev6/rev10）；**逐 die 容量与堆栈高度字段不一致**（例如 strap 5 是 `Hynix_rev6_16Gb_org0x4` 对 `Hynix_rev6_8Gb_4H_org0x4`）。第二种解码的作者指出公开流传的论坛解码脚本"对 HBM 内存配置并不完全正确"。`44`/`66`/`77` 容量映射没有争议。定案需要权威的字段宽度定义，或把一条解码条目与物理识别出的 HBM 堆栈部件号对上。

### 签名范围之外（实际可编辑）

`0x43A00` 及以上的一切都未签名，用 SPI 编程器可自由修改，与已经成功启动的 `0xFF` 填充测试同属一类。

| 项 | 偏移 | 值 / 详情 | 状态 |
|---|---|---|---|
| 板卡功耗上限 | `0x45E45`，3 字节 | `90 D0 03` = 250 W，改成 `E0 93 04` 即 300 W | MAC 之外。**开放，2026-05-09 起未测试** |
| `NV_FUSE_CTRL_OPT_*` 表 | `0x47341`，25 条目 | 13 张探测过的 GA100 卡上全零 | 之外。语义未定 |
| `freqDelta` | `0x47177` / `0x47179` | 8 GB 镜像 ±1000，10 GB 与 A100 镜像 `0` | 之外。解释为什么核心偏移只在 8 GB 卡上有效 |
| M0205 显存训练表 | `0x467f8`（10 GB）/ `0x469f8`（检视的另一份镜像） | 头 `ver=0x10 hdr=8 entsz=1 cnt=1`，原始 `10 08 01 01 10 07 00 00`，16 条 7 字节 strap 子条目 | 之外 |
| InfoROM | `0xC0000` 向上 | 完全未签名 | 之外 |
| 许可 / HULK TOC | `0xFE000`–`0xFEFFF` | 见下文 | 之外 |

M0205 strap 子条目在检视的两份镜像间逐字节相同，例如 strap0 `0f ff ff ff ff ff ff`、strap2 `ff ff ff 0f ff ff ff`、strap4 `ff ff ff ff ff ff 0f`、strap7 `ff ff 0f ff ff ff ff`、strap9 `ff ff ff ff ff 0f ff`、strap12 `ff 0f ff ff ff ff ff`、strap14 `ff ff ff ff 0f ff ff`；除 7 和 9 外的所有奇数 strap 都是全 `ff`。

**由上面的偏移与 MAC 边界推导：** 2026 年 7 月读出的每个与显存相关的表（`freqDelta`、M0205、CTRL_OPT）都位于 `0x43C00` 之上，因此都在每个 170HX MAC 范围之外；而 `0x41D41`/`0x41D53` 的 CFG1 跳线档位表位于边界下方约 10 KB，在范围之内。**这就是干净的分界线：镜像里显存时序和时钟偏移可编辑；显存容量跳线不可编辑。**

### 许可区域与 HULK 槽

**170HX 的许可区域在 `0xFE000`–`0xFEFFF`，不是 `0xFF000`。** 这更正了一个从 A100 借来的全社区假设。经三种方法获得的五份独立 170HX 转储验证（三份 10 GB 转储，其中一份 SPI、一份 MMIO，加两份 8 GB 转储）。在每张 170HX 上，`0xFF000` 的顶部 4 KB 全是 `0xFF` 且未使用。它很重要，因为 170HX 上 `nvflash` 转储 1020 KB，所以该区域在这张卡上*确实*在 nvflash 窗口内——尽管在 A100 上不是。

| 偏移 | 内容 |
|---|---|
| `0xFE000` | 8 个零字节 |
| `0xFE008` | `"LU"` + `00 10 00 00 00 01`：区域头，大小 `0x1000`，版本 1 |
| `0xFE010` | 槽表：`"LIC" 01 00 1D 00`（LIC 在 +0x1D）、`"ULF" 1D 00`（解锁标志）、`"UPR" 7D 04`（解锁参数在 +0x47D）、`"HLK" ED 04`（HULK 证书在 +0x4ED）、`"ULF" 01 00 60 04` 终结符 |
| `0xFE48D` | UPR 槽头，负载为空 |
| `0xFE4FD` | HLK 槽头 `"HLK" 01 00 60 04`，版本 1，标志 0，槽大小 `0x0460`（1120 B） |
| `0xFE504` | HLK 负载，1113 字节容量，**原厂 170HX 上全零** |

推理是：预建但为空的 HULK TOC 意味着 FWSECLIC 每次启动都扫描许可区域，因为如果没人读它，NVIDIA 不会出货一张完整的槽表加 1120 字节保留槽。推论是，在 `0xFE504` 放一张伪造或生产签名的 HULK 证书会是一条解锁路径。这从未通过给 FWSECLIC 插桩得到证明。

> [!NOTE]
> **开放问题**
>
> 在 `0xFE504` 注入 HULK 证书。槽存在，1113 字节，原厂全零，位于 `nvflash` 写入的窗口内，所以原则上不需要 CH341A。两个阻碍：同一分析称即使未签名尾部改动，`nvflash` 也被 FwSecLic 写时验证阻挡，且许可区域是否豁免从未被测试；另外没人有签名证书。最便宜的下一步：往 HLK 负载刷任意非零模式，看写入是否被接受，这能区分"区域可写"与"我们需要有效证书"。

### InfoROM

完全未签名。值得注意的标签：`IMG` 容器头、`BRD` 板卡信息 / 部件号、`OBD` 卡名、`PPO` 功耗 / 性能（**所有 170HX ROM 上为空**）、`BBX` BlackBox 遥测、`RPR` HBM RAS 的行重映射，以及 `ECC` ECC 配置（**仅 A100**）。卡名字符串是 `"NVIDIA-A100-PCIe-40GB"`、`"NVIDIA A100-SXM4-40GB"` 和 `"CMP 170HX"`。

一张活 10 GB 卡枚举出 **17 种不同的对象类型**：APP、BBX、BRD、DEM、IMG、NEN、NVL、OBD、OCT、OEM、OMS、PPO、ROM、RPR、RRL、SEN、ULF，版本为 APP v6、BBX v4 与 v6、BRD v2、DEM v6、IMG v2、NEN v14、NVL v6、OBD v2、OCT v6、OEM v2、OMS v14、PPO v6、ROM v2、RPR v6、RRL v6、SEN v14、ULF v0。同一 SKU 上 `nvidia-smi` 报告 Inforom Image Version `1001.0105.01.02`、OEM Object 2.0，ECC Object 与 Power Management Object 都是 N/A，与 `ECC` 仅 A100、`PPO` 为空一致。

> [!WARNING]
> **不要用 InfoROM 对象总数给卡做指纹**
>
> 22、23 和 28 的总数都被报告过，而且**全部正确**：BBX 和 DEM 是随运行时累积的遥测记录。只有 17 种不同类型和逐对象版本在结构上有意义。

## DEVINIT

DEVINIT 是 VBIOS 内置的初始化脚本，在驱动看到设备之前于启动时编程 GPU 寄存器。在 GA100 上它位于 `0x33800`–`0x41200` 配置区域：结构化明文，熵 4.5–6.0，这正是它的字节能用模式搜索定位、而加密的 FwSec 固件不能的原因。**因为该区域止于 `0x41200`，远低于 `0x43A00` MAC 边界，任何 DEVINIT 修改都会破坏 Booter MAC。**

### 它在哪里运行

闭源的 NVIDIA RM 包含一个 **x86 DEVINIT 脚本解释器，符号 `_nv000358rm`**，使用 ASCII 操作码分发。它在代码地址 `0x264fb1` 读取跳线寄存器 `0x101000`，并通用地执行 VBIOS DEVINIT 寄存器写入。这就是为什么 L2 解码寄存器 `0x17e2a0` 从不以立即数出现在 RM 代码的任何地方：它的地址来自 VBIOS 脚本流，而不是 RM。三个注册表键控制 DEVINIT 在哪里运行：

| 注册表键 | 作用 |
|---|---|
| `RMExecuteDevinitOnPmu` | 在 PMU 上运行 DEVINIT |
| `RmDisableFbflcnDevinitBoot` | 禁用 FBFLCN DEVINIT 引导路径 |
| `RMDevinitBySecureBoot` | 经安全启动运行 DEVINIT |

中置信度：这来自带具体符号与偏移的二进制分析，未经独立复现。

### 启动顺序

```text
NVGI 记录执行
  -> IFR ucode 取 FWSEC 描述符并启动 FWSEC
  -> FWSEC 提升 PLM
  -> devinit / UDE08 编程全部 29 个 FBPA 寄存器
  -> FBFLCN 训练 HBM
```

两个后果直接成立，且都关死明显攻击：NVGI 写入 MR1/MR2/MR3 的任何内容都会在片刻之后被 DEVINIT 用启动跳线的表值覆盖；从 NVGI 写 PLM 也是徒劳，因为 FWSEC 之后会重新提升它们。中置信度；这是固件分析的顺序论证，不是实证测试。

### DEVINIT 与 PCIe Gen1 锁

PCIe 速率限制是 **3 个 DEVINIT 位置共 5 字节**（Gen1 对 Gen3/4），全部在 MAC 范围内。因此 ROM 路线以与显存跳线字节相同的原因关闭：没有 csecret(2)、没有 MAC 伪造、没有启动。

取而代之的完全是运行时。未发布的 `Gen2` 系分支通过从打过补丁的驱动写 PCIe 寄存器达成 Gen2（5 GT/s），从不碰 ROM，得到 `LnkCap max Gen2 0x00456102`、`LnkCap2 0x00000006`、`LnkSta trained Gen2 x4 0x1042` 和 `nvidia-smi` 当前/最大/宽度 `2,2,4`。那只是链路**速率**；链路**宽度**是另一件纯物理的事。见[PCIe Gen2](../unlock/pcie-gen2.md)和[PCIe 子系统](pcie-subsystem.md)。

> [!NOTE]
> **开放问题**
>
> Gen3 和 Gen4 仍未达成。`FUSE_PCIE_GEN23_DIS` `0x0082057c` 和 `FUSE_PCIE_GEN3_DIS` `0x00820580` 在每张探测过的 170HX 上都读 `0x00000001`，另有 `FUSE_PCIE_MAGIC_D` `0x00820520` = `0x16680000`，支持速率向量即使在 PHY 速率被强推到 Gen3 能力的 `0x00340036` 后仍被截在 `0x00000006`。两个未决问题：残余上限是同一组 DEVINIT 字节的重放，还是熔丝三重在下游独立执行；以及，给定一份能重新签名的闪存，单独的五字节 DEVINIT 编辑能否恢复 Gen4。见[Gen3 和 Gen4](../frontier/pcie-gen3-gen4.md)。

### DEVINIT 与 ECC

> [!NOTE]
> **证据在这里背离 DEVINIT**
>
> **这份 VBIOS 分析没有提供 DEVINIT 控制 ECC 的证据。** 整个 ROM 对比中唯一与 ECC 相关的数据点是 InfoROM `ECC` 对象在 A100 上存在、在 170HX 上缺失。54.5 KB 配置表区域的任何地方都没有找到 DEVINIT 侧 ECC 字节。聊天侧把 170HX 的 ECC 行为归咎于 DEVINIT 的理论不受静态分析支持。这是显著的证据缺失而非正面发现，所以置信度为中。

硅片侧佐证：`FEAT_OVR_ECC_PLM` `0x00823800` 冷读 `0xffffff8f`，门控 `0x82380c`、`0x823810` 和 `0x82382C`。HS ROP 能打开它，而**打开它是惰性的**，因为 `0x823814` 的 ECC 启用读出是 POR/熔丝闩锁的，不响应实时覆盖写入；覆盖反正会在 FLR 时还原。名为 `ecc` 的分支完全没有 ECC 代码（只有一个提交 "Fixed dual geometry support"）。ECC 被熔断关闭，无已知杠杆。HBM 堆栈是否带 ECC 供应只得到部分回答：A100 逐 FBPA `CSTATUS_RAMAMOUNT` 的差异被解读为同一批堆栈内 ECC 保留容量，那是一位参与者的推断而非数据手册。见[ECC](../frontier/ecc.md)。

### 运行时重放 DEVINIT

> [!WARNING]
> **实验性质**
>
> 通过 PMU 在运行时重放 DEVINIT **确实**改变了硬件状态，一次会话、一张卡上。它没有产生更多可用内存。

| 寄存器 | 之前 | 之后 |
|---|---|---|
| CFG1 `0x009a0204` | `0x02669000` | `0x22779000` |
| CSTATUS | `0x00000800` | `0x00000800`（不变） |
| LMR `0x00100ce0` | `0x0000028a` | `0x0000028a`（不变） |
| `0x9a038c` | `0xa7` | `0xa6` |
| `0x9a0330` | `0x00100093` | `0x0010009c` |
| `0x9a0334` | `0x002000cf` | `0x00200041` |
| `0x9a0338` | `0x003000ea` | `0x003000f1` |
| `0x9a0390` | `0x00c0052d` | `0x00c00528` |
| `0x9a0394` | `0x000028d9` | `0x0000394f` |
| `0x9a0300` | `0x00000003` | `0x00000003`（不变） |

七个 HBM 时序寄存器中有六个移动到 strap-5 值，但几何仍解析为 40960 MiB，因为档位 `0x77` 被减半为每 FBPA 2048 MiB、横跨 20 个存活 FBPA。strap-5 时序本身加载不了。结果状态在频道内被非正式地称为 "the pg199 config"。PG199 是 NVIDIA 对 Drive A100 的板卡编码，也确实有同名未发布分支，但 `0x22779000` 不是任何正式发布或分支代码写入的值，所以不应把这个标签读成"工具实现了该配置"。

另请注意，**正式发布工具和任何未发布分支都不重放 DEVINIT、不驱动 PMU、不碰 FBFLCN。** 对整个分支集搜索 `devinit`、`PMU`、`FBFLCN` 和 `0x101000`，一无所获。这里描述的所有 DEVINIT 工作都存在于分析制品中，不在发布代码里。

### 显存时钟：一个时钟，四倍

VBIOS 显存字段是**四分之一速率**。这解决了两年多来被记录为 432、729 与 1458 MHz 三方冲突的问题。

| 关系 | 倍率 | `92.00.67`（364 MHz 字段） | `92.00.6D.00.0A`（432 MHz 字段） |
|---|---|---|---|
| VBIOS 字段 | ×1 | 364 MHz | 432 MHz |
| CUDA `deviceQuery` 显存时钟速率 | ×2 | 729 MHz | |
| 营销 / 规格 MHz | ×4 | 1458 MHz | 1728 MHz |
| 有效 Gbps | ×8 ÷ 1000 | 2.9 Gbps | |

1728 MHz 数字通过在一张跑 `0A` 的卡上的 `nvidia-smi` 确认。

> [!NOTE]
> **开放问题**
>
> `0A` 镜像上的 `1728 MHz` 是有效跳线还是升频点。被直接问到时，答案是明显的猜测："我想说 boost"。那个 VBIOS 是否也改变电压、功耗或核心时钟，被问了但从未回答。

> **开放问题**
>
> 是否真的存在一张不同的 "16 GB" 170HX ROM。对比收藏把 `cmp170hx_16gb_92.00.67.00.01.rom` 列为单独文件，版本、构建日期、设备 ID 和子系统都与 8 GB 镜像相同，注释"从未有卡出货"；独立地，TPU 239457 被发现与 8 GB VBIOS 逐位相同。这两者可能是同一文件被数了两次。把收藏文件与 239457 和 257744 的 MD5 或 SHA 对比就能定案。

### 按 SKU 与跨产品 ROM diff

| 对比 | 总差异 | 分解 |
|---|---|---|
| 170HX 8 GB 对 10 GB | 2,684 B | NVGI `0x0000`–`0x5E00` 2,399 B（含四个约 384 B 的 MAC 块，约 1,533 B MAC 内容）；PciAt `0x5E00`–`0xC000` 36 B，全是版本与设备 ID；FwSec 主体 `0xC700`–`0x47700` 249 B，仅训练与配置 |
| Drive A100 对 A100 PCIe 40 GB | 468,557 B（ROM 的 45%） | 签名范围大 96 KB，加完全不同的固件构建 |
| Drive A100 GPU0 对 GPU1 | 49,852 B | 49,797 B（99.5%）InfoROM，55 B NVGI：固件相同，仅逐单元校准 |

8 GB 与 10 GB 镜像之间，NVGI 引导块中**只有两个字节不同**：`0x0004` 是 `0x52` 对 `0x80`（头大小/版本字段），`0x000E` 是 `0x85` 对 `0x57`，子系统 ID 低字节编码 `0x1585` 对 `0x1557`。扣除 MAC 内容后，真正有功能的 SKU 差异极小，与七字节限制的数字一致。

已公布的 Drive A100 区域分解（NVGI 155 B、PciAt 4,799 B、FwSec 主体 91,694 B、未签名尾部 11,142 B、InfoROM 52,847 B）合计 160,637 B，不是 468,557 B。这是源分析中的真实不一致；最可能的解释是区域表只覆盖重叠窗口，而总量是跨镜像的整文件 diff，这些镜像的签名范围相差 96 KB，把其后的所有东西都移位了。没有任何来源调和。

**FwSec 主体大小在每个 GA100 产品线之间都不同**，这在结构上排除了 FwSec/VN 镜像交换（而不只是未测试）：

| 镜像 | FwSec 主体 | 跨度 |
|---|---|---|
| 170HX 8 GB / 10 GB / "16 GB" | 241,664 B（基线） | `0xC700`–`0x47700` |
| 170HX 300 W | 242,176 B（+512） | `0xC700`–`0x47900` |
| A100 SXM4 40 GB | 240,640 B（-1024） | `0xC700`–`0x47300` |
| A100 PCIe 40 GB | 244,224 B（+2560） | `0xC700`–`0x48100` |
| Drive A100 32 GB | **未决**：记录的主体大小（362,496 B）与记录的跨度不一致；`0x5AC00 - 0xC700` = 320,768 B。在重读定案前请用跨度，不用总量 | `0xC700`–`0x5AC00` |

VN 前导在 170HX SKU 间相同，是唯一会让交换看起来可行的事。

## 什么能改、什么不能改

五个目标，按 MAC 范围归属排序。

| 目标 | 偏移 | 在 MAC 内？ | 状态 |
|---|---|---|---|
| CFG1 strap-4 档位字节 | `0x41D53` | 内 | **关闭。** 需要 csecret(2)。由 2026-05-08 使 Booter 卡住的字节翻转证明 |
| PCIe Gen1 锁，5 字节 / 3 个 DEVINIT 位置 | 在 `0x33800`–`0x41200` 内 | 内 | **关闭。** 运行时 Gen2 分支取代了它 |
| ECB 固件块 | `0x14A00`–`0x33800` | 内，且用 csecret(6) 加密 | 内容未知 |
| 功耗上限 250 W 到 300 W | `0x45E45` | 外 | **开放但未测试。** 仅 CH341A |
| `CTRL_OPT` 熔丝表 | `0x47341` | 外 | 调查中，语义未定 |

### 写路径：先验证后写，负载绑定到镜像

一次受控 2×2 实验（VV 认证镜像 × EWR 负载）确立了规则：

| VV 过的镜像 | EWR 负载 | 结果 |
|---|---|---|
| 活镜像 | 活镜像 | ERR = 0 |
| 活镜像 | 8 GB | `0x9C` |
| 8 GB | 8 GB | ERR = 0（成功） |
| 8 GB | 活镜像 | `0x9C` |

第四行是关键：负载就是活的闪存内容，仍被拒绝，因为 VV 认证的是另一份镜像。规则是：用 VV 认证一份真正签名的镜像，然后写*那份镜像的*字节。它被端到端证明：向真实 VBIOS 块写入 7,878 字节外部 8 GB 内容、读回、再逐字节还原。**因此一份真正签名的 80 GB A100 VBIOS 会刷进去。修改过的镜像更早死掉，死在 VV 的 `0x40`。**

> [!NOTE]
> **开放问题**
>
> 缺的是一份签名镜像，让 170HX 的 Board ID 和熔断设备 ID 门在启动时接受；到目前为止每次跨刷都死在那道门，而不是写在写入处。最干净的下一步是对 250 W 卡做**同 SKU** 300 W ROM 的 VV+EWR——它已签名、同设备 ID、同板卡——以确立启动侧的门是 Board ID 还是更窄的东西。

## 失败特征

任何刷写尝试前把这张表放在手边。另见[排障](../procedures/troubleshooting.md)。

| 特征 | 含义 |
|---|---|
| `GFW_BOOT = 0x401` 或 `0x001` | MAC 损坏。签名范围内的一个字节被改了 |
| `GFW_BOOT = 0x8F`，PROM 全读 `0xFF` | FWSEC HS 退出污染。FWSEC 运行了，但 GFW 从未越过它，所以驱动永远到不了 Booter |
| `kgspExtractVbiosFromRom_TU102: did not find valid ROM signature` 然后 `RmInitAdapter failed! (0x62:0x25:2028)` | VBIOS 状态寄存器（SReg）数据被毁。**重刷原厂 ROM 无济于事** |
| `kgspWaitForGfwBootOk_TU102: failed to wait for GFW boot complete: 0x65` | 在 `92.00.66.00.02` 上的 VBIOS 修改尝试期间见过 |
| `RmInitAdapter failed! (0x62:0x55:2674)`，DevID 不变 | 刷了外部（Drive A100）镜像，功能上什么都没发生 |
| `nvflash` 报 `falcon halted` | `nvflash` 带 `--protectoff` 通过了镜像验证，然后运行自己的 SPI 写入 ucode 时失败 |
| VV 错误 `0x40` | 修改过的镜像，在写入阶段之前的验证中被拒 |
| `0xBADF3000` | 上电前 SPI 未写保护 |
| 设备管理器代码 10（Windows） | 测试者制作的每个本地修改 170HX VBIOS 都出现这个 |

## 死路

每条都是带真实结果的真实尝试。没有新信息就不要重试。完整的项目级清单见[死路](../history/dead-ends.md)。

| 尝试 | 结果 |
|---|---|
| 把完整 A100 VBIOS 跨刷到 170HX | 卡在安全模式下不启动且不可用；显存大小、SM 数与着色器数不变；只有子系统 ID 变。2024-07-17 证伪，2026-07-19 与 2026-07-25 再次确认 |
| 把 A100 VBIOS 刷到改过跳线的 10 GB 卡 | 砖掉卡。恢复需要用 SPI 编程器重刷保存的原厂 ROM |
| 在镜像中把跳线字节 `44` 编辑成 `66` 并修校验和 | 驱动加载失败。与 Falcon 在上电时验证并把芯片丢进非安全模式一致。被运行时 `0x009a0204` 的 CFG1 写入取代 |
| 签名范围内单字节翻转（`0x41D53`） | Booter 卡住，`GFW_BOOT=0x001` |
| 简单 ROM 拼接，把 A100 区块塞进 170HX 镜像 | 双重失败：每个 ROM 的跳线表偏移不同，且每个区块都独立 MAC |
| SKU 间 FwSec / VN 镜像交换 | 被主体大小不匹配在结构上排除 |
| A30 FWSEC 模块移植 | 落地即死：10 GB 170HX 与 A30 之间的签名代码模块**已经相同**，所以模块毫无增益。差异数据是验证区内的非代码配置 |
| `nvflash` 带打补丁的镜像验证加 `--protectoff` | 走得更远，然后 nvflash 运行自己的 ucode（即 SPI 写入器本身）时 `falcon halted`。`omgvflash` 和 `nvflashk` 同样拒绝编辑过的 BIOS |
| 从软件写 SPI 控制器寄存器 | 见下文。硬关闭 |
| NVGI 作为攻击面 | 被启动顺序关闭：DEVINIT 覆盖 NVGI 的 MR1/MR2/MR3 写入，FWSEC 重新提升 NVGI 降下的任何 PLM |
| 对 VBIOS 的 TOCTOU | 清掉了 SReg 数据；卡以无有效 ROM 签名失败，重刷原厂也无法恢复 |
| 把 8 GB VBIOS 刷到 10 GB 卡 | 用打补丁的 nvflash 成功刷入并还原，但 8 GB 镜像在 10 GB 卡上不启动，跳线编辑会在刷写期间通过镜像检查失败。注意：两次刷写之间没有重启，所以是提示性而非决定性 |
| Maxwell 时代 ECC 解锁移植到 Ampere | 从未在 GA100 上演示；作者自己也警告对 Ampere 不平凡 |
| 把 sim/emu HBM2e ROM 当模板 | Sim ROM 约 230 KB、布局完全不同，而且即使在那里也只有主跳线表被从 `66` 提到 `77`，`0x1AD72` 的副本仍读 `00 90 66 02` |
| 修改已解密的 VBIOS | 降电压与显存时序位置被识别出来，但**每次尝试的修改都导致驱动加载失败**。打补丁让驱动接受修改状态从未试过 |
| 自签自定义 VBIOS | 据报告在一次泄露窗口期间短暂可行。现在没有可用的签名能力。把泄露窗口细节当作轶事 |
| 以 VBIOS 修改绕过 GSP-RM 问题 | "Checksum failed"。用 VBIOS 刷写击败 Booter 芯片 ID 门"完全没用" |
| 相信 TechPowerUp 的 "Memory Size" 列 | 它不映射到 `.rom` 文件中的任何字段 |

### SPI 控制器无法从软件写入

明确记录以免重试。refire 链 HS 利用**确实**成功打开了 `0xD7D8` 的 SPI PLM，设为 `0x00000000`，以 rp=0 wp=0 确认打开——这证明该利用能从 HS 模式触达并修改 PLM。尽管 PLM 读起来完全打开：

| 寄存器 | 写入 | 回读 |
|---|---|---|
| `SPI_DATA` `0xE4A0` | 从 PL0 写 `0xDEADBEEF` | `0x00000000` |
| `SPI_CTRL` `0xE5A0` | 从 PL0 写 `0xDEADBEEF` | `0x00000000` |
| `ROM_SERIAL_BYPASS` `0xE204` | 从 PL0 写 `0xDEADBEEF` | `0x00000000` |
| `0xE4A0` / `0xE5A0` | 直接 HS-ROP 写入 | 报告 "~"（未落位），寄存器保持 `0x0` |

结论：安全启动状态机强制的一个硬件写过滤器会丢弃除 GFW 启动固件（启动期间的 SEC2/PMU）外任何代理对 SPI 控制器的所有写入。**这张卡上没有任何软件路径能写 CFG1 闪存字节。**

## VBIOS 专属的开放问题

按最易着手优先排序。横切清单在[开放问题](../frontier/open-questions.md)。

1. **把 `0x45E45` 的 250 W 刷成 300 W 功耗上限。** 三字节字段读 `90 D0 03`，应变成 `E0 93 04`。它位于 15,616 字节未签名尾部（`0x43A00`–`0x47700`）往里 9,285 字节，所以不可能破坏 MAC，与已经启动成功的 `0xFF` 填充测试同属一类。唯一的阻碍是 `nvflash` 连未签名尾部改动都被拒，所以需要 CH341A、拆散热器和重涂硅脂。2026-05-09 起开放且未测试。
2. **确定 `NV_FUSE_CTRL_OPT_*` 语义。** `0x47341` 的 25 条目表在 13 张探测过的 GA100 卡上全读零。另有：`0x001404` 的 `PBUS_SW_SCRATCH(1)` 读 `0x20042000`、第 14 位清零，而第 14 位*据信*（从未写测）能让固件跳过它的 CTRL_OPT 清零循环。对已在熔丝下限的卡惰性。
3. **在 `0xFE504` 注入 HULK 证书**（见上文）。
4. **恢复 csecret(2)**，它将一次打开所有 MAC 内编辑——全部七个限制字节。离线预言机消除了 DFA 行动期间对刷写循环的需要。工作量极高。
5. **未签名尾部的显存编辑会生效吗？** 上面描述的 `freqDelta` 实验。
6. **用调试 IMEM 配方解密生产 Falcon/DEVINIT 代码。**
7. **A30 对齐线索。** A30 VBIOS `92.00.66.00.0x` 被报告与 10 GB 170HX 的 `92.00.66.00.0x` 几乎相同，理由是 A30 是运行三个 HBM2 堆栈的 A100，堆栈数由熔丝控制。复杂之处：签名代码模块已经相同，所以唯一价值在被覆盖区域内的非代码配置数据——那正是需要 csecret(2) 的部分。把 A30 ROM 与 10 GB 170HX ROM 做 diff 会枚举出那份配置差异。
8. **diff 软件与硬件 SPI 流量。** 未经证实的第三手说法是 `nvflash`/`omgvflash` 会写裸 SPI 编程器不碰的"中间寄存器"。在软件与硬件刷写期间于 SPI 总线上挂逻辑分析仪，会便宜且决定性地回答。

> [!NOTE]
> **开放问题**
>
> 跳线表是否*在实践中*受 MAC 验证。一种立场认为即使 `0x41D53` 在声明范围内，Falcon 也可能实际不查它。反方是 2026-05-08 在该精确偏移的单字节翻转测试，它让 Booter 卡住。天平强烈倾向"它被验证"。复杂之处是，频道内观察到的失败（"改不了跳线或镜像检查失败"）是**主机侧 nvflash 检查**，不是启动时 Falcon 检查，所以两种立场部分在互相错过。用 CH341A 刷一份跳线编辑镜像（完全绕过 nvflash）加一次 `GFW_BOOT` 读取就能定案。没人报告做过。

> [!NOTE]
> **开放问题**
>
> 170HX 限制住在熔丝还是 VBIOS。工程样品 A/B 刷写显示 VBIOS 承载显存上限、PCIe 上限和*部分*计算惩罚，但不是全部：把 170HX VBIOS 跨刷到一颗跳过签名检查的工程样品 GA100 上，只施加了 **1/12 FP64 和 1/8 FP32**，对真 170HX 的 **1/64 和 1/32**——FP64 残留约 5 倍、FP32 约 4 倍，必然来自别处。正式发布解锁通过运行时写 SS0/SS1 恢复完整 SM 吞吐，强烈暗示残留是 `0x00823804` 门控的功能覆盖，但工程样品实验从未在同时写 SS0/SS1 的情况下重跑。正式解锁是纯软件并不能定案这个问题：它在运行时覆盖状态，而不是证明默认值来自哪里。

> [!NOTE]
> **开放问题**
>
> 供应商的批次级 VBIOS 差异。一个自称批量持有方技术雇员的商业来源说"我们这里有两种 170hx 的 VBIOS，其中一种带宽更高"。没有给版本字符串和带宽数字。至少与 `92.00.67.00.01`（364 MHz 字段）和 `92.00.6D.00.0A`（432 MHz 字段）都在现场一致。从记录上无法解决。
