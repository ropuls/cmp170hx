# NVLink 硬件

## 本页涵盖

CMP 170HX 上 NVLink 的状态：板上物理上有什么、熔丝怎么说、启动日志里能看到什么以及它为什么误导、以及具体关死了哪几扇门。解锁尝试、提案与开放研究见[NVLink 前沿](../frontier/nvlink.md)；本页是硬件描述。

**结论：CMP 170HX 上的 NVLink 不能用、对任何人都从未能用过，而且是被 OTP 熔丝而不是软件禁用的。** 链路没有损坏，连接器在 PCB 上物理存在，晶片按完整的十二链路 GA100 规模刻度，但这一切都没用，因为 `0x00820684` 的 `FUSE_NVLINK_DIS` 读 `0x00000007`，而且不存在能推翻它的覆盖寄存器。解锁器中没有代码碰 NVLink——master 和全部十二个未发布分支都没有。

## 熔丝证据

在 2026 年 5 月的跨卡调查中于两块物理 170HX 单元上测量，并在 2026-05-07 到 2026-07-27 之间至少五次在 `0x20C2`（8 GB）和 `0x2082`（10 GB）两个 SKU 的活卡上经 BAR0 独立重读。

|---|---|---|---|---|---|---|---|---|

直接得出三个结论：

1. **这是刻意的分段，不是回收分 bin。** 记录坏链路组的字段 `FUSE_NVLINK_DEFECTIVE` 在 170HX 和 15 卡调查中每个返回值上读 `0x00000000`；A16 列读的是 `BAR0` 占位符，因为它的 BAR0 太小够不到大部分熔丝寄存器；ES 列空白。如果 NVIDIA 是因为测试失败才熔断这些链路，那就会写在这个寄存器里，而它是空的。
2. **晶片带完整 GA100 NVLink 配置。** `PTOP_SCAL_NUM_NVLINK = 0x0000000c` 描述硅片中内建的十二条链路，不受禁用熔丝影响。它与全部三个 A100 SKU 及 Drive A100 逐字节相同。
3. **禁用经由 STATUS 路径到达，而不是通过控制覆盖。** 两个 `CTRL_OPT` 寄存器都读零，所以没有任何东西设置它们；原始熔丝直接传播进只读状态寄存器。这与卡上其他每个筛选是同样的模式，记录在[熔丝与 OTP](fuses-and-otp.md)上。

### 这不是挖矿 SKU 专属限制

Drive A100 32 GB（PG199，`GA100-550F-A1`，`FUSE_PCIE_DEVIDA` = `0x000020bb`、`FUSE_PCIE_DEVIDB` = `0x000020fb`），在两块物理板上测量，读 `FUSE_NVLINK_DIS` = `0x00000007` 和 `STATUS_OPT_NVLINK` = `0x00000007` 完全一样。三个常规 A100 SKU 都读 `0x00000000`。因此带 NVLink 熔断的 GA100 对 NVIDIA 来说是正常的出货方式，这削弱了"这个特定禁用是加密挖矿对策、可能有对应逃生舱"的任何理论。

另请注意，一些文章称"也读 7"的那块 `0x20bb` "A100 级对比卡"**就是**这块 Drive A100，不是第四个 A100 SKU。设备 ID 一致。

### 两条值得带上的更正

> [!NOTE]
> **开放问题：3 位禁用字段对 12 条物理链路**
>
> `FUSE_NVLINK_DIS[2:0]` = `0x7` 配 `PTOP_SCAL_NUM_NVLINK` = 12，而 `STATUS_OPT_NVLINK` 标注为 16 位字段却也读 `0x00000007`。工作假说（语料库中无物证实）是**三组链路、每组四条**（12 = 3 × 4），这能同时解释反复出现的"所有组"措辞和 RTX 3080 的 `0x1` 对它的 `PTOP_SCAL_NUM_NVLINK` `0x4`。能定案的东西：一块已知*部分* NVLink 筛选的 A100 做对比，或厂商对 GA100 上 `NV_FUSE_OPT_NVLINK_DISABLE` 字段宽度的文档。语料库中两者都不存在。

## 物理板卡

CMP 170HX 复用 A100 的板卡布局。**NVLink 边缘接口的金手指物理存在，且有三个桥接连接器位置。** 这由 2023 年 10 月的一次外部拆解确立，2026 年卡主们也表示同意。

> [!NOTE]
> **更正："CMP 的 PCB 完全没有 NVLink 连接器"说的是 90HX**
>
> "外壳有 NVLink 连接器开孔，但 PCB 没有"这个观察在档案里出现两次：一次归于 170HX，一次——带着更完整的上下文"同一家不知名品牌还做 RTX 3080 20 GB [它]用带 NVLink 连接器的 PCB"——归于 **CMP 90HX**。90HX 是 GA102 RTX 3080 级挖矿板，正对应那句关于 RTX 3080 20 GB 姊妹卡的描述。套在 170HX 上，该说法与拆解证据矛盾。请把归于 170HX 的那次，以及某篇文章括号里那句"CMP 板卡没有 NVLink 连接器"，视为误归因。

### 导流罩挡路

铝制导流罩盖住连接器区域。在它被机加工、拆除或更换之前，什么也插不进去。这与 Tesla P100 情况相同：NVIDIA 在 A100 上给连接器罩了橡胶帽，官方桥卡扣在 A100 外壳上——170HX 没有这些。存在一张 P100 打磨开孔的存照，其电气结果未知。一块水冷头据报告会露出 NVLink 区域。为物理访问重新设计散热器，被列为该领域的实际第一步，先于任何电气工作。见[散热](../operations/cooling.md)。

### 焊装还是缺件：倾向缺件，未定案

这是关于这块板最有后果的开放问题，因为它决定熔丝绕过是否还有用。证据的天平倒向缺件一侧：记录中唯一直接的 A100 对 CMP 板卡对比报告缺件，而反方说法是从原理图读出来的，不是从板上读出来的。

**缺件的证据。** 2023 年拆解说"因为 CMP 170HX 使用相同的 NVIDIA A100 电路板，NVLink 接口的金手指存在，但该功能不支持，PCB 上所有组件均未焊装"，并分别说"与 NVLink 接口相关的 IC 也缺失"。一位研究者从 A100 原理图出发，识别出 GPU 上方五颗具体被删减的电阻：`R234`（000）、`R237`（NP）、`R236`（1k）、`R1024`（000）和 `R238`（000），全部来自第 17 页，外加 `R976`、`R1029` 和 `R1030`，以及三颗 GPU 到地终端电阻且看不到走线。第二位参与者回忆 NVLink 电源部分有缺失器件。

那份清单是在两块板都在眼前时产出的：这些电阻"在真 A100 上焊装，但在 CMP 上缺失"。

**焊装的证据。** 项目自己的 VBIOS 对比表记录"NVLink 桥：外部桥缺失（PCB 完全焊装）"，那是项目文档的一行，不是检视结果。在电阻清单贴出两小时前，另一位研究者说"我不认为有任何缺失的 NVLink 器件。按原理图，GPU 晶片直接连到边缘连接器"，把混淆归咎于桥携带有源器件"包括 ROM 芯片"。事后对官方 A100 桥的直接检视没有发现 EEPROM 和时钟发生器，所以那个说法的基础不成立。

**复杂的细节：** `R237` 在 A100 原理图里本身就标记为 **NP**（不焊装），所以这五颗中至少一颗预期在真 A100 上也缺失。这干净地说明了目测对比多么容易误导。

**能定案的东西：** 一张去罩 170HX 与真 A100 在这些位号上的并排高分辨率照片，或从 NVLink 边缘金手指到 BGA 球 `F1` 和 `G1` 的导通检查。两者都不存在。注意 `R976` 落在芯片下方的 `F51` 球上，该封装至少有 82 行球，所以没有专业的红外 SMD 返工或拆晶片够不到它；`R1029` 和 `R1030` 在芯片边缘连到 `F1` 和 `G1`，用细线可以够到。

即使完美的返工也留下 `FUSE_NVLINK_DIS` = `0x00000007`。

## 启动日志里出现什么

每次 170HX 带 NVIDIA 驱动启动都会产生这一行：

```text
nvidia-nvlink: Nvlink Core is being initialized, major device number 236
```

**它无害，也不是链路训练的证据。** 它来自 `nvidia-nvlink.ko` 软件核心库的 `nvlink_linux.c:344`，宣布模块已加载。它以 `DBG_INFO` 记录，在 GPU 与 GSP 启动之前的早期模块加载期间触发，并且几乎在任意 NVIDIA GPU 的每次驱动加载时都出现。"236" 是 `alloc_chrdev_region` 动态分配的 Linux 字符设备主号，可以随启动而异，所以日志里不同的数字也什么都不说明。

权威检查只需一条命令：

```console
$ nvidia-smi nvlink -s
Device does not have or support Nvlink.
```

该输出在语料库中只记录过一次：2026-07-24，来自一台租赁的八卡已解锁 64 GiB 卡主机。请把它视为与熔丝一致，而不是广泛调查。想要确定就与熔丝互相印证：

```bash
# STATUS_OPT_NVLINK，只读生效状态
sudo python3 - <<'EOF'
import mmap, struct
BDF = '0000:81:00.0'
with open(f'/sys/bus/pci/devices/{BDF}/resource0','rb') as f:
    bar = mmap.mmap(f.fileno(), 0, access=mmap.ACCESS_READ)
    for name, off in (('FUSE_NVLINK_DIS', 0x00820684),
                      ('STATUS_OPT_NVLINK', 0x00820DB8),
                      ('FUSE_NVLINK_DEFECTIVE', 0x0082068C),
                      ('PTOP_SCAL_NUM_NVLINK', 0x0002246C)):
        print(f'{name:22s} 0x{off:08x} = 0x{struct.unpack_from("<I", bar, off)[0]:08x}')
EOF
```

任何 CMP 170HX 上预期：`0x00000007`、`0x00000007`、`0x00000000`、`0x0000000c`。

## 为什么它保持锁定

四扇独立的大门，每扇因不同原因关闭。四扇都必须打开。第五节记录了解锁器从不尝试任何一扇。

### 1. 值来自 OTP，不是软件

禁用从 `0x00820684` 的 OTP 熔丝读出，并镜像进只读状态寄存器。驱动、VBIOS 签名区域或未签名 FwSec 尾部中没有任何软件设置会产生它。"NVLink 也是软件锁的"这一说法，在 2026-07-27 仍在流传，就是错的。

### 2. 没有可写的 FEAT_OVR 寄存器

计算解锁靠打开 `0x00823804` 的 `FEAT_OVR_PLM` 并写入同块的功能覆盖寄存器。显然的问题是同一招能否够到 NVLink。不能，因为该块不含任何 NVLink 条目。`0x00823800` 到 `0x0082382C` 的完整清单：

| 地址 | 寄存器 |
|---|---|
| `0x00823800` | `FEAT_OVR_ECC_PLM` |
| `0x00823804` | `FEAT_OVR_PLM` |
| `0x00823808` | `FEAT_OVR_QUADRO` |
| `0x0082380C` | `FEAT_OVR_ECC` |
| `0x00823810` | `FEAT_OVR_ECC_1` |
| `0x00823814` | `FEAT_READOUT_0` |
| `0x00823818` | `FEAT_READOUT_1` |
| `0x0082381C` | `FEAT_OVR_SM_SPD` |
| `0x00823820` | `FEAT_OVR_SM_SPD_1` |
| `0x00823824` | `FEAT_OVR_ROW_REMAP` |
| `0x00823828` | `FEAT_READOUT_2` |
| `0x0082382C` | `FEAT_OVR_ECC_2` |

十二个寄存器，覆盖 ECC、Quadro 分类字、SM 速度选择、行重映射器和三个读出。没有 NVLink 的。因此"`FUSE_FEAT_OVR_DIS` 在所有卡上读零，所以对 NVLink 掩码做 FEAT_OVR 式攻击至少没有明显被排除"的论点，虽然对熔丝的判断是对的，结论却是错的：它**被**排除了，因为没有那样的寄存器可写。

### 3. CTRL_OPT 覆盖路径被熔丝禁用

`0x008209B8` 的 `CTRL_OPT_NVLINK` 被文档化为生效的逐链路启用，它读零，且被描述为可写。它是整个语料库中被引用最多的候选杠杆。它在这里也几乎可以肯定是惰性的，因为 `0x00820040` 的 `FUSE_EN_SW_OVERRIDE` 在两块 170HX、全部三个 A100 SKU 和 Drive A100 上读 `0x00000000`，而每块消费级和工程样品部件读 `0x00000001`。`0x00820084` 的 `FUSE_DIS_SW_OVR` 在每张卡上读 `0x00000001`。在未签名 FwSec VBIOS 尾部（`0x43A00` 到 `0x47700`）偏移 `0x47341` 找到的 25 条目 `NV_FUSE_CTRL_OPT_*` 表在 13 张探测过的 GA100 卡上全部读零，在这块硬件上是惰性的。

> [!NOTE]
> **开放问题：从来没人执行过那次写入**
>
> 在所有 31 份存档的解锁器附件和每件净室制品中，NVLink 只作为熔丝读出出现。没有探测脚本、没有覆盖尝试、没有记录的写入。强先验是向 `0x008209B8` 的写入被丢弃、`STATUS_OPT_NVLINK` 保持 `0x00000007`。这个阴性结果仍然值得记录在案，因为目前语料库无法说明它是否被试过。实验是在一张可牺牲卡上做读-写-读，然后重读 `0x00820DB8`。

### 4. 没找到可欺骗的熔丝消费者

CMP DevInit 固件**读取** `0x820684`。DevInit 反汇编中 `0x1482xxxx`（MMIO `0x82xxxx`）访问的完整清单是 `0x820C14` 和 `0x820D38`（FBIO 与 FBP 筛选）、`0x820684`（`FUSE_NVLINK_DIS`）、`0x82380C` 和 `0x823814`、`0x820520`（`MAGIC_D`）和 `0x820148`。任何源码里都没有写它的东西，也没有点名过任何生效的覆盖消费者。没人追踪过 DevInit 读到值之后拿它做什么——这是该领域仅剩的可行软件问题。

### 5. 解锁器完全没有 NVLink 代码

对整个正式发布 `master` 树 grep `nvlink` 和每个 NVLink 寄存器地址，一无所获：`common/constants.yaml`、`driver/build.sh`、`driver/VERSION`、`install.sh`、`remove.sh`、`README.md`，以及六个补丁，都没有。`constants.yaml` 只声明两个驱动版本、两个设备 ID、计算值和两个内存 profile。

在全部十二个未发布分支（`80`、`Gen2`、`PG199`、`clanker/driver-port`、`debug-gen2`、`deced`、`docs`、`ecc`、`far`、`housekeeping`、`memory`、`multiple-cards`）中，NVLink 的全部存在就是一个词。`housekeeping` 和 `memory` 分支添加了一张功能状态表，相关行读：

```markdown
| ECC          | Planned |
| NVLink       | Planned |
```

## NVLink 本来值多少

收录是因为缺失功能的代价一直在两个方向上被误述。

| 量 | 值 | 置信度 |
|---|---|---|
| A100 PCIe 每桥 NVLink | 200 GB/s | 高 |
| A100 PCIe 成对总计，三桥全上 | 600 GB/s | 高 |
| 文档化的 Ampere PCIe 拓扑 | 2 块 GPU，三桥全部必需 | 高 |
| Ampere 端口结构 | 4 个子端口 × 4 通道，每通道 50 Gbps = 每端口原始 800 Gbps（来源说 200 Gbps；分解与数字不可能都对） | 中 |
| GA102 第三代每链路 | 双向 14.0625 GB/s，四个 x4 链路 | 高 |
| GA102 第三代总计 | 双向 56.25 GB/s，两块 GPU 之间总聚合 112.5 GB/s | 高 |
| 170HX 今天的互连基线 | PCIe 第 1 代 x4，约 1 GB/s | 高 |

NVSwitch——以及任何比成对更宽的东西——只存在于 DGX 等 SXM 平台内。官方 A100 桥是一块**裸的被动 PCB**：没有时钟发生器、没有 EEPROM、没有 retimer、没有包处理 ASIC，由直接检视确立，SXM2 基板也有独立佐证。消费级 RTX 3090 桥确实带时钟发生器，据信是因为 NVIDIA 不能假设消费级主板提供相同的 PCIe 参考时钟。从 Ampere 到 H200 NVL 一代的所有桥都被评估为被动。

这对推理实际能买来多少本身就未定：一对 RTX 3090 在 vLLM 张量并行下的第一手测量只显示约 10% 的吞吐提升，而第三方发表的同类配置数字约为 48%。模型、量化、批大小与并发不同或未说明。"170HX 因为基线是 Gen 1 x4 而非 Gen 4 x16 会获益大得多"的论点只是推理，熔丝还在就无法测试。见[大模型推理](../operations/llm-inference.md)。

做池化算术时注意：四张已解锁 8 GB 卡给出 256 GB（4 × 65536 MiB），四张已解锁 10 GB 卡给出 160 GB（4 × 40960 MiB）。广为引用的四张 10 GB 卡 320 GB 数字假设了 80 GB 配置，而那被尝试过并发现不稳定。见[80 GB](../frontier/80gb.md)。

**今天可行的替代方案是 PCIe 对等直连，不是 NVLink。** 见[对等直连](../frontier/p2p.md)。

## 常见错误答案

| 说法 | 为什么看着对 | 什么杀掉它 |
|---|---|---|
| "NVLink 在启动日志里，加个桥就行" | dmesg 行确实每次启动都出现 | 那是软件核心库宣布自己已加载，`DBG_INFO`，在 GPU 启动之前 |
| "NVLink 是软件锁的" | 170HX 的另外几个限制确实是 | 值来自 OTP，镜像进只读寄存器 |
| "名为 HULK 的加密是阻碍" | 它是唯一公开的解释，在一个看起来很权威的页面上 | 该站维护者 2026-07-20 弃之，页面作者自己也说它过时；熔丝读出、VBIOS 转储或 DevInit 反汇编中没有任何东西佐证它 |
| "`PHYS_DMG = 1` 意味着链路被标记为损坏" | 寄存器名说物理损坏 | 它在全部十四张探测卡（包括健康的 A100）上都读 `1`。它是写入安全位 |
| "3090 读 0 条链路，所以 170HX 放弃 12 对 0" | 这是项目自己探测脚本里的一句注释 | 除 A16 外每块 GA10x 部件都实测 `0x4` |
| "晶片 NVLink 测试失败，所以被分 bin" | 回收分 bin 通常就是这样 | `FUSE_NVLINK_DEFECTIVE` 在每张探测过的卡上 = `0x00000000` |
| "Titan V 的 NVLink 在 VBIOS 里被禁用，所以这也是固件门控" | 早期 NVIDIA 部件上确有其例 | 在 170HX 上值来自 OTP 熔丝，不是 VBIOS 设置。机制不通用 |
| "写 `CTRL_OPT_NVLINK` 就打开了" | 被文档化为生效的逐链路启用，读零，描述为可写 | `FUSE_EN_SW_OVERRIDE` = `0`。强先验，从未真正测过 |

更多带日期和来源的见[死路](../history/dead-ends.md)。
