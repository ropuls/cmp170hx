# 硬件概览：完整规格

**本页涵盖：** NVIDIA CMP 170HX 已确认的全部规格，原厂状态与解锁状态并排对照，两个 SKU 分别列出。凡是有争议、因卡而异、或从未实测的数据，本页会明确说明，而不是默默二选一。

一句话总结：CMP 170HX 是一块 **GA100** 部件，与 A100 同晶片，两个 SKU 均搭载 70 个 SM、4480 个 CUDA 核心，计算能力 8.0。它的限制来自四套彼此独立的机制，各有各的故事：OTP 熔丝设定的 SM 发射速率限制（已被软件破解）、跳线选择的内存几何配置（已被软件破解）、PCIe **速率**上限（已被软件破解，但仅存在于未发布的实验分支上）、以及 PCIe **宽度**上限——那是 PCB 缺件，只能用烙铁修复。NVLink 和 ECC 被熔断关闭，目前没有已知杠杆。NVLink 是否还在板卡层面缺件，尚无定论。

> [!NOTE]
> **对现有社区 wiki 的更正**
>
> 有三处广泛流传的错误，在此附上证据予以更正。
>
> 1. **SM 数量。** 8 GB 与 10 GB 两个 SKU 暴露的恰好都是 **70 个 SM / 4480 个 CUDA 核心**。这是由一位同时持有两个 SKU 的测试者、一份八设备枚举报告（八张卡全部报告 `cu: 70`）、以及四份独立的拓扑报告共同验证的。任何给出 10 GB 卡不同 SM 数、或与自家注释矛盾的表格都是错的。
> 2. **"PCIe 第 1 代 x4，固件锁定"只说对了一半。** *速率*上限由固件和熔丝共同强制，已被软件破解。*宽度*限制根本不是固件问题：16 条通道中有 12 条出厂时没装交流耦合电容。通道熔丝是干净的（`OPT_PCIE_LANE_DISABLE` = `0x00000000`），而一张未改动的原厂卡运行 Gen2 代码时报告 `LnkCap: Speed 5GT/s, Width x16`，`LnkSta` 却仍然显示 `Width x4 (downgraded)`——这证明限制在板卡层面。另请注意，Gen2 从未在虚拟机直通或 Thunderbolt 下复现成功。
> 3. **"解锁后 FP64 是 6.44 TFLOPS"与"11.6 TFLOPS"的矛盾** 其实是非张量路径与张量路径的混淆，并非真正的矛盾。两个数字都是真实的。见[计算吞吐（实测）](#计算吞吐实测)。

### SM 筛选是按卡而非按 SKU

每张被检视的 170HX 都枚举出 5 个 GPC / 35 个 TPC / 70 个 SM，而 70 已经是熔丝下限：`CTRL_OPT` 对典型卡来说毫无损失。具体哪几个 GPC 被禁用随卡而异，且不随驱动版本变化。一个下午读出的四张卡：

| `OPT_GPC_DISABLE`（`0x820350`） | 关闭的 GPC | SKU |
|---|---|---|
| `0x85` | 0、2、7 | 10 GB |
| `0x45` | 0、2、6 | 8 GB |
| `0x13` | 0、1、4 | 8 GB |
| `0xa8` | 3、5、7 | 10 GB |

`STATUS_OPT_GPC`（`0x820c1c`）总是与之镜像一致。关键在于，在若干张禁用掩码置了三个位元的卡上，`OPT_GPC_DEFECTIVE`（`0x8205c4`）读值为 `0x00000000`——也就是说这些 GPC 是物理完好的硅片，只是为达到产品规格而被关闭。这里确实有可争取的空间，但目前找到的每一条写入路径都被闩锁：以 HS 特权写入 `0x820350`、`0x820c1c`、`0x820768` 和 `0x820084` 都原样读回，而用三种方式强推 `gpcMask`（`0x408970`）都会让它重新断言为 `0xdc` 并导致 `cuInit` 段错误。市面上一张罕见的卡曾被 `CTRL_OPT` 扫到熔丝下限以下（56 个 SM），之后又夺回了 6 个 SM。参见 [GA100 硅片](ga100-silicon.md) 和 [熔丝与 OTP](fuses-and-otp.md)。

> [!NOTE]
> **开放问题：8 GB 卡的真实 HBM 时钟**
>
> 三种惯例同时在流传，且从未被调和。规格数据库和一份 2023 年的 `deviceQuery` 说是 **1458 MHz**（报告为 729 MHz 再按惯例翻倍），对应 1492.99 GB/s 上限。一份 2026-07-27 的直接测量说是 **1728 MHz**，即每引脚 3.456 Gbps、1769 GB/s 上限。第三种说法把 8 GB 卡定为 398 MHz、A100 定为 304 MHz，乘以四分别是 **1592** 和 1216 MHz。实测 1679–1699 GB/s 的读取带宽排除了那次运行是 1458 MHz，但无法在 1592 与 1728 之间取舍。能一锤定音的做法：直接读取原始 FBPA PLL 寄存器并公布分频链。

> [!CAUTION]
> **一次跑完不能证明时钟偏移是安全的**
>
> 在调参参考卡（上限 1400 MHz）上，+250 MHz 完整跑过三轮全显存模式扫描零错误，+300 MHz 跑过四轮零错误，但 **+325 MHz 在未崩溃的情况下静默损坏了内存**：三轮扫描分别返回 6、3、0 个错误。那里的安全窗口只有一个 25 MHz 步进宽，再往后故障模式是坏数据而不是崩溃。每个候选设置都要以四轮全显存扫描为准，而不是两轮；而且注意每张卡硅片个体差异意味着在某一个序列号上验证过的偏移对另一张卡说明不了任何问题。细节与完整故障矩阵见[调参](../operations/tuning.md)。

| 量 | 8 GB SKU | 10 GB SKU |
|---|---|---|
| PCI ID | `10de:20c2`（`0x20C2`） | `10de:2082`（`0x2082`） |
| 显存类型 | HBM2e（SK Hynix） | HBM2（Samsung）。供应商区分是依据时钟、稳定性和 GPU-Z 读取推断的，并非来自封装标记：见[板卡与型号变体](board-and-variants.md) |
| 原厂报告容量 | 8192 MiB（CUDA 报告 7961 MB） | 10240 MiB |
| **解锁后容量** | **65536 MiB（64 GB）** | **40960 MiB（40 GB）** |
| 启用的 FBPA / FBP | 16 / 8 | 20 / 10 |
| 总线宽度 | **4096 位** | **5120 位** |

| 解锁后 CFG1 | `0x02779000` | `0x02669000` |
| 原厂 LMR `0x00100ce0` | `0x00000208` | `0x00000288` |
| 解锁后 LMR | `0x0000020B` | `0x0000028A` |
| `targetFbBytes` / `fb_length` | `0x0000001000000000`（64 GiB） | `0x0000000A00000000`（40 GiB） |
| 原厂 `CSTATUS_RAMAMOUNT` | `0x200`（每 FBPA 512 MiB） | `0x200` |
| 解锁后 `CSTATUS_RAMAMOUNT` | `0x1000`（每 FBPA 4096 MiB） | `0x800`（每 FBPA 2048 MiB） |
| 扫除的 FB 单元 | 2 个 FBP 有缺陷、2 个被禁用（检视过一张卡） | `OPT_FBPA_DISABLE` = `0xc3`；fbpa00/01/06/07 关闭 |
| ECC | 熔断关闭 | 熔断关闭 |

解锁常量不是凭空造的：`0x02779000` 字面就是 A100 PCIe 80 GB 的原厂 CFG1 字，`0x02669000` 是 A100 PCIe 40 GB 与 A100 SXM4 40 GB 的原厂字。解锁恢复的是真实的 A100 几何配置。LMR 以 `MiB = MAG[9:4] << SCALE[3:0]` 编码帧缓冲总大小，每 FBPA 容量随后为 `2^(SCALE+1)` MiB。完整讨论见[内存几何](../unlock/memory-geometry.md)和[内存子系统](memory-subsystem.md)。

> [!NOTE]
> **内存几何配置扛不过 FLR 或断电；计算解锁可以**
>
> SS0、SS1 和 `0x00823804` 能扛过 FLR；CFG1/LMR 几何改写不行。这个不对称性正是计算先于显存交付的原因，也是为什么下面的 DtoD 带宽行都把"无 FLR"列为限定条件。

> [!WARNING]
> **80 GB 配置不是第三个选项**
>
> 实验性的 `80` 分支在自己的 README 中声称可用，实际不可用。它写入 CFG1 `0x02779000`、LMR `0x0000028A` 和 `fb_length` `0x0000001400000000`，三层之间互相矛盾——这正是它在恰好 40 GiB 处折叠的最佳解释（`constants.yaml` 里的 `0x0000028B` / `81920` 是惰性元数据，`build.sh` 从不读取）。一个净室脚本写入一致的 `LMR 0x0000028B` 可以消除折叠，但它未随版本发布，并且仍会在大约一个 CUDA context 之后丢失设备。卡报告约 81920 MiB，77 GiB 的密集填充可以跑过，但访问超过约 40 GB 的内核会导致致命 GPU 丢失，与功耗上限无关。报告的 Xid 码包括 Xid 31（被描述为无害）和 CUDA 内存测试后的 Xid 154；最主要的报告症状是卡死。Xid 31 的说法来自一位旁观者，并未被持有故障卡的测试者证实为*那个*特征码。每次触发只允许一个 CUDA context。见[80 GB 前沿页面](../frontier/80gb.md)。

## 计算吞吐（实测）

锁定与解锁状态，原厂时钟。解锁是一次寄存器写入，不改变任何时钟，所以除特别说明外，以下每个数字都是原厂时钟下的数据。

| 数据类型 / 路径 | 锁定 | 解锁 | 提升 |
|---|---|---|---|
| FP32 非张量（FFMA） | 0.30–0.41 TFLOPS | **12.2–12.8 TFLOPS** | 26–32 倍 |
| FP32 理论值 | 不适用 | 12.63 TFLOPS（4480 × 2 × 1410 MHz） | 卡能达到其约 99% |
| FP32 非 FMA（对照） | 4.31–6.29 TFLOPS | 不变 | 从未被限速 |
| FP64 非张量 | ~0.20 TF/s | **6.2–6.3 TFLOPS** | FP32 的一半，完整 GA100 速率 |
| FP64 张量 | 不适用 | **11.6–12.9 TFLOPS** | 约为非张量速率的两倍 |
| TF32 张量 | 2.96–3.21 TFLOPS | **79–94 TFLOPS** | 15–28 倍；所有数据类型中离散度最大 |
| FP16 张量 | 6.52 TF/s | **158.7–190 TFLOPS** | 较高数字使用 fp16 累加 |
| BF16 张量 | 6.40 TF/s | **164.4–192.7 TFLOPS** | 上限为 2048 × 70 × 1410 MHz = 202.1 TFLOPS |
| FP16 标量（非张量） | ~42–50 TFLOPS | 不变 | **从未被限速**，即使在锁定卡上。GA100 以 FP32 速率的 4 倍运行 16 位 hfma |
| INT32 | ~12.5 TIOPS | 不变 | 约为 A100 的 20 TIOPS 的 62.5% |
| INT8，张量 MMA 微基准 | 1.60 TOPS | 335.0–335.6 TOPS | 直接 `mma.s8s8s32` |
| INT8，库 / 服务路径 | 1.63 TOP/s | **44.1 TOPS，仍然受限** | 比 FP16 *慢*约 3.7 倍，而 A100 快约 2 倍 |
| INT4 张量 MMA | 11.55 TOP/s | 320.2 TOPS | |
| INT1 | 46.16 TOP/s | ~1039 TOP/s | 超过每秒 1 PetaOP |
| FP8 / FP6 / FP4 | 不适用 | **硬件不支持** | 对 `sm_80` 属预期；MMA 扫描将每种都枚举为不支持 |

INT8 结果的实际含义值得直说：做推理请用 W4A16（AWQ 或 GPTQ，INT4 权重配 BF16 激活），完全避开 W8A8；KV cache 必须是 BF16，因为 `sm_80` 不支持 FP8 KV。见[大模型推理](../operations/llm-inference.md)和[性能](../operations/performance.md)。

> [!NOTE]
> **`deviceQuery` 的 8960 核心与 25.27 TFLOPS 是错的**
>
> `deviceQuery` 打印 `Total SPs: 8960 (70 MPs x 128 SPs/MP)` 和 25267.20 GFlops。差异恰好是 2 倍，与该工具套用计算能力 8.6 的每 SM 128 条 FP32 通道、而非 GA100 的 64 条一致。算术与每一项实测结果都支持 4480 核心与约 12.6 TFLOPS。

## PCIe

两个限制相互独立，绝不能混为一谈。

| 量 | 原厂，未解锁 | 使用解锁器 | 加装电容改造后 |
|---|---|---|---|
| 链路速率 | 第 1 代，2.5 GT/s | **第 2 代，5 GT/s** | 改造不改变此项 |
| 训练出的链路宽度 | x4（物理连接 x16） | x4 | **x16**（焊接不完整则为 x8） |
| `LnkCap` | `0x00456101` | `0x00456102` | 不适用 |
| `LnkCap2` | `0x00000002`（仅 2.5 GT/s） | `0x00000006`（2.5 与 5.0） | 不适用 |
| `LnkCtl2` 目标 | 不适用 | `0x0002` | 不适用 |
| `LnkSta` | `0x1041` | `0x1042` | 不适用 |
| `nvidia-smi` 当前 / 最大 / 宽度 | `1, 1, 4` | `2, 2, 4` | 宽度随焊接结果 |
| 去加重 | −6 dB | −3.5 dB | 不适用 |

**实测主机带宽：**

| 配置 | 带宽 | 置信度 |
|---|---|---|
| 第 1 代 x4（原厂） | ~0.80–0.85 GB/s | 高 |
| 第 2 代 x4 | 1.68–1.71 GB/s | 中；一份存档的 OpenCL-Benchmark 截图，一张未改造卡 |
| 第 1 代 x16（仅电容改造） | 2.88 GB/s 平稳、零错误 | 中；标称约 4 GB/s，差距归因于 PCIe 1.1 信令开销 |
| 第 2 代 x16 | 6.63–6.67 GB/s | **中：一台机器、一天（2026-07-26）、一次抓取。** Gen2 x16 的稳定性尚未确立 |

**宽度为什么是 x4：** 16 条通道中的 12 条（通道 4–15）出厂时省略了交流耦合电容，每个差分对 2 颗，共 24 颗器件，位于 `C1100`–`C1350` 编号区。规格是 **0402、220 nF（0.22 µF）、X7R、16 V 或更高**，来源为 NVIDIA A100 GA100-883 参考原理图 P1001-B02 第 3 页（"IO: PCIe CONNECTOR"）；确认可用的器件是 Samsung `CL05B224KO5NNNC`。（介质是 X7R。"XR7" 是常见笔误。）24 颗中只补 12 颗会得到 x8，因为 PCIe 宽度协商会回退到下一个合法宽度；改造后得到 x8 意味着焊接不完整或桥接，而不是独立的硬件上限。通道熔丝干净，所以宽度没有任何可编程之处。见[物理改造](../operations/physical-mods.md)。

**速率为什么是第 1 代：** 两个熔丝影子在 170HX 两个 SKU 上都读为熔断，而在探测过的其他 12 块 Ampere 部件上读为未熔断：`FUSE_PCIE_GEN23_DIS`（`0x0082057c`）= `0x00000001`，`FUSE_PCIE_GEN3_DIS`（`0x00820580`）= `0x00000001`。`FUSE_PCIE_MAGIC_D`（`0x00820520`）读为 `0x16680000`，第 25 位（`GEN4_SPEED_DISABLED`）置位，而 DRIVE GA100 参考部件读 `0x00200000`。值得注意的是，Gen2 解锁**在 `OPT_GEN23` 从未被清除的情况下依然有效**：对它的每次写入尝试都在硅片上失败，真正的杠杆其实是 CYA_0 / LINK_CONFIG_0 / XP3G / PRIV_MISC_1 这些覆盖寄存器。Gen3 和 Gen4 仍未实现：Gen3 的*通告*已能工作，但 `LnkSta` 从未离开 2.5 GT/s。见[PCIe 子系统](pcie-subsystem.md)、[Gen2](../unlock/pcie-gen2.md) 和 [Gen3/Gen4](../frontier/pcie-gen3-gen4.md)。

> [!WARNING]
> **实验性质：Gen2 不在正式发布的产品中**
>
> 正式发布的 `master` 只包含补丁 `0001` 到 `0006`，`constants.yaml` 里没有 `pcie:` 块，"What Gets Unlocked" 表格只有三行、没有 PCIe 条目。`0007-pcie-gen2.patch` 存在于分支 `debug-gen2`、`Gen2`、`far` 和 `deced`；`0008-pcie-gen2-probe-retrain.patch` 存在于 `Gen2`、`far` 和 `deced`。没有一条被合并。Gen2 在现场也不是确定性的，不支持虚拟机直通，在 Thunderbolt 3 扩展坞上完全失败（Oculink 可以，因为它本质上是直连转接）。

## NVLink、P2P 与其他缺失功能

| 功能 | 状态 | 原因 |
|---|---|---|
| NVLink | **熔断禁用** | `FUSE_NVLINK_DIS` `0x00820684` = `0x00000007`，`STATUS_OPT_NVLINK` `0x00820DB8` = `0x00000007`，与 Drive A100 部件一致。仅此一条就关死了门。板卡侧 NVLink 器件是否焊装**尚无定论**：两边都有直接证据；见[NVLink 硬件](nvlink-hardware.md)。`0x00823800`–`0x0082382C` 块中没有任何 NVLink 寄存器，任何分支中都没有 NVLink 代码 |
| P2P（对等直连） | 此卡缺失 | 从未演示成功；未判定是被熔断还是被驱动门控 |
| ECC | 熔断关闭 | `FBPA_ECC_CTRL`（`0x009a0470`）= 0，`MASTER_EN` 只读；无遥测；名为 `ecc` 的分支里根本没有 ECC 代码 |
| NVENC | 不可用 | 是熔断关闭还是熔丝门控未知；没有报告过可用的 NVENC 会话 |
| MIG | **能启用，但无法分区** | `0x00820840` 的第 0 位可将其打开且报告为持久，但只暴露一个 profile（`1g.64gb`，63.00 GiB，70 SM，P2P No），所以 GPU 实际上无法细分；`-cgi 9,3g.20gb -C` 返回 `Invalid Argument`。不在正式发布树中 |
| 可调整大小 BAR | **通告了但无实际作用** | 能力出现在 `[bb0 v1]`；每个 BAR 只通告一个支持的大小，BAR1 无论报告多少帧缓冲都停在 64 MiB。"ReBAR 需要 Gen3" 的反对意见已被驳斥。未在 Gen2 训练成功的卡上测试 |

## 功耗与电气

| 量 | 值 |
|---|---|
| TDP / 默认功耗上限 | **250 W**（原厂 VBIOS：默认 = 最大） |
| 功耗上限范围，原厂 VBIOS | 最低 100 W 到最高 250 W。`nvidia-smi -pl` 可用；只是原厂之上没有任何余量 |
| 使用 300 W OC VBIOS 的功耗上限 | 最高 300 W；一次 30 分钟的 `gpu_burn` 记录到 `POW 278 / 300 W`。适用于 **8 GB** SKU；本语料库中没人验证过它在 10 GB 卡上与解锁组合使用 |
| 插槽供电上限（`DevCap`） | **75 W**；超出部分全部来自辅助供电接口 |
| 外部接口 | **一个 8-pin EPS（CPU 风格）** 插座，内带两路 12 V 供电轨，`12V_EXT1` 和 `12V_EXT2`。额定 300 W。卡随附一个双 8-pin PCIe 转 8-pin EPS 的 Y 型转接线 |
| 空闲功耗 | 27–46 W，强烈依赖温度和驻留状态。常驻 CUDA context 会把它从约 33 W 推到约 45 W |
| 性能状态 | **只有 P0。** `nvidia-pstated` 返回 `NVAPI_ERROR`；双 P 状态的分支没有任何变化 |
| 供电轨 | `3V3_PEX`（经 LDO 降至 1.8 V）、`12V_PEX`（经 MP1475 降至 5 V，经 MP2988 降至 1.35 V 与 PEXVDD，经第二颗 MP1475 降至 HBMVPP 2.5 V）、`12V_EXT1`/`12V_EXT2`（经 MP2988 多相输出 NVVDD 1.0 V 核心与 HBMVDD） |
| VRM 布局 | **相对 A100 缺件。** 每侧缺三颗功率 MOSFET 和电感，而 A100 40 GB 每侧一颗、A100 80 GB 一颗不差；另一组对比把它定为约 20 相中的约 6 相。8 GB 的 64 GB 解锁据报告无需任何 VRM 改动 |

> [!CAUTION]
> **8-pin 插座是 EPS，不是 PCIe**
>
> 8-pin PCIe 电源线的防呆键位与卡上的 EPS 插座不同，只能硬塞进去，而且两种接口的部分引脚上 12 V 与地线是互换的。硬塞进去**会损坏卡**。请使用随附的转接线：一条腿提供 150 W 预算，两条腿 300 W。
> 模组电源线也是各品牌专用的，模组侧没有统一的引脚定义；跨品牌混用可能毁掉硬件。

按工作负载实测的功耗远低于标称值，这是这颗部件的特性而非故障：常规 FP32 烤机只能到约 60 W，张量 `gpu_burn` 约 75 W，而整数与内存密集负载可到 160 W 以上，持续真实负载落在 200–280 W。**在这张卡上，绝不要用 FP32 烤机来验证稳定性或散热。** 把功耗上限从 250 W 提到 300 W，在核心与显存都低于 65 C 时实测 BF16 **+2.8%**。完整细节见[供电](power-delivery.md)和[功耗与电源](../operations/power-and-psu.md)。

## 外形、散热与热限制

| 属性 | 值 |
|---|---|
| 外形 | 全长双槽 PCIe 扩展卡 |
| 厚度 | ~40 mm / 1.57 in（双槽）；卡体与 PCIe 金手指边缘相距约 5–6 mm |
| PCB | 与 A100 40 GiB 板卡几乎（若非完全）一致。A100 水冷头和 A100 导流罩物理上都能装上 |
| 散热器 | **全被动**：裸散热片无风扇，设计上靠服务器机箱高转速风扇的强制气流散热。每次抓取的 `nvidia-smi` 都报告 `Fan Speed : N/A` |
| 公布的 CFM / 静压 / dBA / 鳍片间距 | **不存在。** 任何风量数字都必须来自社区实测 |
| GPU 关机温度 | 98 C |
| GPU 降速温度 | 95 C |
| GPU 最高工作温度 | 85 C |
| 显存最高工作温度 | 95 C |
| 实际降频起始 | ~80 C（一位测试者的遥测；社区设计目标定在 70 C 核心 / 75–76 C 显存热点） |

> [!CAUTION]
> **GA100 存在漏电驱动的热失控**
>
> 结温升高会提高 CMOS 漏电，漏电提高功耗，功耗提高温度。在一张装了水冷头但没有冷却液干跑的卡上亲眼见过：空闲功耗在 80 C 时从 **40 W 升到 60 W 且仍在爬升**。如果散热彻底失效，这颗部件不会停在降频点上，而是越过它继续爬。如果你没有冷却液干跑这张卡，五分钟内必须断电。有实测结果的散热方案对比见[散热](../operations/cooling.md)。

## 对照锚点

| 部件 | SM / 核心 | 显存 | 总线 | 备注 |
|---|---|---|---|---|
| CMP 170HX 8 GB，解锁 | 70 / 4480 | 64 GB HBM2e | 4096 位 | 本卡 |
| CMP 170HX 10 GB，解锁 | 70 / 4480 | 40 GB HBM2 | 5120 位 | 同一颗硅片，不同的筛选结果 |
| A100 PCIe 40 GB | 108 / 6912 | 40 GB | 5120 位 | 原厂 CFG1 `0x02669000` |
| A100 PCIe 80 GB | 108 / 6912 | 80 GB | 5120 位 | 原厂 CFG1 `0x02779000`，LMR `0x0000028b` |
| A100 32 GB Drive（PG199） | 96 | 32 GB | 4096 位 | 九个速度选择熔丝全部读 0；与 170HX 一样 NVLink 被废 |
| CMP 90HX | GA102，GDDR6X | 不适用 | 不适用 | 完全不同的晶片；没有隐藏显存，没有 NVLink 金手指 |

解锁卡相对 A100 的定位，从未用两块部件上的匹配基准测试定案。流传的估算集中在 70–75%，与 70/108 的 SM 比大致吻合，两个方向都有离群值。按规格看，解锁后的 64 GB 卡在带宽、容量与 BF16/FP16 吞吐上与 AMD Instinct MI210 相当，互连是 AMD 明显占优的地方。
