# 开放问题登记册

**本页涵盖：** CMP 170HX 上的每一个未解决问题，从全部 24 份已裁决领域文档中聚合、去重，并按可处理性而不是重要性排序。每个条目包括：想要什么、尝试过什么、为什么失败、什么证据能定案，以及最有希望的下一步。

最有用的一件事是：**开放清单的很大一部分很便宜**。Tier 0 中有六项完全不需要硬件，只需要一个头文件、一个哈希或一次 `--dry-run`。Tier 1 中另有十几项需要一张卡、一次重启和一份发布的日志。真正难的问题（NVLink、ECC、Gen3）难在有已识别的原因，而这些原因下面都有说明，而不是含糊带过。80 GB 曾经在那个组里，现在不在了：折叠已被解释并消失，剩下的更窄（见条目 1.1）。

在存档期间关闭的条目被保留在原位，标记为已关闭并记录结果，而不是删除。除非明确说明，下面没有仍然开放的内容。

要看能力状态而不是开放问题，参见[状态板](status-board.md)。

## 条目如何分级

| 层级 | 关闭成本 |
|---|---|
| **Tier 0** | 无硬件。一个文件、一个头文件、一个哈希、一次离线 dry-run 或一次代码改动。 |
| **Tier 1** | 一张卡、一次启动或一条命令。之后发布日志即可定案。 |
| **Tier 2** | 一张卡加一次重建、受控 A/B 或插桩运行。 |
| **Tier 3** | 新能力：设备、没人有的硬件，或没人构建过的技术。 |
| **Tier 4** | 测量争议。不是未知，而是从未在单一方法论下测量过。 |
| **无法回答** | 记录和代码中的任何东西都无法定案。 |

## Tier 0：无需碰卡即可定案

### 0.1 LMR 量值字段宽度

**想要：** GA100 上 `NV_PFB_PRI_MMU_LOCAL_MEMORY_RANGE` 中 `LOWER_MAG` 的宽度：`[9:4]` 的 6 位还是 `[10:4]` 的 7 位。
**尝试过：** 只有算术。在 6 位字段下，规则 `size_MiB = MAG[9:4] << SCALE[3:0]` 对实际使用中的全部五个值（`0x208`、`0x288`、`0x20B`、`0x28A`、`0x28B`）都是精确的，而 `0x50A` 解码为 16384 MiB，不是 81920 MiB。在 7 位字段下 `0x50A` 会是 `80 << 10` = 81920 MiB。
**为什么开放：** 没有人读过 `dev_fb.h`。
**定案证据：** 头文件定义。这是查阅，不是实验。
**为什么重要：** 它是 `0x28B` 对 `0x50A` 之争与干净答案之间剩下的最后一件事，而该之争直接喂给 80 GB 重试（条目 1.1）。

### 0.2 移植分支中七个未经验证的小版本能应用吗？

**想要：** 对 `clanker/driver-port` 分支 `driver/VERSION` 中列出的、没有任何 `constants.yaml` 条目背书的七个驱动版本，做模糊匹配确认或从白名单移除。
**尝试过：** 没有。风险是代码阅读发现的。
**下一步：** 下载每个 tarball 并对照匹配的大版本补丁目录运行 `patch -p1 --dry-run`。纯离线且机械。

### 0.3 `booter_load` 在驱动 535 到 610 之间真的不变吗？

**想要：** 确认一个被操作性使用的说法（"extract once"，提取一次），580 命名的二进制被喂给 610 时代的链。
**尝试过：** 断言过两次，从未展示。任何地方都没有跨版本哈希。
**定案证据：** 535.x、580.x 和 610.x 中 `g_bindata_kgspGetBinArchiveBooterLoadUcode_GA100.c` 的 `IMAGE_PROD` 条目解压后的 SHA-256。
相关且同样便宜：对同一 bindata 归档中的 `IMAGE_DBG` 和 `IMAGE_PROD` 做哈希，这能定案从调试派生的 ROP 链是否保证在生产硅片上工作。

### 0.4 修复 `0008` 重训练成功谓词

**想要：** 一条关于 Gen2 说真话的驱动日志。`LnkSta 0x1042` 是真正的 Gen2 链路，但 `0008` 把 `PCI_EXP_LNKSTA_DLLLA`（位 13）纳入成功测试，而该位永远无法置位，因为 GPU 的 `LnkCap` 位 20（DLL Link Active Reporting Capable）是 0。
**后果：** 补丁在可用链路上打印失败，这已经误导一项下游分析得出 `0008` "运行太晚"的结论。
**下一步：** 删除 DLLLA 项，或让它以 `PCI_EXP_LNKCAP_DLLLARC` 为条件，或改从上游桥而不是端点读 `LnkSta`。`0008-pcie-gen2-probe-retrain.patch` 中一行改动。

### 0.5 工具报告缺口

三个自包含、无需硬件即可编写的新增项：

- 把正式发布解锁实际操纵的五个 PLM 地址加进 `probe.sh`：FBPA PLM `0x009a0148`、WPR PLM `0x001fa7c4`、WPR_CFG PLM `0x001fa7cc`、WPR2 低/高 `0x001fa824` / `0x001fa828`，以及 MMU LMR `0x00100ce0`。现有的 120 寄存器目录早于解锁，一个都不覆盖。
- 给 `verify.sh` 增加 PCIe 检查。它在任何分支上都不检查链路速率，**包括 Gen2 谱系**，所以那个 README 声称 Gen2 "Working" 的分支发布的验证器看不到 Gen2。
- 固定或校验 `open-gpu-kernel-modules` tarball。`build.sh` 用 `curl -L --fail` 获取它并缓存，树中任何地方都没有验证。

### 0.6 Gen2 和多卡的合入阻塞器

**想要：** 默认安装中的 Gen2 和多卡支持。
**树中可见的阻塞器：** `0007` 是一个大型调试插桩 hunk，全程以 `LEVEL_ERROR` 记录；`tools/retrain.sh` 在当前 Gen2 谱系上是死代码（`Gen2`、`far` 和 `deced` 都在安装时 `rm -f` 它，只有更早的 `debug-gen2` 安装过它；其硬编码 BDF 只在 `deced` 上被修复）；`constants.yaml` 漏掉机制依赖的五个寄存器。
**下一步：** `multiple-cards` 安装器改动（`b1cb6d8`）是自包含的，可以独立于 Gen2 PCIe 补丁单独落地。master 的补丁 `0001` 已经把两种几何烤进去了，所以 `mixed` profile 无需任何驱动改动即可工作。

## Tier 1：一张卡，一次启动

### 1.1 折叠消失后，什么仍然限制 80 GB

**在无驱动路径上大体已回答；驱动内构建仍未用它重建过。**
**原本开放的：** `80` 分支在恰好 40 GiB 处的折叠是来自不自洽 LMR 还是 LTC 解码。按编译状态，分支编程 CFG1 `0x02779000`（层 `0x77`，每 FBPA 4096 MiB，20 个 FBPA 共 81920 MiB）对照 LMR `0x0000028A`（40960 MiB）和 `fb_length 0x1400000000`（80 GiB）。三层、三个不同答案，折叠边界与 LMR 完全吻合。

**在无驱动路径上已回答，2026-07-25。** 一次把 LMR `0x028b` 与 CFG1 `0x02779000` 和 L2 解码 `0x10000300` 组合的触发起来后得到 **79.3 GiB 总计、79.0 GiB 空闲**和一个**77 GiB** 缓冲区，它*没有*折叠：偏移扫描读到了旧的 40 GiB 碰撞点之后的真实带宽，运行被频道内总结为"80GB seems to be verified in tests"（80GB 似乎在测试中得到验证）。随后 2026-07-27 在出厂启动时序下有一次 72 GiB 无折叠运行。所以自洽 LMR 假设得到支持，LTC 解码不是绝对墙。

**仍然开放的**比该条目最初的框架更窄：

- 40 GiB 以上的带宽约为峰值 79 %，而不是低偏移处看到的约 98 %。
- 每次触发在 Xid 154 之前大约只有一个 CUDA context 存活。
- 没有人从编译驱动复现过任何这一点。在 `driver/patches/0001-sec2-postbl-plm-ss-cfg.patch` 中设置 `lmrValue = 0x0000028BU` **并且**在 `driver/build.sh` 中设置 `LMR="0x0000028B"`（不只是构建从不读取的 `constants.yaml`）仍未编译、未启动。

参见[80 GB 问题](80gb.md)。

### 1.2 `RMPcieLinkSpeed=0x1` 还是 `0x2`？

**想要：** Gen2 的正确 modprobe 行。
**状态：** 两种拼写都随分支发布。`debug-gen2/install.sh:191` 和 `Gen2/install.sh:280` 写 `NVreg_RegistryDwords="RmForceEnableGen2=1;RMPcieLinkSpeed=0x1"`；`far/install.sh:280` 和 `deced/install.sh:280` 写 `0x2`，由提交 `8854d3e` "Remove clamp link to Gen1" 引入。两种读法内部自洽，取决于该键的意思是"钳到第 N 代"还是"启用至第 N 代"，而 README 声称 Gen2 工作的分支发布的是 `0x1`。
**下一步：** 同一张卡、同一内核启动三次（无键、`0x1`、`0x2`），每次都发布 `LnkSta`。便宜且决定性。

### 1.3 595 / 590 / 580 驱动移植能启动吗？

**尝试过：** 该分支于 2026-07-21 发布并明确征召测试者；没有任何回音。
**为什么停滞：** 它需要一个愿意降级一块可用卡的负责人。
**定案证据：** 每个分支一位测试者报告 `dmesg | grep SEC2_DEBUG` 和 `POST-BooterLoad verify` 行。那一行就能回答。

### 1.4 `610.43.02` 还是 `610.43.03` 更可靠？

在频道内直接问过，从未回答。两个版本上都有成功的解锁；`610.43.03` 只是 `driver/VERSION` 中的第一个。
**下一步：** 从现有安装基数收集 `driver_version` 元数据文件和 SEC2 PLM 打开成功率并比较。

### 1.5 MIG 在解锁卡上可用吗？

MIG 相关寄存器已填充且可读（`FBHUB_MEM_PART_BOT 0x00100b88`、`MID 0x00100b8c`、`BOUNDARY_CFG0 0x00100b90`、`SYSMEM_HSHUB_CONNECTION_CFG 0x00100b98`），熔丝调查显示 170HX 是*没有*编程 MIG 分区，而不是 MIG 被熔断关闭。另外，通过 `0x820840` 位 0 的 MIG 使能已被演示并报告为持久。
**已报告过一次：** 在解锁卡上 `nvidia-smi mig -lgip` 恰好列出一个 profile `MIG 1g.64gb`（63.00 GiB，70 SMs），`nvidia-smi mig -cgi 0` 能创建它，而标准 A100 profile（`-cgi 9,3g.20gb -C`）返回 `Invalid Argument`。所以 MIG 能打开，但不能按出厂状态给卡分区。
**下一步：** 在第二张卡上重复，并找到 RM 在何处构建 GA100 GPU 实例 profile 列表，以便添加更多 profile。如果使能成立，开 pull request；维护者提出过愿意合入一个。

### 1.6 P2P 在纯 170HX 主机上做任何事吗？

**尝试过：** 树外 P2P 补丁可以构建进 cmpunlocker 树。一位测试者报告对纯 170HX 无效果。同一天的正面报告来自一台还带两张 RTX 3090 的机器，这正是负面报告所说的唯一能工作的混合型号场景。
**定案证据：** 纯 170HX 多卡主机上带和不带叠层补丁的 `p2pBandwidthLatencyTest` 连通性矩阵。测试便宜，结果无歧义。
**注意事项：** 所有参与者都同意 P2P 受带宽限制，在 Gen1 x4 下收益很小。

### 1.7 Gen2 x16 的长期稳定性

复现已定案：两台机器、五张卡、两个板卡版本、`lspci` 抓取，90 分钟四卡连续负载下零 AER 错误。参见[现场报告](../operations/physical-mods.md#field-report-four-cards-at-gen2-x16)。

缺少的是时长。没有人发布过数天持续负载后的错误计数器，这是边缘交流耦合网络显露自身的唯一剩余方式。
**下一步：** 任何运行电容改造卡 Gen2 x16 的人在一周正常运行时间后发布 `cat /sys/bus/pci/devices/<bdf>/aer_dev_correctable`，同时附 `lspci -d 10de:20c2 -vv | grep -E 'LnkCap:|LnkSta:'`。

### 1.8 `0x008200FC` 读出什么，可写吗？

三个不相容的观察：`0x000003FF`，写入失败且直接主机 `writel` 也被封顶在 `0x3FF`（2026-07-09）；整个 Ampere 阵容上 `0xffffffff`（2026-07-16）；以及九个 PLM 分支工具的 `PLM[8] OPT_PLM(0x8200fc) attempt=0 status=0xffff reg=0xffffffff`，报告为成功（2026-07-23/24）。同一个寄存器有两个名字：分支代码中的 `OPT_PLM`，净室工具中的 `FUSE_SS_PLM`。
**下一步：** 在任何解锁之前在冷启动卡上读 `0x008200FC`，然后在九个 PLM 打开中每个之后读，同一块单元。

### 1.9 RAMCFG 重新 strap 结果（已关闭）

> [!TIP]
> **2026-07-25 关闭：确认为负面，正如预测**
>
> 一张 10 GB 卡上的 RAMCFG 电阻被移到 `HHLLH`，即 8 GB 出厂 strap 模式。卡启动了，`probe.sh` 读到 `FBPA_CFG1_BROADCAST` 在 `0x009a0204` 处仍然等于 **`0x02449000`**，即 10 GB 值。频道内总结为"the resistor change had no effect"（电阻改动没有效果）。这正是**代码预测的结果**：驱动以 PCI 设备 ID 为几何键，而不是 strap。值得注意卡启动时 L2 解码已经在 `0x10000300`。物理 RAMCFG 重新 strap 对容量是死路。

### 1.10 逐出测试折叠在正式发布几何上复现吗？

显示 8 GiB 边界以上均匀 79 % 峰值平台的偏移扫描只在被放弃的 80 GB 配置上跑过。正式发布 master 把 BAR0/PRAMIN 对两个设备 ID 都钳到恰好 8 GiB，这有提示意义，但 PRAMIN 是 CPU 窗口而扫描是设备侧 memset。
**下一步：** 在正式发布的 8 GB 到 64 GB 卡上重复相同偏移和块大小扫描。如果台阶在 8 GiB 处重现，那是几何效应；如果不是，它特定于过度触发。

### 1.11 uBatch 悬崖

一块 84 个 SM 中 68 个的 CMP 100-210 因一个 `n_ubatch` 标志调在 SM 数之下一点而获得 **3.04 倍** prompt 处理增益。70 SM 170HX 上没有运行过任何等价物。
**下一步：** 在计算解锁卡上用 `n_ubatch` 从 48 扫到 80 跑 `llama-bench`。语料中最便宜的未测试性能线索。

### 1.12 记录限流起始点

四个温度数字并存：80 C 观察到限流、社区报告 85 C、驱动报告 `GPU Max Operating Temp 85 C` / `GPU Slowdown Temp 95 C`，以及一个冷却失败时 100 C 以上限流的说法。这些可能在不同层上都为真，但没有人捕获过限流日志。
**下一步：** 记录 `nvidia-smi --query-gpu=temperature.gpu,clocks.sm,clocks_throttle_reasons.active`，从 75 到 95 C。

## Tier 2：一张卡加重建或受控 A/B

### 2.1 10 GB 卡上的中间容量

**想要：** 稳定的 40 GB 与坏掉的 80 GB 之间的某个东西。在频道内直接问过，回答是"I don't believe its been tried"（我不相信有人试过）。
**为什么明显路线不工作：** 每通道层是粗粒度的（`0x44`/`0x66`/`0x77` = 512 / 2048 / 4096 MiB），所以仅靠层无法到达中间大小。
**下一步：** 把 CFG1 固定在层 `0x77`，通过 `targetFbBytes` 把驱动可见大小钳到 48、56 或 64 GB，然后在每一档运行全写后全读的折叠测试。每档一次常量改动和一次重启。它也是坏堆栈捡料理论的决定性证伪器。

### 2.2 广播对比每-FBPA CFG1 写入

正式发布驱动只把 CFG1 写到广播别名 `0x009a0204`。唯一报告的无幻影回读来自逐个写入所有 FBPA。没有人插桩过 FBPA 广播是否是真正的 PRI 特权环硬件机制。
**下一步：** 在 FB 几何 PLM 打开且无 devinit 的情况下，只写广播并读取 `0x00900204 + n*0x4000` 处全部 24 个每-FBPA CFG1 镜像以及 `0x0090020C + n*0x4000` 处 `CSTATUS_RAMAMOUNT`，然后用每-FBPA 写入重复并比较。

### 2.3 哪个 PLM 实际门控 LMR？

**想要：** 守护 `0x00100CE0` 的特权掩码，这样 LMR 可以不经过高安全触发从主机写入。一张候选 FBHUB 表被发布，然后被其自己的作者否认。
**没人走的捷径：** 正式发布驱动在打开恰好四个 PLM 后*确实*成功从主机写入 LMR，所以**那四个中已经有一个门控它**。对正式发布 `plmTable[]` 做四路消融即可识别是哪个。

### 2.4 CFG1 前导数字的含义（已关闭）

> [!TIP]
> **2026-07-27 关闭：位 29 把层减半**
>
> 实验已运行。在 20 个活跃 FBPA 的卡上把 CFG1 `0x22779000` 写在 `0x02669000` 的位置，**把 `0x77` 层减半**到每 FBPA 2048 MiB，得到 20 x 2048 = 40960 MiB（40 GB）。每-FBPA `CSTATUS` 保持 `0x0800`，LMR 在改动期间保持 `0x0000028a`，所以容量移动完全来自 CFG1。
>
> 第二个效应出现在时序块中：`HBM_CFG0` 在 `0x9a038c` 从 `0xa7` 变到 `0xa6`，即双秩位，6 个时序寄存器中的 7 个移到了它们的 strap-5 值。所以前导数字不是纯容量除法器；它重新选择秩配置并拖带时序 strap。携带相同奇数 `2` 的候选 VBIOS strap 条目 `00 90 77 22` 与该读法一致。
>
> 写入可能需要 ROP 路径；那部分被报告为不完全确定。

### 2.5 通过尝试 Gen2 熔丝的同一张表实现 Gen3

**值得一次启动，但先验低。** 23 项 `xp3gTable` 确实包含 `FUSE_PCIE_GEN23_DIS 0x0082057c`，但该写入被观察到在硅片上*失败*（`status=0xffff rd=0x00000001`，随后是 `SEC2_DEBUG: PCIe xp3g booter FAILED to set OPT_GEN23`），所以这个熔丝组上没有可扩展到 `0x00820580` 的已验证写入路径。Gen2 是通过 `CYA_0` / `LINK_CONFIG_0` / XP3G / `PRIV_MISC_1` 覆盖加一次根端口重训练达到的，而不是通过那次熔丝写入。`FUSE_PCIE_GEN3_DIS 0x00820580` 读出 `0x00000001`，**从未被任何人写入**，也没有代码路径请求过高于 2 的目标链路速率。
**下一步：** 把 `0x00820580 = 0` 加进同一张表，然后请求 TLS = 3 并读 `LnkCap2`。如果它达到 `0x0000000E`，连续性论证成立；如果保持 `0x00000006`，Gen3 熔丝在下游被独立强制——这目前是更有依据的读法（把 PHY 速率强制到 Gen3 能力值 `0x00340036` 后链路仍停在 Gen1）。

### 2.6 第二个功能覆盖组

`0x823830` 到 `0x82383C` 从 PL0 读出 `0xbadf5040`，在 HS 读取时返回真实值。没有手动 PLM 覆盖该组，也从未执行过 HS 写后读回。相关且同样未测试：`0x823b00` 作为 `0x823824` 处行重映射器的候选 PLM。

### 2.7 隔离 SS1

"SS1 削弱 64 位计算"的说法是一种未测试的信念，恰好挨着一个正确的 FP64 测量。SS1 自 2026-07-14 起一直在配方中，总是与 SS0 一起发布。
**下一步：** 一个移除 `0x00823820` 写入的一行构建，然后重跑 OpenCL FP64 测试。如果信念是错的，预期 6.421 TFLOP/s；如果是对的，接近 0.19。

### 2.8 为什么 INT8/IMMA 仍被门控

解锁卡以 44.1 TOPS 做 INT8，比其 FP16 慢约 3.7 倍，而 A100 的 INT8 约为 FP16 的 2 倍。IMLA 熔丝读出与 FMA 熔丝相同的 `0x5`，SS0 同样设置它们的覆盖 nibble，但实测速率并不跟随。另外，裸 MMA 路径测得 335 TOPS，而库路径（torch、cuBLAS、OpenCL）停在 43-48。
**下一步：** 一次显式 `CUBLAS_COMPUTE_32I` INT8 输入 GEMM 对照裸 MMA 数字，加上 `0x00823818` 转储和按数据类型的微基准，以检查*有效* IMLA 字段是否真的是零。

### 2.9 残留计算门

- `SM_ISSUE_RATE_MODIFIER 0x00504204` 在完全解锁卡上读出 `0x00000005`，解锁不触碰它。在解锁卡上把它写成 0 并重跑基准套件从未做过，尽管该寄存器在 PL3 下主机可写且写原语存在。
- `SKED_UNK54 0x00407054` 是 GSP 固件中被引用最多的未文档化 SKED 寄存器（13 处引用），也是 13 卡群组中唯一在 170HX 上非零、在 A100 和 RTX 3090 上都为零的寄存器。没有人对它做过写测试。驱动在 GR 初始化期间清除它，所以它只能在驱动加载前观察到。
- `FEATURE_READOUT_1 0x00823818` 没有已知字段布局。对出厂 `0x016DB6ED` 做朴素的九乘三比特解包不匹配熔丝。在解锁卡上扫 SS0 的单个 nibble 并观察哪些位移动，是一个直接的位映射实验。

### 2.10 训练状态对比"未训练显存"理论

`FBPA_TRAINING_STATUS 0x009a0974` 在每张卡上读出 `0x00000000`，**包括已经携带 64 GB CFG1 值的解锁卡**，然而 80 GB 不稳定性的主要解释是上层区域未训练且没有时序。没有人把 `TRAINING_STATUS` 与实际崩溃轨迹关联起来。
**下一步：** 在过供给层的崩溃前后立即读取它，并 diff 出厂启动与解锁启动之间的 `TIMING*_GEN` 影子。

### 2.11 80 GB 处的保持对比地址解码

为 >40 GB 失败提出了两种机制，它们预测不同的失败几何。保持失败会按时间和地址在整片上层区域散布错误；解码折叠会在 2 的幂边界产生精确别名。观察到的折叠坐在**恰好 40 GiB**，对保持问题来说精确得可疑，而加倍刷新成功落在全部 20 个活跃 FBPA 上却没有修复不稳定，同时付出约 40 % 带宽代价。
**下一步：** 在 80 GB 几何、出厂时序、单 context、刚冷启动的卡上运行全写后全读折叠测试，报告通过/失败和失败的地址分布。
**相关且未解释：** `cuda_memtest` 在重启后立即对全部 80 GB 通过一次，之后每次重试都失败。这种重启依赖是最具体的剩余线索。

### 2.12 可恢复的 FBP

有些卡显示 `FBP_DISABLE 0x852` 对照 `FBP_DEFECTIVE 0x840`，多了两个仅禁用位。频道内实际转储的那张 10 GB 卡 `DISABLE == DEFECTIVE == 0x840`，软件覆盖实验显示即使从 HS 有效掩码也不动。
**下一步：** 在掩码不同的卡（8 GB 级卡）上运行八寄存器读取，在禁用 GSP 的情况下尝试 CPU-RM 下重新启用，并检查对 `0x00820364` 的写入是否在 FLR 后存活。
**注意事项：** "禁用但非缺陷"的硅片是否可恢复本身尚未证实。

### 2.13 IOMMU 与 Gen2 可靠性故事

存在直接矛盾的报告。多位测试者在一处 grub 改动后从"still PCIe 1"走向成功，分支安装器现在自动设置 IOMMU；一份独立设置脚本把 `iommu=pt` / VT-d 列为"已测试并确认不必要"，其确认的主机完全没有做 grub 改动。
**定案证据：** 在相同软件上的 {IOMMU 关、开、pt} × {Intel、AMD} × {用户态锤、驱动内 `0008`} 矩阵。看似合理但未演示的调和：`iomem=relaxed` 只对用户态 `mmap` 基础的重训练重要，IOMMU 模式只在某些芯片组上重要。

### 2.14 Gen2 的重启持久性

`nvidia-smi` 在 `install.sh` 后立即报告 `2, 2`，在某些系统上重启后报告 `1, 1`，可复现，重跑 `install.sh` 每次都能恢复。
**工作假设：** 持久性取决于*已补丁*模块是否真的在启动时加载，而不是只被安装器热补丁。
**下一步：** 在失败系统上，重启后检查 `modinfo` 和 `dmesg` 是否出现已补丁模块和 `SEC2_DEBUG: PCIe` 行，然后再怪罪重训练。

### 2.15 FLR 存活图有一条未撤回的异议

几何在 FLR 上恢复被报告为"每次都"实测（2026-07-12），同一位研究者第二天推翻，又被一份 FLR 回读表和一张存活图重新确立。裁决强烈倾向"FLR 恢复"，但推翻从未被正式撤回。
**下一步：** 在未加载驱动的情况下对 CFG1、LMR 和 CSTATUS 做一次干净的 FLR 回读，随卡 ID 一起发布。

## Tier 3：需要新能力、设备，或没人有的硬件

### 3.1 ECC

**想要：** 纠错，它会实质性地改变风险图景，并可能让边缘几何可用。
**尝试过：** 硬件上什么都没做。2026-07-20 被直接问过，回答是 "Not yet."（还没有。）
**阻塞机制：** `OPT_ECC_EN 0x00820228 = 0`，`FBPA_ECC_CTRL 0x009a0470` 的 `MASTER_EN` 只读。不知道 `MASTER_EN` 是熔丝门控还是 PLM 门控，而这两者暗示非常不同的上限。
**最便宜的第一个实验：** `FEAT_OVR_ECC` 家族（`0x0082380c`、`0x00823810`、`0x0082382c`）一旦 `0x00823804` 打开原则上就可写，而正式发布补丁已经这么做。测试在 DEVINIT 后写入它是否有任何效果。
**部分解决的前置条件：** HBM 堆栈是否带有任何 ECC 供给。对熔丝表的一次解读（从未对照数据手册核对）说 GA100 上的 ECC 是 HBM2 堆栈作为带内容量的一部分：A100 每-FBPA `CSTATUS_RAMAMOUNT` 读出 `0x07ff` / `0x0fff`，而消费级部件读出 `0x0800` / `0x1000`。如果相反它是厂商 QA 捡料属性，那这个问题没有意义。参见 [ECC](ecc.md)。

### 3.2 NVLink

**想要：** 真正的解锁。**截至 2026-07-20 的总结：** "Still unsolved, a bit harder as there's no fuse mask."（还没解决，因为没有熔丝掩码所以更难。）
**两条覆盖路径都已关闭：** `CTRL_OPT_NVLINK 0x008209B8` 惰性，因为 `FUSE_EN_SW_OVERRIDE = 0x0` 且 `FUSE_DIS_SW_OVR = 0x1`；FEAT_OVR 路线关闭，因为 `0x00823800`-`0x0082382C` 块完全没有 NVLink 寄存器。
**桌面上没有任何可着手之处。** 至少能产出数据的三件最便宜的事：

1. 在一块可牺牲卡上对 `0x008209B8` 和 `0x00820820` 做读-写-读探测，然后重读 `STATUS_OPT_NVLINK 0x00820DB8`。预期结果是写入被丢弃，状态保持 `0x00000007`。**那个负面值得记录**，因为语料目前甚至不能说它被尝试过。
2. 去罩 170HX 在 `R234`、`R236`、`R237`、`R238`、`R976`、`R1024`、`R1029`、`R1030` 位号周围的高分辨率照片，外加从 NVLink 边缘金手指到 BGA 球 `F1` 和 `G1` 的通断。这定案 PCB 区域是否装填了元件的长期争议，而后者决定熔丝绕过是否真的有用。注意 `R237` 在 A100 原理图本身中被标记为 **NP**，所以真品 A100 上至少一颗也被预期缺失。
3. 坐上真正的 A100 桥接器。记录中从来没有人同时拥有一张 170HX 和一个桥接器，所以连接器是否对齐都尚未确立。

中介层制造被讨论过（连接器采购、Megtron 层压板、非标准卡朝向），在条目 3 返回正面结果之前没有意义。

### 3.3 Gen4 与 DevInit 五字节编辑

PCIe Gen1 锁是 VBIOS MAC 范围**内部**跨 3 个 devinit 位置的 5 个字节，所以在不伪造 MAC 的情况下 ROM 路线关闭。该编辑单独在可重新签名的闪存下能否恢复 Gen4 从未被测试；"仅固件补丁不足"的结论是对熔丝值的推断，而不是尝试补丁的结果。另外，研究 Gen4 的人**没有 Gen4 能力的主机**，所以它在技术上被阻塞之前先被硬件访问阻塞。
已命名但未尝试的替代方案：伪造 TS1/TS2 Rate-ID 的线级 retimer 中介层（Astera Aries、TI DS160PR810 类），以及转移 GSP-RM 消费 `0x57c` / `0x580` 熔丝读取位置的 GSP 补丁（470.42.01 `gsp.bin` 中 `0x5D55834` 处的跳转表、580.105.08 `gsp_tu10x.bin` 中 `0x4DD9B00`）。

### 3.4 HBM 时序与 MRS 重放

**想要：** 过供给区域的正确时序，以及无需物理拆散热器重刷写就能改变显存 strap 的能力。
**为什么写 `TIMING*` 寄存器无效：** `CONFIG0.USE_TIMING_REGS`（`0x9A0290` 的位 31）是 **0**，所以控制器忽略原始值并使用内部生成的值。
**为什么 MRS 重放失败：** 已发表论文报告它*能驱动的每个 agent*（主机、非安全模式 SEC2、HS SEC2、PMU、非安全模式 GSP）都无法发出 die 会消费的模式寄存器设置命令。写入似乎按来源身份被丢弃。唯一可见地驱动 die 的 agent 是启动时运行自己代码的 FB Falcon。
**机械上可行，然后被阻塞：** 基线 MR1 `0x00100093`、MR2 `0x002000cf`、MR3 `0x003000ea`；推导出的 strap-7 MR1 `0x0010009b`、MR2 `0x00200029`、MR3 `0x003000ef`；重放回 strap 4 精确复现了启动值。驱动随后以 `RmInitAdapter failed! (0x62:0x40:2674)` 拒绝。
**频道内命名且从未尝试的下一步：** 补丁驱动以容忍改变后的状态，而不是试图让状态看起来未被触碰。
**这里一切的前置条件：** 从一张已知良好 64 GB 卡和一张 10 GB 卡转储 HBM 自报（IEEE 1500 块，`0x009a3cb4`..`0x009a3cc8`）、FBPA 训练结果寄存器和 MR 寄存器。

### 3.5 L2 / LTC 解码墙

一个托管显存原子内核越过 40 GB 分页，会通过 UVM 原子故障路径把 `0x17E2A0` 处的 L2 解码从 `0x70000300`（每通道 2 GB）翻到 `0x10000300`（每通道 4 GB）。工作负载是跨 46 GiB 的 2 MiB 步长原子操作，约 23,552 次原子操作，用时 0.3 s。解码在工作负载存活期间保持，context 拆除的瞬间恢复，触发故障毒化 context（CUDA 错误 719，然后 Xid 45，然后 Xid 154）。一个单字节驱动修改可以在没有工作负载的情况下把它固定在那里。
**为什么这不是答案：** 翻转它不能修复 >40 GB 问题，那是"downstream, unfortunately"（不幸地在更下游）。"下游"意味着什么从未被钉死，**那就是缺口**。
**下一步：** 为同样的惰性重新使能找到非故障触发，并表征下游实际阻塞什么。

### 3.6 恢复一个 csecret

三个索引映射到三个能力：**secret(6)** 解密 ECB 固件 blob（会产出 121.7 KB 明文固件加 Booter 代码）；**secret(2)** 伪造内容 MAC，会一次性打开 2 个 CFG1 字节和 5 个 PCIe devinit 字节，即整个 7 字节 VBIOS 限制；**secret(0)** 是启用带 `SKIP_VBIOS_SIG` 的 HULK 证书的调试绕过。
**没有 csecret 被恢复。** 三者都是需要电压毛刺硬件的差分故障分析目标。一个来自全 `0xFF` 已知明文预言机的即时离线密钥验证器已存在，所以 DFA 活动不需要闪存周期来验证。非常高的努力。

### 3.7 需要硬件编程器的 VBIOS 编辑

**2026-07-25 更新：`nvflash` 并非完全被阻塞。** 一个*打过补丁的* `nvflash`（omgvflash 风格）把完整的出厂 8 GB 镜像写到一张 10 GB 卡上然后刷回去，无泄漏、无编程器。仍有两件事失败：**strap 编辑过**的镜像在刷写期间触发主机侧镜像检查，外国镜像无法启动。两次刷写之间没有重启，所以把写入本身当作提示性而非确定性；参见 [vbios.md](../hardware/vbios.md)。

这*不*确立的是**未签名尾部**编辑是否能通过该镜像检查。没有人尝试过。所以带 SOIC 夹（和 1.8 V 适配器）的 CH341A、拆散热器和重新涂硅脂仍是下面三个编辑的假定路线，但现在更便宜的实验是先尝试用打过补丁的 `nvflash` 做尾部编辑：

- **`0x45E45` 处 250 W 到 300 W 的功耗上限。** 3 字节字段读出 `90 D0 03`，应变成 `E0 93 04`。它位于 `0x43A00`-`0x47700` 的 15,616 字节未签名 FwSec 尾部内，所以不可能破坏 MAC。自 2026-05-09 起记录为 OPEN 且未测试。
- **`0x47177` / `0x47179` 处的 `freqDelta` 和 M0205 训练表。** 在一切 MAC 范围之外。`freqDelta` 在 8 GB 镜像上是 ±1000，在 10 GB 镜像上是 0，所以把 ±1000 写进 10 GB 镜像并检查核心偏移是否出现，是一个干净的自然实验。
- **`0xFE504` 处的 HULK 证书注入。** 槽位是 1113 字节，出厂全零，且因为 170HX 的许可证区在 `0xFE000`，它落在 nvflash 写入的 1020 KB 窗口内。许可证区是否豁免 FwSecLic 检查从未被测试。Lapsus 泄漏中的三个生产证书（`HULK_9970`、`HULK_12231`、`HULK_12549`）带有 `STRICT_ID_MATCH=NO` 并针对 `FUSE_FEATURE_OVERRIDE 0x823800`，被描述为"ready to test as-is"（可直接测试）。**任何地方都没有报告测试结果。**

### 3.8 一个无驱动解锁，交接给原版已签名驱动

**想要：** 一个能在 Secure Boot 和 Windows 代码完整性下存活的解锁。
**为什么它一直失败：** 原版驱动的 booter 拒绝触发后的 SEC2 状态，出现两次加载的"互斥角"（`0x31` 互斥锁被持有、`0x62` WPR2 升起、`0x29` 来自 `0x1180f8`，因为 `mutexfree` 终止符把高 nibble 留在 `0xf`）。即使在 10 GB 且几何一致时也失败，证明被触发扰动的是 SEC2 交接状态，而不是几何或写入次数。**正式发布解锁器通过从已补丁驱动内部编排几何绕过了它。** 两个候选根修复仍在：保留 booter 成功路径，让 SEC2 启动其 RTOS 并自己设置 DONE；或恢复 AON `SECURE_SCRATCH` PLM 和特权状态——后者目前只有电源域重置能做到。

### 3.9 移植到其他硅片

- **CMP 90HX（GA102）。** 主机侧阶段 1 已完成，目标已知：`FEAT_OVR_PLM 0x823804 = 0xffffff8f`（通过 `FUSE_QUADRO_WR_SEC = 1` 自密封）、`FEAT_OVR_SM_SPD 0x82381c = 0x16334012`（目标 `0x88888888`）、`FUSE_EN_SW_OVERRIDE = 1`、`FUSE_FEAT_OVR_DIS = 0`。**阻塞器是 GA102 VBIOS 中 SEC2 HS Booter IMEM 已加密**，所以静态分析一无所获。一项分析得出结论 GA102 booter 没有溢出点；反提案是完全不用 GA10x booter，而是在 GA10x 部件上加载 **TU10x** booter，支持依据是 TU10x 和 GA10x 调试 booter 使用相同的 AES-128 秘密，以及一份 TU10x `booter_load` 在 90HX 上加载且 PLM 写入成功的报告（自我限定"1 positive test isn't enough"，一次正面测试不够）。只有计算值得解锁：90HX 物理携带 10 GB GDDR6X。
- **CMP 50HX（TU102）。** 完全是另一套显存访问控制寄存器："there is no single PLM there but there seem to be several other masks for the interesting registers"（那里没有单一 PLM，但似乎有几个其他掩码覆盖那些有趣的寄存器）。
- **PG199 / DRIVE A100（`10de:20bb`）。** 启动以 `Booter failed 0x54` 失败，发生在 `kflcnResetIntoRiscv 0x0` 之后，尽管 PLM 打开且 CFG1/LMR 写入落地。没有人知道 `0x54` 意味着什么，状态码 `0x31`/`0x47`/`0x15`/`0x29`/`0x88`/`0x96` 全部通过在 booter 反汇编中定位其写入位置被钉死，而反汇编已在手。名为 `PG199` 的分支**不含任何 PG199 支持**。

### 3.10 NVGI 固件前写入原语

SPI ROM 中的 NVGI 记录由 PBUS/XVE 从 ROM 初始化的序列器**在任何固件运行之前**执行，即在 FWSEC 升起 PLM 之前，而迄今对熔丝组尝试的一切都是锁定后的 HS 运行时。完全未测试。
**其提出者自己的注意事项：** NVGI 是单拷贝，没有 `+0x60000` 回退，所以一次坏写入在没有 1.8 V SPI 编程器的情况下不可恢复；它是"一个可能导致大问题的花哨脚枪"。
**下一步：** 在考虑任何写入之前，只读地追踪 ROM 转储中的记录格式。

### 3.11 缺失的 38 个 SM

**想要：** 从 70 SM 到接近 108。
**已尝试且失败：** `FUSE_CTRL_OPT_TPC_GPC` 写入（仅移除）、对 `OPT_GPC_DISABLE`、`STATUS_OPT_GPC`、`OPT_TPC_GPC2` 和 `DIS_SW_OVR` 的高安全写入（全部反弹），以及三种方式强制 `gpcMask`（`0x408970` 重新断言为 `0xdc`；`cuInit` 段错误）。
**频道内命名但未尝试的候选：** 经静态 floorsweeping-masks 查询（`0x2080122a` / `0x2080122b`）的 GSP-RPC/RM 控制路径、GR 影子写入，或把 ROP 移植到 PMU / GSP / FECS / GPCCS。
**冷静的背景：** 在 `OPT_GPC_DEFECTIVE = 0` 的卡上，被禁用的 GPC 物理上是好的，所以有东西可赢，但迄今找到的每条写入路径都被锁存。有一张卡被发现被 CTRL_OPT 扫到 56 SM 而不是熔丝底线 70，通过夺回 6 个 SM 达到 62；那是*罕见*案例，其他每张被调查的卡都已经在其熔丝底线。

## Tier 4：需要一次受控会话的测量争议

这些与其说是未知，不如说是从未在单一方法论下取过的数字。每一项都需要一位测试者、一张卡、一次会话，并说明工具、时钟和浮点计数约定。

> [!TIP]
> **已关闭：解锁后的 FP64 离散度**
>
> FP64 曾经以 11.48 到 12.91 对比 6.3 TFLOPS 的争议坐在这个表里。它已解决，而且从来不是计数错误。2026-07-15 一次 clpeak 转储在同一张卡的同一次运行中打印了两个数字：**FP64 非张量 6.31 TFLOPS**（`double : 6308.65`，正好是同次运行 `float : 12565.14` 的一半，即架构 1:2 比率）和 **FP64 张量 11.96 TFLOPS**（`wmma_fp64`，8x8x4 DMMA 路径）。高簇就是张量路径。参见 [compute-throttle.md](../unlock/compute-throttle.md)。

| 争议 | 离散度 | 什么能定案 |
|---|---|---|
| HBM 带宽 | 各来源 **1305.86 到 1600 GB/s**。理论峰值是 1555.2 GB/s（1215 MHz DDR × 5120 位） | 在同一个会话中用同一个工具跑一张 8 GB 到 64 GB 卡和一张 10 GB 到 40 GB 卡 |
| INT8 / INT4 | 44.1、50.5、276、约 280、约 300、320.2、335.6 TOPS 都被报告过。INT4 测出*低于* INT8，而 Ampere 应该约 2 倍 | 在记录了时钟和解锁状态的卡上，以固定形状各跑一次 INT8 和 INT4 CUTLASS GEMM，随内核一起发布 |
| TF32 | 七个工具间 79 到 94 TFLOPS。出厂卡上 TF32 是否被限流存在争议 | Torch GEMM、`gemm_probe.cu` 和 clpeak 在同一个会话中背靠背，加上一张由 `0x00823818 != 0` 确认锁定卡上的 TF32 运行 |
| L2 缓存 | `deviceQuery` 打印 32768 KB；规格数据库说 8 MB；一个微基准独立发现 32 MB | 发布一条指针追逐延迟曲线，显示工作集在哪里跌落 |
| 着色器数 | `deviceQuery` 打印 8960 SP 和 25.27 TFLOPS；算术偏向 4480 和 12.63 TFLOPS（工具套用了 cc 8.6 的每 SM 128 FP32 lane，而不是 GA100 的 64） | 已被算术有效定案；记录是因为没有来源在实验上解决它 |
| 显存时钟 | 304、364、432、864、1215、1458、1728 和 1890 MHz 都出现。不同工具使用不同时钟域和倍率，没有人说明转换 | 一张卡、一次会话：一起捕获 `nvidia-smi -q -d CLOCK`、mixbench 和带宽扫描，附 VBIOS 版本 |
| `clocks.max.sm = 1935 MHz` | 一个报告字段，不是运行时钟。每个持续测量都停在 1410 MHz（`-pl 300` 时 1470 MHz），VBIOS 表最大是 1695 MHz | 在第二张卡上复查一次 |
| 单卡 27B decode | vLLM 上 97、90、75 和 58.5 t/s，加上 llama.cpp Q4_K_M 的 36.87 t/s，在后端、量化、MTP 状态、上下文长度和 vLLM 版本上各不相同。每个数字都是单份报告 | 逐字运行一份已发布仓库配置并发布标志 |
| PCIe 敏感性 | 宽度几乎无关（单卡 +2 %）对比代际关系很大（3 卡管线并行 prefill +44 %） | 在一台机器、一个模型上跑 {Gen1、Gen2} × {x4、x16} 的 2×2 矩阵 |

| 长期稳定性 | 最长的已验证干净运行是四张卡上的 2 小时压力测试、一次 10 分钟 cuBLAS 运行，以及 1-2 天 LLM 运行的二手报告。24 小时和 48 小时运行都开始过，从未被报告 | 发布那些结果 |

## 需要 X 光、开盖或卡尺的物理问题

- **封装上有多少 HBM 堆栈，来自哪家厂商？** 一块开盖 8 GB 卡可见六个堆栈，其中十二个 FBP 中四个被扫掉；一份 die-shot 来源声称六个中有两个是假件；第三个读法就是四个堆栈。三者都预测同一个实测 4096 位总线，所以总线宽度无法区分任何东西。一篇流传的指南反而声称五个 16 GB 堆栈，那会暗示 5120 位总线，与测量不符。强工作假设（8 GB 用 SK hynix、10 GB 用 Samsung）从未被封装标记、X 光或厂商 ID 读出验证过。**注意几何不依赖它：** 无论哪种情况 CFG1 profile 都相同。
- **R240/R241（DEVID_SEL）在板上的哪里？** 想要它是因为设备 ID 是驱动几何的键，而 `OPT_DEVID_SW_OVERRIDE_DIS = 1` 关闭了每条软件路线。搜索启发式（在 200 系位号区域、PCB 上携带 500 以下位号的一侧，一颗旁边有空白焊盘的电阻）合理且未规模化尝试。两位研究者对候选区域是靠近 R986-R1005 还是在对面存在分歧。
- **导热垫是 1.5 mm 还是 2 mm？** 一位开过卡的卡主测了一次，另一个人说了一句"我觉得"。一把卡尺定案。
- **未装填的 4 针导流罩焊盘真的是风扇接口吗？** 一份报告称 12 V 和地存在，无转速或无 PWM；同一条线程中的怀疑者说它看起来不像风扇连接器。没有照片确认的引脚定义，没有可工作的风扇安装。

## 记录无法回答

- **总产量。** 估计从 1 万到数十万不等。已发布估计通过把 FY2022 CMP 收入除以假定的平均售价得出数量，没有按型号的销售组合。按型号出货数据公开不存在。诚实的答案是不存在可靠数字。
- **2026-07-05 那条把 Gen2 视为已解锁的消息**，比复现结果早三周，且与 2026-07-07 一条说 "We still need something for PCIe 2.0"（我们仍然需要点东西处理 PCIe 2.0）的消息直接冲突。要么是一个从未传播的更早独立结果，要么是时间戳归属错误。只有原始消息元数据能定案。该消息的技术内容（Gen3 是熔丝门控）与其他一切一致，可以信赖；日期不能。
- **正式发布工具是否符合净室自己的规则。** 正式发布载荷中的每个常量都可以从早于泄漏产物的已注明日期公开材料独立推导，而且净室几天前已经发布过等价链。同样真实的是正式发布代码在泄漏产物后 70 分钟出现，移除了一处敌对改动并添加了一个设备 ID 分支。原则上的可推导性不是事实上的推导。记录中没有任何东西能定案；参见[净室与出处](../history/clean-room-and-provenance.md)。
- **泄漏的包是被泄漏的还是被独立重实现的。** 靠近工作的人两种立场都有人持，且无论哪种方式产物功能等价。
