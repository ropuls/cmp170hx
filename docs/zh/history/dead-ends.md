# 死路：什么不工作，以及为什么

## 本页涵盖

2026 年 3 月至 2026 年 7 月期间，CMP 170HX 项目共记录了大约 **507 条死路**。本页按领域记录其中有意义的部分：当时真实持有的假说、它当时为何合理、杀死它的具体证据，以及它被放弃的日期。

开始新工作前先读这一页。其中好几条消耗了数周。有几条是被提出者自己推翻的，有时就在几分钟内，而这正是整份档案中最健康的模式。这里没有任何嘲弄：每一条都是基于当时可得证据的站得住脚的解读，而错的那几条，错在有趣的原因上。

本页存在是为了守护三个头条结果：

- FP32 节流**确实**由硬件强制实施，而且它**仍然**被击败了。两半都是真的。那份"无法覆盖"的已发布结论，对它所测试的每条路径都正确，对它从未尝试的那条路径则错了。
- L2/LTC 地址映射寄存器 `0x17E22C` 曾是团队对显存容量墙的根因模型，持续了一周多。它不是那堵墙。正式驱动从不触碰任何 `0x17Exxxx` 寄存器。
- 项目自己的 `docs` 分支**不是**权威。它编造缩写展开、打印代码不会写的寄存器值，并记载一个不存在的脚本。任何人拿它验证解锁，都会错误地得出解锁失败的结论。

## 如何阅读一条目

每条目携带四样东西：**假说**、它为何**貌似合理**、什么**驳倒了**它并给出具体证据，以及它被**放弃的日期**。凡是被其作者自己收回的主张，都会注明，因为自我收回是远比第三方争议更强的信号。

死路不等于未解决问题。未被驳倒而只是悬而未决的事项在 [未解决问题](../frontier/open-questions.md) 与 [状态板](../frontier/status-board.md) 上。被更好的东西取代的事项在此记录为已取代，并指向取代物。

## 计算与 FP 节流

### `SM_ISSUE_RATE_MODIFIER`（`0x00504204`）是节流寄存器

**假说。** 字面名为 "SM issue rate modifier" 的寄存器控制 1/32 FP32 发射速率。把它清零，节流解除。

**貌似合理因为**这个名称正是任何人想要的，寄存器在 PL0 主机可写，且在 170HX 上读到 `0x00000005`，与速率选择熔丝的值相同。两个独立事实似乎对上了。

**被驳倒因为**13 卡交叉探测：`0x00000005` 也是 A100 SXM4 40G、A100 PCIe 40G、A100 PCIe 80G、A10、A5000、A6000、RTX 3080、RTX 3080 Ti、RTX 3090、RTX 3090 Ti 与 Drive A100 读到的值。全速数据中心部件携带完全相同之值，所以它不可能编码节流。写入零没有产生性能变化。2026-07-27 在一张 96-SM `0x20bb` GA100（`NVIDIA DRIVE-PG199-PROD CC 8.0 SMs=96`）上复核，该卡读 `0x00000005` 而每个 `FUSE_SS_*` 都读 0。正式树中**零**引用 `0x504204`。

**放弃于**2026-05-31，2026-07-27 复核确认死亡。

### `RMOverrideSmSpeedSelect` 注册表键

**假说。** GSP 固件内一个真实的 NVIDIA 注册表键设置 SM 速率选择覆盖。设置它，节流解除。

**貌似合理因为**该键是真实的，整条消费链被逆向跟踪：VA `0x01607B78` 的 init 函数读取该键，并把一个存在标志加一个覆盖 dword 存入 GPU 配置结构；VA `0x01155DCC` 以半字读取覆盖；VA `0x01175A48` 至 `0x01175B2C` 的四个辅助函数测试位 0 至 3；存在标志检查位于 `0x014853E4` 与 `0x01491F34`。

**被驳倒因为**跟踪链条到其目的地。覆盖流入 PROD_DIFF 列表与 HAL 注册表表，最终指向 `0x504204` 的 `SM_ISSUE_RATE_MODIFIER`，而该地址的写在生产硅片上被静默丢弃。该地址甚至不作为字面量出现在固件中；它是经 HAL 抽象到达的。机制名对了，目标寄存器错了。

**放弃于**2026-04-04。

### 在 GSP 固件内伪造 `speed_select` 熔丝值

**假说。** 补丁 GSP 固件内的熔丝读取，使 GSP-RM 构建并交给 FECS 的 Production Differential 寄存器列表把 `SM_ISSUE_RATE_MODIFIER` 编程为 0。

**貌似合理因为**它攻击的确实是真相来源（熔丝读取）所在的层（PROD_DIFF），也确实在配置层。这不是瞎猜。

**被驳倒因为**两个独立事实。FECS 通过一个横跨 `0x20000000` 至 `0x23050000` 的 priv 窗口触及 GPU 寄存器，而 `SM_ISSUE_RATE_MODIFIER` 所在的 SM 寄存器空间（`0x20504xxx`）完全不在该窗口内，所以即使 PROD_DIFF 列表完美，FECS 物理上也无法写该寄存器。另外，GSP-RM 由 NVIDIA 签名。对 `gsp_ga10x.bin` 的十四个固件补丁（VA `0x1629618`、`0x1629694`、`0x16297f8`、`0x15d70bc`、`0x15d70f8`、`0x14b1480`、`0x14b1478`、`0x1607e20`、`0x1629680`、`0x1592b38`、`0x1592c50`、`0x1592d7c`、`0x1593620`、`0x15939a0`）加 12 处 `nvidia.ko` 编辑，把 FFMA 从 0.3159 TFLOPS 移到 0.3146 TFLOPS，0.4% 的差值被正确地称为测量噪声。

**放弃于**2026 年 4 月，2026-07-23 发布。

### "FP 节流由硬件强制实施、无法覆盖"

这是项目中后果最严重的一条死路。

**假说。** 一份外部发布的 AI 生成报告（约 18 小时 agent 时间、约 110 美元 API 花费）逐字得出结论："FFMA 节流不是软件限制。不是固件配置。不是驱动策略。它是芯片的物理属性，在工厂编程，由任何软件有机会介入之前运行的硬件逻辑强制执行。"

**貌似合理因为**它尝试的每条路径都真的失败，且其测量正确。这不是草率的工作。它自己的页脚记录了环境：Ubuntu 22.04，内核 5.15.0-174-generic，NVIDIA 驱动 535.288.01，CMP 170HX（`0x2082`），2026 年 4 月。

**被驳倒因为**2026-07-25 对一张已解锁卡的寄存器 dump 显示 `0x00823800` 与 `0x00823804` 读 `0xffffffff`，`0x0082381c` = `0x88888888`，`0x00823820` = `0x00000008`，`0x00823818` = `0x00000000`。搜索空间从未包含 `FEATURE_OVERRIDE` 寄存器块：它从未打开 `0x00823804` 的权限级掩码，也从未写 `0x0082381c`。

**值得保留的微妙之处。** 熔丝本身确实不可改，节流也确实由硬件强制执行。报告遗漏的是：强制实施在**权限级 3** 通过一个取代熔丝的有文档覆盖项可配置，而这个覆盖项之所以可用，仅仅是因为主杀熔丝 `OPT_FEATURE_FUSES_OVERRIDE_DISABLE`（`0x008203f0`）在这颗部件上读 `0x00000000`。NVIDIA 没有烧断覆盖启用。若它被烧断，那份报告就对了。

**放弃于**2026-07-25。驱动 535.288.01 也早于正式解锁器针对的 GSP 布局（610.43.02 与 610.43.03），这是其固件分析不适用的另一个原因。

### 不加载驱动时仅主机写寄存器

**假说。** 不加载驱动从主机写解锁寄存器，然后加载原厂驱动并保持结果。

**貌似合理因为**写入肉眼可见地落地。2026-06-30 一位研究人员在不加载驱动的情况下写了 `0x009A0204 = 0x02779000`、`0x0082381C = 0x88888888` 与 `0x00823804 = 0xFFFFFFFF`，并全部正确读回。

**被驳倒因为**之后加载原厂驱动：`0x00823804` 读回 `0xffffff8f`（重新锁定），节流除数回到 5。原厂驱动在正常 bring-up 过程中重新锁定权限级掩码。这正是驱动内 GSP 启动路径设计要解决的失败模式。

**放弃于**2026-06-30。被在 SEC2 Booter 窗口内打开掩码并在同一次驱动加载中写寄存器取代。参见 [解锁原理](../unlock/how-it-works.md)。

### 打开 `0x008200FC` 的 `FUSE_SS_PLM`

**假说。** 速率选择熔丝掩码在每张卡上都完全打开（`0xffffffff`），读起来像疏忽。就穿它。

**貌似合理因为**恰好位于目标寄存器上的无守卫权限级掩码正是让解锁成为可能的那类错误，而一份早期整合配方（2026-07-07）把写它列为三个高安全步骤之一。

**被驳倒因为**它背后是什么：`OPT_SM_SPEED_SELECT` 寄存器是 OTP 熔丝**影子**，无论权限如何都只读。另外，写掩码本身失败：无论从 ROP 还是直接主机 `writel`，它都物理上只读，封顶 `0x000003FF`。当时记录的正确诊断是："不需要 PLM，如果我们直接改 SM_SPD 寄存器。"正式解锁完全不触碰该地址。

**放弃于**2026-07-09。它以代号 `OPT_PLM` 重新出现在 Gen2 家族分支的九条目掩码表中。

### 恢复额外的 SM

**假说。** 卡被 floorsweep 到 108 个中的 70 个 SM，且 floorsweep 控制寄存器可写，所以缺失的 SM 可以重新打开。

**貌似合理因为**`FUSE_STATUS_OPT_TPC_GPC(i)`（`0x820c38 + i*4`）清楚显示禁用模式（GPC0、GPC3 与 GPC5 读 `0xff`，其余读 `0x01`），控制寄存器就在旁边 `0x820838 + i*4`。envytools 还把 floorsweep 寄存器描述为权限级 r4 可读写。

**被驳倒因为**档案中最干净的否定结果实验，它带两个对照。**阳性对照**：对 FBPA CFG1 `0x9a0204` 的高安全写把 `0x02449000` 改成 `0x02779000` 并保持，`resetPLM = 0xff` 全程，证明 Booter 写原语是活的。**可达性对照**：对 `CTRL_OPT 0x82083c` 的高安全写把 0 改成 `0x80`，`STATUS 0x820c3c` 以 `0x1` 对 `0x81` 响应，证明 floorsweep 块本身接受高安全写。真正的目标全部弹回：`OPT_GPC_DISABLE 0x820350` 保持 `0x45`，`STATUS_OPT_GPC 0x820c1c` 保持 `0x45`，`OPT_TPC_GPC2 0x820768` 保持 `0xff`，`DIS_SW_OVR 0x820084` 保持 1，`RING_ENUM_GPC` 从未离开 5。GPC 禁用寄存器是锁存的。权限级从来不是阻碍。

**放弃于**2026-07-27，在一张 8 GB 卡（`0x20c2`）上。

对 `gpcMask`（强制 `0xdc` 到 `0xff`）的并行攻击被一个已让 64 GB 显存解锁工作的人以三种独立方式尝试：经 RM floorsweep 结构、经主机 MMIO 写 `GPU_REG_WR32(0x408970, 0xFF)`，以及补丁 GSP 固件的 `andi` 指令为 `li a4,255`。三种情况下软件栈都报告 8 个 GPC 与 112 个 SM，`0x408970` 每次都读回 `0xdc`，且 `cuInit` 段错误。掩码不是杠杆；GPC 确实被熔丝关闭或功耗门控。

### 调校死路

这里每条都在 2026-07-27 的单次会话中于硬件上测得，对任何调校卡的人直接有用。参见 [调校](../operations/tuning.md)。

| 假说 | 什么驳倒了它 |
|---|---|
| 1650 MHz 以上的时钟上限买到性能 | 1700 MHz 与 1740 MHz 上限都交付约 1600 MHz 有效频率与 213 至 214 TFLOPS，不比 1650 MHz 的 214.7 TFLOPS 好。硅片在 +350 时封顶约 1604 至 1614 MHz |

> **实验性**
>
> `nvidia-smi` 在解锁卡上报告 `clocks.max.sm = 1935 MHz`。这是**报告字段，不是可达成时钟**，且仅凭一次未经复核的报告。VBIOS 表最大图形时钟是 1695 MHz，实际硅片上限在 +350 偏移时约 1604 至 1614 MHz。持续 SM 时钟是 **1410 MHz**，或 `-pl 300` 时 1470 MHz。不要按 1935 MHz 规划。

## 显存几何与容量

### `0x17E22C` 的 L2/LTC 地址映射墙

这是团队对容量限制的工作根因模型，持续了一周多，而且是错的。

**假说。** GSP-RM 从 `0x17E22C` 的 L2/LTC 地址映射推导可用 framebuffer 大小，其值为 `fbSize >> 28`，由 DEVINIT 在 10 GB 处锁存。因此 10 GB 以上的真实容量需要编程地址映射，而打开 `0x17E0xx` 的 LTC 权限级掩码需要驱动内 `kgspExecuteBooterLoad`。

**貌似合理因为**它于 2026-07-14 以 ROOT-CAUSE 记录并附支持细节：该值是从主机只读的镜像，位 [24:22] 即使高安全模式也不可写，40 GB 的目标值 `0x00a00404` 在运行时无法锁存。原生值 `0x28` 恰好匹配 10 GiB。该模型正确预测了几个中间观测，这正是它得以持久的原因。

**被驳倒因为**2026-07-22 的一次运行达到真实 40 GB，而 `0x17E22C` 全程停在原生 `0x00280404`，从未编程。链头逐字记录更正：`CORRECTED 2026-07-22: usable fbSize tracks LMR(0x100CE0)+CFG1+CSTATUS (all fire-writable), NOT the amap 0x17E22C.` 常设确认是：正式驱动在任何地方都不含 `0x17Exxxx` 地址，master 或十二个分支快照中都没有。

**放弃于**2026-07-22。一个真实的寄存器事实在收回后幸存：**`0x17E22C` 的位 23 被熔丝锁定**。

与之同时记录的诚实自评值得实质引用：开源 CPU 侧 RM（`kern_mem_sys_gp102.c`）从 LMR `0x100CE0` 计算 framebuffer 大小，而非 `0x17E22C`；且启用 GSP 固件后，CPU-RM 根本不读该寄存器，而是在 `GspStaticConfigInfo` 中经 RPC 从 GSP-RM 接收 framebuffer 大小。"`0x17E22C` = fbSize>>28"的标签来自先前基于原生值匹配 10 GiB 的推断笔记，而非读取固件——团队从未反汇编过固件。

一个相关主张——正式驱动的掩码表写 LTC 解码簇（`0x17E2B4` / `0x17E2A0` / `0x17E2E4` / `0x17E2FC`）——是**假的**。正式表有四项：`0x001fa7cc` 到 `0xfffff0ff`、`0x009a0148` 到 `0xffffffff`、`0x001fa7c4` 到 `0xffffffff` 与 `0x00823804` 到 `0xffffffff`。

### 10 GB 卡的 80 GB 几何

**假说。** 10 GB 卡可以吃下 8 GB 卡的 CFG1 值 `0x02779000`，配 80 GiB 的 `fb_bytes` `0x0000001400000000`，达到 81920 MiB，就像 8 GB 卡达到 65536 MiB 那样。

**貌似合理因为**它距一条可行路径只差一小步，提交历史显示它被认真对待（"Trying an 80GB unlock instead of 40GB"，然后 "Correct LMR for 80GB"），几何寄存器接受它，卡能启动，且 `nvidia-smi` 报告约 81920 MiB。PRAMIN 另外证明物理 DRAM 存在 80 个不同的 GiB。已发布论文也反复声明 10 GB 到 80 GB（摘要"10 GB instead of 80 GB"，表 1 "Memory capacity (10 to 80 GB)"）。

**被驳倒因为**分支出现后一到两天内三名独立测试者：`cuda_memtest` 在 39 GiB 以上挂起，模型加载在约 20 GB 以上失败，第二名测试者在 40 至 60 GB 区间看到失败。回退到 40 GB 几何恢复可用负载。论文自己的稳定性数据与驳倒一致：80 GB 下一次 gpu-burn 运行 2,796 个错误，而同一张卡 40 GB 时干净运行。

**放弃于**2026-07-19 至 2026-07-20。master 为 10 GB 卡发货 40 GB：CFG1 `0x02669000`、LMR `0x0000028A`、`fb_bytes 0x0000000A00000000`。

> [!CAUTION]
> **`80` 分支按构建而言内部不一致**
>
> 分支的 `common/constants.yaml` 说 `lmr: "0x0000028B"`，而 `0x28B` 算术上正是 81920 MiB 的正确 LMR。但 `build.sh` 从不读 `constants.yaml`。在该分支上，`driver/build.sh` 第 93 行设 `LMR="0x0000028A"`，`install.sh` 第 138 行打印 `Unlock geometry: 80GB (CFG1=0x02779000 LMR=0x0000028A)`，`driver/patches/0001-sec2-postbl-plm-ss-cfg.patch` 第 144 行烤入 `lmrValue = 0x0000028AU`。构建期 Python 重写被短路，因为双设备守卫找到它寻找的全部七个标记并提前退出。**提交 `3c53aca` "Correct LMR for 80GB" 只改了惰性元数据。** 每个跑过 `80` 分支的测试者都在 LMR 向 MMU 声明 40960 MiB、`targetFbBytes` 向 GSP 声明 80 GiB 的同时，编程了 CFG1 `0x02779000`（每个 FBPA 4096 MiB，FBPA 几何 81920 MiB）：三方不一致恰好预测了被报告的行为——`nvidia-smi` 报 80 GB、硬件解码 40 GiB、别名测试恰在 40 GiB 处折叠。该分支的任何*构建*都从未携带一致的 `0x28B` 三元组。一致的寄存器集是另外由净室 refire 脚本达到的，且那里没有出现折叠：参见 [80 GB 问题](../frontier/80gb.md)。

围绕该分支还有两处对记录的更正：

- **"没有补丁文件与 master 不同"是错的。** 字节比较显示 `0002` 至 `0006` 相同，但 `0001-sec2-postbl-plm-ss-cfg.patch` 恰好有两行不同：`cfg1Value = 0x02669000U` 变成 `0x02779000U`，`targetFbBytes ... 0x0000000A00000000ULL` 变成 `0x0000001400000000ULL`。分支还改 `build.sh`、`install.sh` 与 `constants.yaml`。
- **"80 GB 需要焊接一些 SMD 元件"是错的。** 达到 80 GB 不需要任何硬件修改，也没有已知的东西能稳定它。2026-07-25 经验性佐证：一张未改装的 10 GB 卡用 refire 脚本达到同样的 80 GB 状态。

尚未解决的问题见 [80 GB 前沿页](../frontier/80gb.md)。

### 测量陷阱

**4 GiB 的 `cuMemGetInfo` 结果。** 2026-07-22，一次无 FLR 的 GSP-RM 启动后，`cuMemGetInfo` 报告 `total = 4.00 GiB`。它貌似合理，因为它带一个自洽的分配模式：36、20 与 12 GiB 分配以 `r=1` 失败，而 10 GiB 成功。次日上午被不复现与识别出**测试工具链中的 ctypes bug 把 64 位 `size_t` 截断为 32 位**而驳倒。同一会话随后测出 39.67 GiB 总与 39.39 GiB 空闲。这是该类的原型：数字错了，工具错了，佐证模式是巧合。

**不带 L2 驱逐的朴素内存折叠测试。** 早期折叠检查报告 37 至 38 GiB 处出现折叠。修正后的方法论在读回标签前先灌 1 GB 驱逐 L2，之后不出现折叠。**2026-07-22 之前任何未驱逐 L2 的折叠结果都应丢弃。**

**折叠工具链本身不可靠。** 一次次级总线复位回到一致原生状态（10240 MiB、驱动 610.43.03、CFG1 `0x02449000`、地址映射 `0x00280404`）后的对照运行分配了 9 GiB 真正原生显存，却在五轮中报告"4608 chunks, 4608 corrupt/aliased"，即原生显存在折叠——不可能。更早同一工具链把 10 GiB 报告为"5120 chunks verified, 5120 aliased/corrupt"，第 1 轮约 26.6 GB/s，第 2 至 5 轮约 197 至 198 GB/s。这追溯性地使一批更早的"40 GB 处折叠"结论失效。

**稀疏内存探测。** 表面上是相对密集扫描的合理优化，而且确实被用过。它在折叠卡上给出假阴性，因为折叠在通道交错偏移处别名（`LOW[0]` 映射到 `40GiB[+576]`），所以它写一个伙伴却检查另一个地址。源指令是明确的：不要把密集扫描优化成稀疏扫描。

**"`nvidia-smi` 显示了它，所以它存在。"** 一个早期手动流程从 `nv-linux.c` 强制 `fb_size` 到约 80 GB，并把 `uvm_gpu` 堆设为 81920 MB，而 `STRAP` 与 `LMR` 携带 64 GB 值（`0x9A0204 = 0x02779000`、`0x100CE0 = 0x0000020B`）。报告的 80 GB 是坐在 64 GB 几何之上的驱动侧显示覆盖。该谱系之后的每个日志都报告 `fbTotal=65536MB`。这解释了一整类误导性早期截图，也是密集标签验证标准的起源。参见 [验证](../procedures/verify.md)。

**"PRAMIN 在 LMR `0x28c` 时显示真实内存直到 159 GiB。"** 日志在 64、72、76、78、79、80、81、82、84、88、96、112、128 与 159 GiB 处把读回标为 REAL，干扰测试被报告为独立。算术确实一致，因为 `0x28c` 解码为 163840 MiB。但同一次运行以 `recovered cap=10240 MiB` 结束，作者把它当玩笑，并于 2026-07-12 弃绝整个内存分析。日期：2026-07-07。

**"10 GB 以上带宽塌到 32 GiB/s，因为 HBM 未训练。"** 第一次扫描字面显示 1 GB memset 1449 GiB/s（100%）、4 GB 1446（100%）、8 GB 1251（86%）、16 GB 1242（86%）、32 GB 及以上掉到 32 GiB/s，"untrained" 是对每个 80 GB 症状的主流解释。同日一次偏移扫描显示从 8 GB 一直到 76 GB 均匀 **79% 的峰值、无死区**。32 GiB/s 读数是扫描测试耗尽单个 CUDA context 的伪影。日期：2026-07-25。

## 固件、Falcon 与 Booter ROP

这是档案中最密集的领域。这里几乎每一条都是：一个貌似合理的常量、gadget 地址或退出策略被携带数天，直到反汇编或硬件 A/B 定案。什么是真的参见 [Falcon 与 Booter](../unlock/falcon-and-booter.md) 与 [ROP 链](../unlock/rop-chain.md)。

### "显存解锁的软件投递在架构上不可能"

**假说。** 一个五环死结，2026-07-12 被声明为已证明且结构性：显存 strap 需要重安全模式写入；Booter 的单一高安全退出固有地把 `0x8403C4` 的 SEC2 复位掩码盖成 `0x8f`；`0x8f` 阻止第二次加载的 Booter；只有 FLR 能清 `0x8f`；而 FLR 把 framebuffer 配置回退到只读 strap 默认。两个候选投递架构都被宣布封死：单加载被 SEC2 在 CORE_RESUME 的双重角色封死，双加载被 `0x8f` 污染封死。声明的"可用路径"是对电阻 R1004 与 R1005 的物理重 strap。

**貌似合理因为**每个环都被独立观察到，且每一条孤立地都是真的。

**数天内被驳倒两次。** 2026-07-13 一个 Hello-World ucode 证明 SEC2 在 `0x8f` 时仍运行代码。2026-07-15 一个 `mutexfree` 终结符以 `resetPLM = 0xff` 退出，完全没有 FLR。作者写道："it overturns the documented 0x8f is unavoidable verdict."

**放弃于**2026-07-15。一个相关的绝对断言——"`0x8f` 在高安全到非安全退出时硬件锁存，因此任何退出都不能留下 `0xff`"——走了同样的弧线：机制成立，结论不成立。从不运行 teardown 的提前与自旋驻留退出，显式以 `0x8403C4 = 0xff` 作为最后动作写入，确实会留下 `0xff`。

R1004 与 R1005 的物理重 strap 仍是真实硬件选项，也是当时诚实的结论。它不是最终发货的东西。

### GSP 启动的"结构性墙"

**假说（2026-07-10，22:40）。** GA100 GSP 启动在架构上与 Booter 溢出漏洞利用不兼容：启动需要启动中 GSP 复位加 SEC2 驱动的重载，单发溢出劫持第一次 SEC2 加载，而被利用的 SEC2 无法服务 CORE_RESUME，因为它掩码锁定、SCP 密钥被擦除且没有位 26 代码路径。"漏洞利用恰好破坏了启动所需要的东西。"

**貌似合理因为**每次尝试都以 `0x62:0x55` 失败。

**2026-07-12，15:20 被驳倒**：一次对照运行——干净、不污染的第一加载——第二加载一路启动到 `nvidia-smi` 报告 10240 MiB。`0x55` 是 ROP 自己的 `WPR2_HI = 0` 写清除 WPR2 造成的自伤（`0x55` 字面就是"can't load GSP-RM into WPR2"），残留的 SEC2 污染来自第一加载自身的驱动重试循环。

### `0x10aa` 与写原语

**假说（2026-07-02 至 03）。**"`0x10aa` 写 BAR0 中的预定义寄存器。这些地址不能改变…… `0x10aa` 函数毫无用处，连当 gadget 部件都不行。"次日更强地重申："`0x10aa` 函数是误导。对我们完全无用。"

**貌似合理因为**该函数确实引用看起来固定的地址，且 `0x8224` 看起来像更直接的写。

**被驳倒因为**反分析显示 `0x1c100` 与 `0x1c200` 是 BAR0 master 的地址与数据端口而非最终目标，且 Booter 自己把 `0x29b8` 路由到 `0x10aa` 以写自己的 WPR2 寄存器，证明 `r0` 与 `r1` 能穿过中间的 `0x1064` 与 `0x8264` 调用存活。到 2026-07-06，`full_0x10aa` 链被硬件确认为任意高安全 BAR0-master 写。`0x10aa` 就是正式 payload 在偏移 `0xf788` 种植的写 gadget。提出者承认从它获得了"a lot of useful information and hints"。

**放弃于**2026-07-06。

两个随之解决的死路：

- **"`0x1c300` 的 BAR0-master 所有权互斥锁在静默丢弃我们的写。"** 貌似合理因为 `0x1c300` 在 `0x1042` 被引用，且被劫持的流跳过了 Booter 启动期间执行的任何获取。被两个事实杀死：Falcon 单核单线程，其自身运行不需要互斥锁（任何互斥只协调不同 GPU 处理器之间）；调和分析显示链的写字节完美，"bug 完全在退出尾部…… 写确实发出；尾部把它们扔了"。2026-07-02 提出，2026-07-11 驳倒。
- **"直接写"理论**，声称 gadget `0x8224` 写 `BAR0[r10 & 0xFFFF] = r11`，只对 `0xA800` 以下的 BAR0 偏移有效，且硬件应用读-改-写掩码。它貌似合理因为活体卡上测的四对写读回构成整洁模式：掩码 `0xFFFFFFFF` 读回 `0xFFFFFF8F`，strap `0x02779000` 读回 `0x02449000`，LMR `0x0000020B` 读回 `0x00000208`，WPR2 `0x1FFFFE00` 读回 `0x01F77000`。驳倒：`0x8224` 是 `csb_write`，写 Falcon CSB 空间 `I[r10]` 而非外部 BAR0，所以那些"读回"只是从未被写的寄存器的**未触碰原厂值**。`0xffffff8f`、`0x02449000` 与 `0x208` 恰是文档化的原厂值。日期 2026-07-15。

### 16 位地址截断模型

**假说。** 高安全 Falcon 间接写引擎把 32 位地址截断为 16 位，所以 `0x009A0204` 落在 `BAR0[0x0204]`，配逐寄存器 PRI 写掩码过滤值。一个变体声称对 `0x9A0204`、`0x100CE0`、`0x823804` 与 `0x1FA824` 的写实际落在 `0x0204`、`0x0CE0`、`0x3804` 与 `0xA824`。

**貌似合理因为**那些截断偏移确实读 `0xbadf`，看起来像佐证。

**被驳倒因为**每个真正落地写的工具：2026-07-08 poke 生成器、2026-07-22 refire chain 与正式解锁器都传**完整 32 位地址**并在完整地址读回。该模型也无法解释 `0x00900204 + n*0x4000` 的 per-FBPA 写，它们共享低 16 位。一个相关的截断写列表（`0x00000204`、`0x00000CE0`、`0x0000A7CC`）被呈现为 BAR0 相对，但内部不一致，因为同一列表把掩码写保留在完整 `0x00823804`，且任何地方都不存在确认截断写的读回。

**放弃于**2026-07-13 至 2026-07-16。把它当作抄录错误，而非独立的寻址模式。

### Mailbox `0x31`

**假说，四种连续解读。** (a) 带 `excause = 0xa` 的 `IMEM_MISS_INS` Falcon 故障，来自 recovery 跳进未加载的 IMEM，可能是 ROP 已夺权的迹象。(b) 驱动种植的值。(c) "Canary passed, PC hijacked (exploit successful!)"，一个 loader 脚本逐字打印过。(d) 一个早期"HS-entered"标记，表示 phase-3 quiesce 停滞。

**貌似合理因为**`0x31` 确实出现在每个故事都说得通的点上。

**2026-07-17 / 18 解决**：在反汇编中定位该值：Booter 自己在 ucode 偏移 `0x7a` 处把 `0x31` 盖为它的第一个存活标记，覆盖驱动种植的 WprMeta 物理地址参数，`0x1d0f` 的 `report_status` 之后改写它。所以 `0x31` 只意味着"`report_status` 从未运行"，这与早期停滞**和**成功劫持都兼容。它不是错误码，也不是任何东西的证据。

一个并行的混淆——"`0x65 == 0x31`"——在 2026-07-10 一小时内被杀死：WPR2 错误只来自寄存器写，而一次无写的两加载运行仍产生 `0x65`。

### `0x1180f8` 的顶半字节

**假说，单日（2026-07-15）内修订三次。** 首先：mutexfree 终结符留下 `0xf0000000`，`booter_unload` 以 `0x29` 拒绝它，所以半字节 0 被宣布正确。然后，因为 `whole_stack_rejoin`（走得最远、RISC-V 核活跃）写半字节 `0x1` 且原厂启动后状态读 `0x11000000`，目标被修订为 `0x1`，三次先前测试被宣布为错误。

**被反汇编驳倒**：`0x80a5` 的 `check_1180f8_nibbles` 要求**传入**顶半字节为 0。**半字节从来不是阻碍。** Booter 死在 `booter_load_wpr_main` 的 `0x22ba` 更深处，在目标引擎握手处挂起，`MB0 = 0x31`、无 halt，产生驱动的 `0x65` 超时。

**放弃于**2026-07-15，已消耗若干测试迭代。

两个相邻理论随之死亡：

- **"`0x1180f8` 就是 ACR 互斥锁或 WprMeta 所有权令牌"，非零顶半字节意味着"WPR2 被拥有"。** 貌似合理因为半字节确实随启动阶段变化，且互斥在附近释放。被驳倒两次：互斥由 `0x1c0e` **内部**的 `0xccb` 调用释放，而非半字节存储；且该寄存器后来被识别为启动阶段暂存，字段为 `[27:24]`、`[31:28]`、`[23:20]` 与位 26。
- **"`0xd66` 的互斥获取在半字节存储前把 `r10` 踩成拥有者 ID `0xf`。"** 被反汇编驳倒：`r10` 在 `0xd66` 调用**之前**于 `0x1c1f` 复制到 `r0`，`0xf` 来自 `main` 在 `0x80f1` 的显式 `-1` 存储（`mov $r15 -0x1; mov $r9 $sp; add b32 $r9 $r9 0x8; st b32 D[$r9] $r15`），把 `0xffffffff` 放进 `D[sp+8]`；`0x1c0e` 随后写 `(0xffffffff << 28) = 0xf0000000`。

`0x1180f8` 的交接值也移动了两次：`0x11000000` 到 `0x13100000` 到 `0x17100000`。`0x11000000` 错是因为位 26 = 0 会通过 Booter 在 `0x1c9a` 的 `0x29` 检查但失败主机 `_kgspIsReloadCompleted` 轮询；`0x17100000` 被测量为两者都通过。`0x17100000` 写还产生了新的 FBPA 掩码打开失败，而正式链完全不依赖它。

### 曾被归罪又被洗清的溢出机制

- **"每条携带写的 rejoin 链都在 `0xccb` 失败。"** 每次点火之间带 FLR 的系统隔离显示每种写变体都在 `0xccb` 失败，`finalize = 0x01000000`，而无写 `whole_stack` 链以 `0x11000000` 通过。沿途排除：BCR 特定行为（普通暂存写同样失败）、共享 BAR0-master 状态、`0x10` 处 main-SP 帧碰撞，与溢出大小（`0xF810` 同样失败）。提出的根因是写花费 main-SP 移动 `+0x18`，把 `main` 放到 `0xFFFC`，使 `0xccb` 的 SP 相对访问卷过 `0x10000`；约束是 `main` 必须保持在 `0xFFF0` 以下，而最小 BAR0-master 写花费 `+0x10` 或 `+0x18`。**Booter 中不存在降低 SP 的 gadget**：`mov $sp $r9` 只出现在 `_start`，它会重跑启动，且所有 `mpush` 与 `add $sp -N` 形式都在函数序言内。当时记录的警示：该结论是 AI 生成的分析，从未被独立复现。日期 2026-07-06。
- **"写与干净的 `0xff` 退出结构性不兼容。"** 2026-07-12 13:58 以经过测试的消去矩阵宣布"已证明且结构性"。同日数小时后被 `0x8117` 裸退出路线取代，它完全跳过 `main` 的 finalize。并行的"7 个空闲栈词"线索被称为红鲱鱼。
- **"扩大溢出技巧"**，把 payload 提高到 `0xF810` 使 DMA 卷进 DMEM `0x0` 至 `0xF`，让 finalize 局部变量由 payload 控制。最初有希望，被描述为带已发出写到达 finalize。同日被隔离扫描排除：`0xF810` 与每个其他写变体同样失败。它确实确立了一个有用事实：Falcon 栈从 `0xFFFF` 环绕到 `0x0000`。日期 2026-07-06。
- **"sig-DMA 溢出砸碎栈"作为免驱动失败的解说。** 被四个独立对照消除：假地址给出相同结果；大小 `0x200` 对 `0xF800` 给出相同结果；会捕获任何帧砸碎的自旋滑道仍然 halt；强制一致孔径仍然 halt。内核日志中无 IOMMU 或 DMAR 故障，所以它是与签名无关的、固定点处的 Falcon 内部异常（`EXCI cause 0x9`）。真正的原因被定位到 `nvidia.ko` 的 FWSEC 与 ACR 路径建立而免驱动路径没有的 SEC2 上下文缺口。**溢出机制本身健全**，同样的溢出在 `nvidia.ko` 下有效。日期 2026-07-07。
- **对签名补零。** 假说是整个 `0xF800` 缓冲都可是任意 payload。payload 必须**以真实、有效的签名开头**：补零使原厂 Booter 在 ROP 夺权前就以 mailbox `0x31` 退出。与对照实验一致：签名加 256 个正确字节能启动，任何签名破坏都给 `0x31`。
- **"驱动忽略膨胀的 `.fwsignature` 节大小。"** 解读是原厂驱动从 `pGspFw->signatureSize` 确定签名内存描述符大小并精确复制那么多字节，而非节的 `sh_size`，所以拼接永远不会溢出。快速读源码时原厂代码路径看起来正是如此。同日在 `_kgspCreateSignatureMemdesc` 内加一行诊断打印驳倒：`NVRM: _kgspCreateSignatureMemdesc: V3DIAG signatureSize=0xf800 memdescSize=0xf800`。容器读取器 `_kgspFwContainerGetSection` 验证 `sh_size` 与 `sh_offset`，所以拼接确实到达它。日期 2026-07-11。
- **烤入的 `REJOIN_WPRMETA`。** rejoin payload 硬编码 `{r2: 0xf7700000, r4: 0xffeff000, ...}`，注释"captured live, attempt-1"。来自真实点火的活体 WprMeta dump 显示 framebuffer 地址每次启动随机化，所以静态捕获无法复用。审阅者还标记重建栈把两个金丝雀相邻放置，这不应发生。日期 2026-07-06。
- **"Booter 行为与几何无关。"** 2026-07-14 被同一后 Booter 检查点的并排对比驳倒：SEC2 MB0 `0x0`（Booter 报告成功）对 `0x31`（漏洞利用残留，Booter 从未报告）；RV_STATUS `0x35`（RISC-V 活跃）对 `0x0`（从未启动）；finalize `0x11000000` 对 `0x0`；WPR2 `0x02777000` 两者都刻。40 GB 时 Booter 在刻 WPR2 之后、finalize 之前 halt，**不调用 `report_status`**，这是陷阱或异常而非数据验证不匹配。
- **`RA_SKIP` 核启动理论。** 2026-07-13 提出：GSP-RM 的 RISC-V 从未启动，因为 `RA_SKIP = 0x38a7` 跳过 `hw_init_block 0x692f` 中 Booter 的核启动块。数天内被取代：冷启动与 `whole_stack_rejoin` 运行都显示 RISC-V 核启动（RV_STATUS `0x33` 或 `0x35`），真正阻碍是被持有的 ACR 互斥锁与 RmInitDone 阶段。
- **把非确定性 payload 落地归咎于缓冲物理地址布局。** 点火 #1 落地全部 5 次写；之后约 12 次相同点火只落地 3/5，丢弃 strap 与复位掩码写。签名 payload 物理地址在运行间于 `0x104800000` 与 `0x104a00000` 之间交换，给出 `MAILBOX0 = 0x31` 对 `0x6e`，使缓冲顺序看起来有因果关系。被后续 39 次点火驳倒：全部返回 `0x6e`，3 至 5 次写，外加填充扫描与池复位都无法复现好的落地。`iommu=pt` 与 hugepages 被明确排除。真正差异是 GSP 启动状态：点火 #1 是唯一一次在 `.04` 驱动启动 GSP-RM 后立即运行，在 WPR2 中留下有效 WprMeta。日期 2026-07-12。

### 分析目标与工具错误

- **把 `gsp_tu10x.bin` 当作 Booter 解密。** 好几个人花了数天。它不是 SEC2 Falcon Booter；它是 Booter 验证的 GSP RISC-V ELF payload。`file gsp_tu10x.bin` 对 580.65.06 构建返回 "ELF 64-bit LSB relocatable, UCB RISC-V, soft-float ABI, version 1 (SYSV), BuildID[sha1]=9ea6f739bfdf716c0d1211471c68a083e376fe4c, not stripped"。Ghidra 从它产出约 **100 MB 的 C**，`riscv64-unknown-elf-objdump` 约 **1.5 GB 的汇编**。真正目标只有约 `0x6000` 字节、约 25 kB，反汇编约 390 kB：`booter_load_ga100_*.bin`。貌似合理因为它是驱动加载的 GSP 固件文件、在 `/lib/firmware/nvidia/*/` 中、看起来加密。**重要细微之处：**该文件并非无用。净室 Python 解锁把其 ROP payload 注入的正是这个文件的 `.fwsignature_ga100` 节。它是错误的反汇编目标，却是正确的投递载体。日期 2026-06-30。
- **担心 `-debug` 编译标志会移动每个 gadget 地址。** 貌似合理因为那是 debug 构建通常做的，若为真整套净室路线就会死亡。两种方式驳倒：debug 与生产二进制恰好同样大小；一条完全由 debug 反汇编构建的 ROP 链在生产硅片上正确执行。日期 2026-07-02。
- **`faucon` 反汇编器与模拟器对加密 Booter。** 报告为"encrypted/obfuscated"并放弃。实际产出结果的分析是手工做的。日期 2026-07-21。
- **`envytools` 作为 Falcon 安全启动的来源。** 记录为否定结果：加密页完全是"Todo: write me"。不要再搜。
- **信任社区 Falcon 模拟器为基准真相。** 一条本应在 `$r15` 留下原金丝雀并回显到 mailbox 的金丝雀回显 ROP 在模拟器中打印金丝雀，但在真实硅片上，一个变体产生每启动随机数、另一个什么也没有。另外，模拟器与验证过的 `mpopaddret` 语义都预测某链下一个返回地址槽在字节 63364，但硅片上链漂移并返回 `0x31`。从未解决。
- **手工重建进入溢出的调用链。** 放弃因为 `0x4d4` 从至少 20 处被调用，静态推理无法确定哪些帧在栈上。被从 8 GB 卡逐字逐出真实栈（**35 次启动**）取代。
- **LLM 生成的 DMEM 图把 32 字节签名缓冲放在 `0x5c00` 至 `0x5c1f`。** 2026-07-13 流传，被审阅为"good summary"带"some minor technical errors"。它比那更糟。它既列出 `0x0800` 的"signature verification buffer"又列出 `0x5c00` 的"SIGNATURE BUFFER (32 bytes)"，自相矛盾。它在一个 DMEM 图里列出"IMEM code"范围，在哈佛架构下是范畴错误。它还把 `0x9100` 列为"CSB"、`0xd000` 至 `0xd500` 为"mailbox registers"、`0x10100` 与 `0x14000` 至 `0x14b00` 为"IO windows"、`0x30000+` 为 payload 区域——这些全是 CSB 或 IO 地址，或在 `0x10000` 的 DMEM 末尾之外。**被工作漏洞利用确认**的条目是 `0x0600`（WPR 描述符）、`0x0700`（镜像描述符）、`0x0800`（签名缓冲）、`0x6330` 至 `0x633f`（暂存）与 `0x6340`（栈金丝雀守卫）。还有一个要留意的误标：同一家族文档写"Signature buffer: BAR0[0x0800]"。它是 **DMEM** `0x0800`，不是 BAR0。
- **208 个可写 BAR0 寄存器扫描。** 报告找到 208 个 PRI 掩码 `0x00000000` 的完全可写寄存器，聚集在签名缓冲、配置与 mailbox 区域。作为扫描输出貌似合理，但来源与上述 DMEM 图同一文档，从未被独立复现，且它把"0x0800 (signature buffer)"列为 BAR0 寄存器，重复 DMEM/BAR0 混淆。视为未验证。
- **bot 声称"直接写对 BAR0 偏移 < `0xA800` 有效、之上失败"。** 被挑战为内部不一致，随附 ROP 链被证明结构性破损：它用 `0x30bb` 与 `0x30be` 作电梯，它们位于长函数 `0x2e80` `image_auth_decrypt()` 的开头，其中 `$r10` 与 `$r11` 被多次覆盖。调用 `0x8224` 的正确电梯是 `0x1fb9` 与 `0x1fbd`。日期 2026-07-15。
- **直接调用 `0x8224 csb_write` 而非 `0x10aa` 或 `0x10b9`。** 有效，但需要在 ROP 中为每个寄存器手工编排地址、数据、命令与轮询序列，花费更多帧而没有任何好处。`0x10b9` 是干净的链式封装，因为它以 `mpopaddret $r3 0x4` 结束并直走下一个写帧。
- **一个"mega-ROP"放在低 DMEM。** 被观察排除：DMEM `0x100` 以下根本没有任何分配。
- **区域拼接想法**——把 DMEM `0x650` 处的 `0x1000` 写放进 `nvidia.ko` rejoin ROP——被发现需要溢出后的 DMA-to-WPR2 写，未继续。
- **寄存器扫描结论 `0x9a0148` 及其同类无功能。** 扫描发现 `0x100b10`、`0x100b38`、`0x9A0148`、`0x9A014C`、`0x9A0108`、`0x9A0008`、`0x9A010C` 与 `0x9A000C` 都不是常开（FLR 时 `0xffffffff` 回退 `0xffffff8f`），并把它们标记为对几何无功能。正式补丁每次启动都把 `0x009a0148` 打开为 `0xffffffff` 并记录读回。扫描作者自己立即标记了解释它的方法论漏洞：扫描在高安全模式打开掩码，然后**在 FLR 之后**从主机做几何写，所以如果几何影子只锁存高安全内写，扫描会对每个掩码都报告几何失败，无论其如何。日期 2026-07-16 至 18。
- **"先打开四个 FBPA 掩码"作为高安全路径的前提。** 被测量驳倒：一次高安全广播 CFG1 写把全部 20 个活 FBPA 从 `CSTATUS 0x200` 移到 `0x800`。高安全模式完全绕过 FBPA 掩码；打开它们只对主机-PL0 per-FBPA 写需要。日期 2026-07-15。
- **CMP 90HX 上的持久性。** 一位测试者报告漏洞利用"landed on 90hx and it... persists"，随后几分钟内收回："wait, i didnt test ss0/ss1 writement after flr" 与 "false positive"。幸存为有意义的只有：Turing 代 `booter_load` 确实可以被**加载**到 GA102 Ampere 卡上。日期 2026-07-14。
- **`/lib/firmware/nvidia/ga100/gsp/dmem.bin` 作为 payload 覆盖。** 钩子在正式代码中存在并记录成功，但在发布的启动流中，第一次 `kgspSec2PostblTimingRefillPayload()` 在任何 Booter Load 消费它之前就用内建模板重写整个缓冲。任何想靠往那里放文件换 payload 的人应当知道它对**发布路径无效果**。缺失以 `0x59` 报告且良性。
- **DMEM 写突破前的 IOMMU 调试。** 在 2026-06-28 使 SEC2 DMEM 写工作之前，大约花了一天在 IOMMU 死路上。基于 vfio 的开发中 Falcon DMA 引擎运行（`wcount_delta=2`）但零字节落到 SEC2 DMEM（`dmem_after=0`），使 Booter 带着 `sig0=0`、`mb0=0x31`、`TRACEPC=0x16b` 等待。编码、总线主控、hugetlb 分配与陈旧 SEC2 状态都被排除。工作假说是 `intel_iommu=on` 下驱动的 INSTBLK 页表没有映射漏洞利用缓冲的物理地址。被测试驳倒：IOMMU 关闭、`iommu=pt`、VFIO IOVA 与论文的 FBIF 常量都无法修复。
- **跳过 100 十进制字节而非 `0x100` 十六进制。** 一位测试者从字节 100 解密得到乱码。分发的指令明确：前 **`0x100`** 字节是明文、不得解密，边界处的零填充不得反汇编，反汇编必须从 `0x100` 重启。
- **"加密区域从字节 760 开始，那里熵上升。"** 同日驳倒：760 数字是提取器合成头与签名块仍被前置的伪影。一旦除原始固件外的所有东西都被移除，文件显示恰好 `0x100` 个未加密字节与干净的 16 字节 AES 对齐。一个相关早期观察——pad 模式在 8 字节而非 16 字节边界——是同一伪影。
- **一个 4,196 字节 blob，结果几乎全空。** 发布到频道的 `0x1064` 字节二进制是 Falcon Booter 描述符镜像，其从 `0x0500` 到 `0x1064` 的整个尾部都是零。记录以免有人再分析它。
- **对显存几何的 die 级与 HBM 控制器攻击。** 未继续。声明的理由：HBM 控制器在启动时只接受 Falcon 核的命令，中断或注入内存训练不容易。这是文档化阅读而非测量，所以是**降级优先级而非不可能性证明**。
- **"GSP-RM 加密且无法反汇编。"** 貌似合理因为 GSP-RM 是签名 radix3 blob 且没人打开过。被作者自己于 2026-07-23 收回，并被一份反汇编了 13.25 MB RISC-V ELF 的外部文档反驳。正确阻碍是**签名，不是加密**：修改过的 GSP-RM 无法通过认证。
- **FLR 解锁的"跨 FLR 复位持久"声称。** 单文档内自相矛盾：它断言链经受两次连续 FLR，然后承认因为阶段 1 结束时恢复原厂 GSP，掩码只从补丁 GSP 重新注入"until the stock GSP is swapped back in and you do another FLR cycle"。从未被独立复现。日期 2026-07-12。
- **永久锁恐惧。** 2026-07-21 提出（"wait can new nvidia drivers perma lock them?"）。以这些理由拒绝：解锁不使用原厂签名驱动、开源树已被广泛 fork、170HX 上从未演示任何运行时 OTP 熔丝机制。推测的反制机制没有产出任何支持证据。

## PCIe：速率、宽度、Gen3 与 Gen4

> [!CAUTION]
> **把速率与宽度分开**
>
> PCIe 链路**速率**（Gen1 到 Gen2）是软件与固件解锁，只在未发布分支发货。PCIe 链路**宽度**（x4 到 x16）由 16 条通道中 12 条出厂时 AC 耦合电容被移除造成，只能手工焊接 24 颗 0402 元件修复。下面好几条死路纯粹因为有人混淆了二者。参见 [PCIe 子系统](../hardware/pcie-subsystem.md) 与 [物理改装](../operations/physical-mods.md)。

### 四层墙

**假说（2026-07-24）。** 一份 PCIe 现场手册得出结论四层全部经验性关闭：运行时寄存器写、寄存器语义、持久固件与硅片熔丝。它在两个独立面上验证：4,032 次运行的离线固件模糊扫描（66 函数 x 126 函数-寄存器对 x 32 个单比特值），与硅片上直接写探测。

**貌似合理因为**每个单独组件确实惰性。

**被它自己的第 6 节驳倒**，该节陈述了例外：*"The full community Gen2 sequence ... as a single combined write was not run: every component is individually proven inert, so it is a low-odds combination."* 那个低概率组合成功了。之前没有人从 Booter 权限窗口内发出**组合**序列（CYA_0 位 2 清、LINK_CONFIG_0 MAX_RATE = 2、XP3G 覆盖与值、PRIV_MISC_1、VSEC），也没有人在这些写生效期间驱动根端口 retrain。

**Gen2 的放弃**2026-07-24 至 26。**Gen3 的一半结论仍然成立。**

### 对代次上限的固件与 strap 攻击

**devinit Gen-strap 字节。** 170HX PCIe 速率限制是**跨 3 个 devinit 位点的 5 个字节**，通过搜索对 Falcon 寄存器 `0x14118F78`（小端字节模式 `78 8f 11 14`）的引用定位。与 A100 SXM4 不同的字节是命中 #8 `0xBB` 到 `0xE2`、命中 #10 `72 DE` 到 `52 DD`、命中 #11 `97/59` 到 `95/39`。全部五个字节 **100% 落在** Davies-Meyer `csecret(2)` MAC 范围 `0x2200` 至 `0x43C00` 内，所以无密钥伪造是 2^128 第二原像。状态：关闭，2026-05-31。

> [!WARNING]
> **直觉方向恰好错了**
>
> 社区的 `pcie_set_speed` 方向是反的。strap 字段是**单调限制性**的：0 表示所有代次启用，3 是 170HX 设置（清除 Gen2、Gen3 与 Gen4），`0xF` 越界且全部禁用。**抬高上限需要更低的 strap 值，而不是更高**，且不存在写端口。被签名 FWSEC 中的 devinit 读-改-写是 `mov r9 0x14118f78; ld; and 0x3ff / or 0x400; st`，位于 VBIOS 偏移 `0xE88C`，每个 ROM 有 26 处引用；170HX 对 A100 的差值是**写入的值**，而非代码。2026-07-24 驳倒。这是语料中最有价值的更正之一。

一个相关地址空间错误被延迟收回：2026-07-24 的现场手册把 devinit Gen strap 描述为位于约 321 MB 的"Falcon PRIV bus, >16MB, not host BAR0"，并在此基础上构建"no host aperture exists"论证。2026-07-27 更正收回它：FWSEC falcon 代码中每个 `0x14xx....` 常量都是与孔径基址 `0x14000000` OR 的 BAR0 偏移，所以 `0x14118F78` 是 BAR0 偏移 `0x118F78`，在普通 16 MB 窗口内。常设警示：主机读 `0x118F78` 返回 `0xbadf1100`，所以 FWSEC 语境之外的主机可达性仍未证明。

其他固件路线：

- **重刷编辑过的 VBIOS**（`nvflash` 或 CH341A 编程器）。Ampere RSA 签名检查拒绝它，卡无法启动。`0x40B4B`、`0x40F05-3D` 与 `0x40FC5-CB` 的 Gen-cap 字节都在 MAC 内。2026-07-24 驳倒。
- **泄露的生产 HULK 证书**，ROM 内位于 `0xFE504`、带 `csecret(40)` 与 `STRICT_ID_MATCH=NO`，会是绕过 2^128 伪造的 `FUSE_FEATURE_OVERRIDE` `0x823800` 的*签名*覆盖。受 `RmActivateHulk` fmodel 标志门控，该标志在生产硅片上为 false；需要证书文件；且卡上 FEAT_OVR 写反正不动 `OPT_GEN23`。大体已无意义。
- **刷入真正的 A100 80GB VBIOS 恢复 PCIe 4.0。** 鉴于字节相同的 BIT 表与几乎相同的 PCB，高度貌似合理。测试并失败："Theyve tested that and it doesnt work. the pcie 4.0 bit at least."2026-07-19 报告。

- **`Gen2` 分支上的 `RMPcieLinkSpeed=0x1`。** 安装该分支写一个把链路钉在 Gen1 的 modprobe 选项，同时却在尝试启用 Gen2。`far` 上在提交消息"Remove clamp link to Gen1"下更正为 `0x2`。

> [!NOTE]
> **未解决问题**
>
> `RMPcieLinkSpeed` 应是 `0x1` 还是 `0x2` **真的未定**。两种写法都发货，作者各自相信自己的对：`Gen2` 与 `debug-gen2` 写 `0x1`，`far` 与 `deced` 写 `0x2`。`Gen2` 分支——其 README 声称 Gen2 工作——发货 `0x1`。不存在 A/B 启动测试。一张卡上的一次三方启动对比即可定案。

## ECC

ECC 被熔丝关闭，没有找到任何杠杆，且没有遥测。参见 [ECC 前沿](../frontier/ecc.md)。

**假说。** 打开 ECC feature-override 掩码 `0x00823800`（它门控 `FEAT_OVR_ECC` `0x82380c`、`ECC_1` `0x823810` 与 `ECC_2` `0x82382c`）并写影子即可打开 ECC，在解锁区域获得错误可见性。

**貌似合理因为**影子寄存器存在、已填充，掩码在 170HX 冷启动读 `0xffffff8f`，且高安全 ROP 可证明能打开它。这与生效的计算解锁同形。

**被两个独立失败层驳倒。** `0x00823814` 的 ECC 启用读出是 POR/熔丝锁存，不响应实时覆盖写。且 `FEAT_OVR_ECC` 不在常开域，所以覆盖反正 FLR 时回退。`FBPA_ECC_CTRL` MASTER_EN 位 0 只读。多次专门尝试（`fire_ecc_driverless_test.sh`、`fire_ecc_unlock.sh`）失败，结果写成 `ecc-unlock-dead.md`。

**放弃于**2026-07-16。2026-07-28 确认 **`cmpunlocker` 的任何分支都不含任何 ECC 写**。

另外两条 ECC 死路：

- **名为 `ecc` 的分支不是 ECC 工作。** 其 `driver/patches/` 目录与 master 字节相同，唯一提交是 `bb4d669 Fixed dual geometry support`。它与 master 的其余差异是 `README.md`、`constants.yaml` 注释、`build.sh`、`install.sh`、`remove.sh` 与一个 master 后来删除的 `requirements.txt`。任何人都不应把它当作 ECC 工作读。一个相关声称——`| ECC | Planned |` 与 `| NVLink | Planned |` 在 `ecc` 分支 README 中——也是假的：那些行只出现在 `memory` 与 `housekeeping` 分支 README 中。
- **Maxwell 时代 ECC 解锁移植到 Ampere**，刷设备 ID 编辑过的 Quadro VBIOS 并经 INF 强制安装 Quadro 驱动，在 Maxwell 上以照片证据演示，同一发帖者立即警示："As for how you would do that for Ampere? I have no idea... this is not trivial for Ampere"。从未在 GA100 上演示。日期 2026-07-19。
- **经 feature-override 路线启用 ECC 或 PCIe Gen3。** 两者都被认为由 DEVINIT 在驱动运行前确立，ROP 与 feature-override 方法无法改变。PCIe 还在熔丝级双重锁定（`FUSE_PCIE_GEN23_DIS = 0x1`、`FUSE_PCIE_GEN3_DIS = 0x1`）加五字节 devinit 改动，所以纯固件补丁不足。日期 2026-07-24。

> [!NOTE]
> **未解决问题**
>
> HBM 栈是否携带 ECC 供应只得到部分回答。A100 per-FBPA `CSTATUS_RAMAMOUNT` 差值（`0x07ff` / `0x0fff` 对消费级 `0x0800` / `0x1000`）读起来像同一栈内保留给 ECC 的容量，但那是寄存器值推断，不是数据表。参见 [ECC](../frontier/ecc.md)。

两条 VBIOS 相邻的更正值得直说：

- **"RSA 签名区域止于约 `0x45000`"在两点上不精确。** 边界在 250 W 170HX ROM 上是 `0x43A00`、300 W ROM 上是 `0x43C00`，由 RFRD `field_0C` 声明，且它是**以 `csecret(2)` 为密钥的对称 MAC**，而非镜像上的 RSA 签名。RSA 由启动 ROM 用于认证 Booter 代码，是独立机制。
- **432 / 729 / 1458 MHz 显存时钟的"三方冲突"不是冲突。** 它是同一时钟的三个倍数；VBIOS 字段是四分之一速率。
- **"8 GB SKU 携带 `92.00.6D.00.0A`"作为 blanket 声明是错的。** 2026-07-26 dump 的两张物理 8 GB 卡报告 `92.00.67.00.01`，两台主机的四张卡现场显示两个版本都有。`92.00.67.00.01` 是生产 8 GB 镜像；`92.00.6D.00.0A` 是更晚的 300 W 超频镜像。

## 驱动与内核补丁集

参见 [驱动补丁](../unlock/driver-patches.md) 与 [驱动版本](../procedures/driver-versions.md)。

### 两加载架构

**假说（2026-07-05 至 07）。** 加载 1 中解锁，然后在加载 2 重载干净驱动并保持结果。

**貌似合理因为**几何写可证明落地并在 `rmmod` 后存活。

**被一个真实而非想象的循环依赖驳倒。** 加载 1 的 GSP 失败驱动在卸载时把 SEC2 复位掩码在 `0x008403c4` 重新锁定，这是 ROP 无法阻止的驱动侧动作，而清除它所需的 FLR 回退非常开几何。另外，第二次加载必须清除 WPR2，但清除它把复位掩码重新抬到 `0x8f`，阻止原厂 `kflcnReset` 并产生 `0x65`。WPR2 状态也无法在两次启动之间用 PL0 主机写清除。

**放弃于**2026-07-07。当时的声明结论正是最终发货的："漏洞利用必须一次通过设置几何并完成启动，留下一个干净的补丁驱动对照解锁后大小初始化的活 GSP-RM。"中间找到第二条逃生路线：2026-07-22 的免驱动工作清除 WPR1 与 WPR2_HI，使原厂驱动**完全无 FLR** 启动。

### 3 MB WPR2 放置不匹配

**假说（2026-07-13）。** Booter 在固定原生 10 GB 顶部刻 WPR2，`[0x277700000, 0x27fee0000]`，约 136 MB，strap 派生因为 FWSEC 忽略 40 GB 覆盖。驱动的首次尝试布局 `[0x277400000, 0x27ff00000]`（约 139 MB）恰好从 Booter 基址下方 `0x300000`（3 MB）开始，且大约大 3 MB。重试时驱动逐步移得更远（`0x277400000`、然后 `0x26e800000`、然后 `0x265c00000`），从不收敛。"那个 3 MB，一个可疑的整数，就是全部缺陷。"

**貌似合理因为**数字精确、从寄存器解码，发散模式看起来像经典的差一个区域 bug。

**同日被驳倒**：构建字节精确的 WPR2 布局——"a byte-exact WPR2 layout does NOT resolve 0x55. So 0x55 was not (only) a placement problem."真正的适配检查住在封闭的 Booter ucode 内。

**放弃于**2026-07-13。

### 对抗项目自己残留的补丁

**信念。** 一类 `0x55` 失败是硬件或几何行为。

**现实（2026-07-13）。** 更早一次 `0x55` 修复尝试留下的 CMP 170HX 驱动补丁把 `placeFbSize` 硬设为 8 GB，使驱动布局低于 Booter 在原生 10 GB 顶部刻 WPR2 的位置。"So we're partly fighting our own patch."这追溯性地解释了多少天的"几何回退"观察："who knows how many days that was there... I've been working with a 10 GB card for over a week now."

**当时记录的教训：** 始终对照原始树重新基线。提出的干净测试是不带 `fb_size` 覆盖的原厂未修改驱动。

关于正式补丁还有三个事实，没有任何挖掘出的声称记录过，任何审计树的人都应知道：

- **补丁 0001 对所有 GPU 移除"WPR2 already up"退出，不只是 CMP。** 如果打过补丁的模块曾在混合系统加载，这可能掩盖无关硬件上真正糟糕的 GPU 状态。

- **一个 GA102 适配把整个 WPR2-already-up 块注释掉**，带 `// Bypass WPR2 check (for CMP 90HX compute unlock)`。GA100 正式补丁只把它弱化为警告。GA100 行为才是 170HX 的规范。

## 热、功耗与散热

参见 [散热](../operations/cooling.md)、[热学](../hardware/thermals.md) 与 [功耗与电源](../operations/power-and-psu.md)。

### 当作 300 W A100 散热器出售的 3.24 W 蜗牛风扇

**假说。** 常见出售的印刷"A100 cooling"转接器带 3.24 W 鼓风机，能处理 300 W 卡，因为厂商那么宣传。

**貌似合理因为**它是默认购买、物理上合身、列表这么说。

**被一手测量驳倒**：**直接 PSU 供电下全力只有 150 至 180 W 上限**。对 250 W 卡这不够，更远未到 300 W。

**放弃于**2026-07-20。这是档案中最直接可执行的散热更正：任何买标准转接器的人买到的大约是列表声称散热能力的一半。

### Strap 电阻

Strap 电阻值得单独说明，因为该想法至少以不同形式出现六次，且每次都因容量而被驳倒。

**假说。** 原厂 10 GB 配置 `LLLLH` 可以切换到 `LLLHL` 得 40 GB 或 `LLLHH` 得 80 GB，更一般地说，显存 strap 电阻选择容量。

**貌似合理因为**strap 可证明在 VBIOS strap 表中选择显存配置，且 A100 原理图的 GPU strap 配置表确实把 STRAP2、STRAP1 与 STRAP0 映射到厂商特定 RAMCFG 值。该想法源自 LLM 建议，事后被维护者标记为幻觉。

**被 2026-06-23 的穷举排列驳倒**：10 GB 卡原厂 VBIOS 上最后三个 strap 的全部 8 种组合**都没有产生任何容量变化**。`LLHHH` 把系统完全砖死、无 POST。物理移除三个 strap 也没有改变任何东西，所以它们有默认。第二名测试者独立确认无效果，维护者同日接受揭穿。2026-07-25 复核：10 GB 卡物理重 strap 使 CFG1 不变于 `0x02449000`，而未改装卡仅靠软件就达到相同容量。

**放弃于**2026-06-23，2026-07-25 复核。

后续 strap 死路：

- **"电阻改装启用了 80 GB 解码变化。"** 2026-07-24 一张 10 GB 卡的物理重 strap 被归功于启用 L2 解码变化到 `0x10000300` 与 80 GB 结果。"之前"值依赖上下文：`0x70000300`（脏）、`0x60000300`（干净 40 GB 点火）、`0x10000300`（电阻改装后或活 UVM 原子）。2026-07-25 探测显示 `FBPA_CFG1_BROADCAST = 0x02449000`，即与原厂相同，且一张**未改装** 10 GB 卡用 refire 脚本复现相同 80 GB 状态。依赖在一天内被退役。
- **把 RAMCFG 重 strap 成 8 GB 模式使 64 GB 路径适用于 10 GB 卡。** 被源码驳倒：正式驱动从 `pGpu->idInfo.PCIDeviceID >> 16` 选择 CFG1 与 LMR，不来自任何 strap 或 RAMCFG 值。一位测试者 2026-07-24 执行了该确切修改，从未报告启动或训练结果。
- **一个 `strap5` 电阻在两个熔丝化设备 ID 间切换。** 貌似合理：die 确实携带两个设备 ID 熔丝（`OPT_PCIE_DEVIDA 0x008204d8` 与 `OPT_PCIE_DEVIDB 0x0082056c`），提出者已定位另外五个 strap 电阻，机制在 NVIDIA 专利中有描述。两个原因死亡：strap 从未被定位；一周后发布的五 strap 图恰好枚举五个 strap，其中没有 `strap5`。
- **重新烧设备 ID 熔丝**（10 GB `2082` 到 `20B2`，或 `20C2` 到 `20F2`）以允许刷真正 A100 VBIOS。从未尝试。提议本身列出弱点：烧更多熔丝通常进一步劣化卡，且消息含内部矛盾。`20B2` 是 `2082` 的已知笔误，2026-06-29 频道内更正。两个 170HX ID 是 `0x20C2`（8 GB）与 `0x2082`（10 GB）。
- **"Strap2 给 40 GB、Strap1 经只读 RAMCFG strap 进 L2 解码锁存给 80 GB。"** 转述者标记电阻位号与位置完全未验证，且不知道哪个物理 strap 是哪个。被作者自己削弱：他注意到 40 GB 解锁已经无需任何硬件修改就工作。一个涉及反复焊接与拆焊的测量脚本被起草，从未执行。
- **通过读 `0x101000` 位 [23:20]、移动一颗电阻、冷启动并重读来识别 VRAM strap 电阻。** LLM 生成，除批评它建议短路而非移动电阻外判定正常。从未尝试。被同日声明反驳：没有已知方法读回选择了哪个 strap 值，唯一指示是 `0x009A0204` 处的值。被寄存器写路径变得无意义。
- **"硬件解锁不可能。"** 2026-06-29 直说。**部分错。** 对经 strap 的 VRAM 容量为真，但对 PCIe 通道宽度为假——那里电容改装是唯一路线且可靠工作。准确陈述是：硬件修改无法移动熔丝边界，但**可以恢复被移除的 PCB 功能**。

两条进一步电容改装说明。介质是 **X7R**，不是"XR7"——一个广泛传播的换位：规范部件是 24 x 0402、220 nF（0.22 uF）、X7R、额定 6.3 V 或更高、位号范围 C1100 至 C1350，Taiyo Yuden `MAASJ105SB7224KFCA01` 为确认的厂商部件。且声称正式解锁 README 记录了 x4 限制是**假的**：grep 整个工作树、完整历史与全部十二个分支检出，零出现"capacitor"、"AC coupling"、"solder"或任何通道宽度寄存器或措辞。关于电容的技术声称真实且证据充分；只有归因于正式 README 是错的。

## 项目自己 docs 分支中的文档缺陷

`docs` 分支（`cmpunlocker-branches/docs/`）是项目中最危险的工件，因为它看起来权威、在项目自己的仓库内，而且错的方式会让工作解锁被报告为失败。**不要把它当参考。** 以下所有内容都对照正式源码验证过。

### 编造的缩写展开

| 术语 | docs 分支说 | 实际是什么 |
|---|---|---|
| **PLM** | "Program Logic Modules"，如"The SEC2 Booter executes firmware sequences (PLMs)" | **权限级掩码（Privilege Level Mask）。** 它是寄存器的属性，不是被执行的模块。正式代码写权限级掩码寄存器：`0x001fa7cc` WPR_CFG、`0x009a0148` FBPA、`0x001fa7c4` WPR 与 `0x00823804` FEAT |
| **PMM** | "the PMM (Permute Mask Model)"，与一个"SEC2 Booter PMM" | **代码中无处出现。** 该词是发明 |
| **LMR** | "LM Request"与"LM (Local Memory) Request register" | 寄存器是 `NV_PFB_PRI_MMU_LOCAL_MEMORY_RANGE`：Local Memory **Range（范围）**，不是 Request |
| **SS0 / SS1** | "Suspension State"寄存器，"artificially disable clusters of SMs" | `FEATURE_OVERRIDE_SM_SPEED_SELECT`（`0x0082381c`）与 `FEATURE_OVERRIDE_SM_SPEED_SELECT_1`（`0x00823820`）。它们控制逐指令单元的**发射速率**，而非哪些 SM 活跃 |
| **PMA** | "Power Management Array"，带"PMA is reconfigured for the enabled SM clusters" | RM **物理内存分配器（Physical Memory Allocator）**。`0003-late-pma.patch` 是纯内存管理器代码：声明 `PMA_REGION_DESCRIPTOR`、遍历 `pHeap->pPmaObject`、调用 `memmgrIsPmaInitialized`、记录 `pmaFreeBefore`、`pmaTotalBefore`、`pmaFreeAfter`、`pmaTotalAfter`、`heapFree` 与 `heapTotal`。"late PMA"步骤扩展高 PMA 区域以覆盖新暴露的 framebuffer。它与**功耗管理毫无关系** |

### 错误的值与错误的日志行

- **"cmpunlocker 向 SS0 与 SS1 都写 `0xffffffff`，启用所有簇。"** 正式代码写 `GPU_REG_WR32(pGpu, 0x0082381cU, 0x88888888U)` 与 `GPU_REG_WR32(pGpu, 0x00823820U, 0x00000008U)`，`common/constants.yaml` 同意（`ss0: "0x88888888"`、`ss1: "0x00000008"`）。验证在 master 与每个分支的 `0001-sec2-postbl-plm-ss-cfg.patch` 全部 15 份副本中相同。
- **预期的 dmesg 行 `SEC2_DEBUG: SS0 = 0xffffffff` 与 `SEC2_DEBUG: SS1 = 0xffffffff`**（`docs/ARCHITECTURE.md` 第 81 与 82 行）永远不会出现。**任何人拿这些字符串验证解锁都会错误地得出它失败的结论。**
- **日志行 `SEC2_DEBUG: Executing unlock sequence...`** 在文档中作为预期输出打印。**它不存在于代码的任何地方。** 不要 grep 它。
- **"把 PLM 权限设为 `0xffffffff`（所有 PLM 启用）。"** 四个中三个被打开为 `0xffffffff`，但 **`WPR_CFG`（`0x001fa7cc`）被写为 `0xfffff0ff`**。循环自己的成功测试把 `0xfffff0ff` 视为打开。master 的 README 携带同一不精确的较弱版本（"Expected: PLMs opening to 0xffffffff"）。
- **"注入自定义 PLM 序列。"** 代码通过用篡改的签名缓冲重跑 Booter Load 打开四个特定权限级掩码寄存器。没有注入序列。
- **"原厂固件设置这些以禁用约 50% 的 SM。"** 两种 SKU 原厂都枚举全部 70 个 SM，解锁前后 SM 数都保持 70 不变。
- **`sudo ./uninstall.sh --yes`**（docs 分支 `README.md` 第 68 行与 `docs/INSTALLATION.md` 第 40 行）。**任何快照中都不存在 `uninstall.sh`**，包括 `docs` 分支本身。正确命令是 `sudo ./remove.sh --yes`，同一分支的 `ARCHITECTURE.md` 第 118 行那么说，所以分支自相矛盾。参见 [卸载](../procedures/uninstall.md)。

### docs 分支之外的其他文档缺陷

- **`80` 分支 README 中 80 GB 的"Working ✓"行。** 该 README 中"Working"意味着"报告大小并启动"，而非"通过内存验证"。作者 2026-07-19 自己的评估谦逊得多："I'd say even having 80GB show up in nvidia-smi without rejected boot is a success (for now)."
- **`DEBUGGING.md` 的补救措施"所有 PLM 必须显示 `0xffffffff`。"** 见上文。
- **正式 README 的 `0x20C2`-only 背景句。** 代码对 `0x20C2` **或** `0x2082` 门控。README 两段后自己的表列出两张卡。
- **170th-Street 规格页在 SM 数上自相矛盾**，计算表给 70 SM、结尾注给"8GB variant: 56 SMs, 4,096-bit memory bus"。寄存器账目定案为 70。
- **170th-Street 时间线页仍说 PCIe 电容改装"documented but unconfirmed on the 170HX specifically"。** 被同一 wiki 自己的改装页取代，该页记录了 2026 年 4 月确认的 170HX 成功，带前后 `lspci` 输出。
- **170th-Street 规格页仍说"PCIe Gen 1 x4 (firmware locked), ~1 GB/s"**，而同一 wiki 的解锁页把 Gen2 速率列为功能。
- **参考材料中的 NVLink 对比表内部不一致**，打印"NVLink killed, CTRL_OPT override path under investigation"，而同一文档确立 `FUSE_EN_SW_OVERRIDE = 0x0`、因此"CTRL_OPT fuse override disabled, cannot be changed, inert on 170HX"。熔丝测量胜出。

## 经聊天传播但正式代码中没有的值

这些不完全是错，而是**已被取代且仍在流传**。每一个都是项目历史某时刻真实工作工件中的真实值。没有一个代表正式驱动所做的。

### 守卫值 `0xFACEB13D`

**它来自哪里。** 概念验证用 `0x4a7` 填充。2026-07-04 社区按约定采用 `0xFACEB13D`，明确拒绝 `0xDEADC0DE` 与 `0xCAFEBABE`，理由是它们被过度使用且可能出现在 NVIDIA 自己的代码中，那会让读 DMEM dump 时归因模糊。ROP v1 在 `D[0x6340]` 与每个栈金丝雀槽都种 `0xFACEB13D`。

**正式发什么。** `0xc0deca7e`，写在 payload 偏移 `0x5b40`，即 DMEM `0x6340`。缓冲其余部分的填充 dword 保持 `0x000004a7`。

**为何功能上无关紧要。** 机制与值无关：守卫字只需匹配。三个值因同一原因有效。`0x4a7` 填充曾被单独相信是功能要求，2026-07-04 被解释为只是一个自循环检测器，让主机看到 Falcon 停在 panic 循环而非漫游。它并非漏洞利用工作需要，不过正式驱动仍出于那个诊断原因使用它。

**为何文档上重要。** 任何 grep 正式 payload dump 找 `0xFACEB13D` 的人都找不到，可能得出 payload 畸形的结论。

还存在一个中间设计：`0x10b9` multiwrite 链把种匹配字的方法换成**指针技巧**，把 `GUARD_ADDR 0x6340` 作为操作数传给两个金丝雀槽，使比较自引用，守卫值 0 可接受。正式驱动回退到种匹配字但换不同常量。

### gadget `0x10b9`

**它来自哪里。** 研究链标准化采用带 `r0` 与 `r1` 的 `0x10b9` 中途进入。它是干净的链式封装，因为它以 `mpopaddret $r3 0x4` 结束并直走下一个写帧。每个社区 multiwrite 链都用它，而长期相信 `0x10b9` 在第一写之后"丢弃额外写"被 2026-07-15 诊断为生成器中的反序槽位 bug，而非机制故障。它原生链式。

**正式发什么。** 正式驱动用带 `r10` 与 `r11` 的 **`0x10aa` 全入口**，由电梯 `0xcbd` 与 `0x1fbd` 编排。`0x10aa` 是正式 payload 在偏移 `0xf788` 种植的 gadget。正式 payload 中地址字面量是 `0x000010aa`。

**两者都工作。** wiki 不得混用：为 `0x10b9` 语义写的链读正式 payload dump 时不会正确对应，反之亦然。正式 payload 是独立、单写谱系。

### `0xFFxx` 对 `0xF7xx`"分歧"

**声称。** 一份出处审阅注意到社区 DMEM 偏移聚集在 `0xFFxx` 范围，而正式补丁的 payload 偏移是 `0xF7xx`，得出结论社区要么针对不同 Booter 构建工作，要么尚未收敛到正确布局。它被写成泄露推导评估中的高关切项。

**为何看起来真实。** 两份文档确实打印不同数字，不同数字通常意味着不同东西。

**实际是什么：单位伪影，不是分歧。** payload 被 DMA 到 DMEM `0x800`。因此 **payload 偏移加 `0x800` 等于 DMEM 地址**，两组数字是不同参考系中的同一地址：

```text
payload 0xf754 + 0x800 = DMEM 0xFF54
payload 0xf7c4 + 0x800 = DMEM 0xFFC4
payload 0x5b40 + 0x800 = DMEM 0x6340   (the canary guard)
payload 0x1100 + 0x800 = DMEM 0x1900   (the 0x7 that secure_teardown restores)
```

评估把补丁偏移引为可疑、把 DMEM 地址引为干净，**在同一个槽位上**。该审阅其余部分站得住：它列出的三种退出策略（`secure_teardown`、提前退出 `0x8117` 与 `multiwrite_then_mutexfree_cleanexit`）及其对 `0x8403C4` 作为复位掩码的识别都正确。

**定案日期：** 2026-07-18。

同一评估的两个相邻出处关切也被驳倒：

- **"推导偏移需要模拟器、NVIDIA 内部栈帧文档或泄露 Booter 源码。"** 链中每个代码地址都是 2026-07-01 发布反汇编中的指令边界；gadget 语义与 `mpopaddret` 收尾在 2026-07-10 的公共图谱中列表；六字段 `0xFF48` / `0x18` 帧网格在 2026-07-15 的公共 git 提交中与同日散文文档中。全部早于泄露 diff。
- **"偏移 `0x5b40` 接收 `0xc0deca7e` 不在任何公共来源中。"** 已发布论文在其模拟器 trace 中给出 `buffer=0x800` 与 `guard@0x6340`，并发布 `guard: 0x00000000 -> 0xc0deca7e` 作为桩值。`0x6340 - 0x800 = 0x5b40`。偏移与值都可用一次减法重建。

### 引用前值得检查的其他值

| 流传值 | 正式现实 |
|---|---|
| FEAT 掩码打开为 `0x000000FF` | `0xFFFFFFFF`。`0xFF` 只设读写半字节，`SOURCE_ENABLE` 保持 0。一位研究者另报告向 50HX feature-override 掩码写 `0xFFFFFFFF` 匹配标志描述，无成功，所以正确编码在每个部件上**必要但不充分** |
| CFG1 `0x27790000` 对应"64GB 可用 VRAM" | `0x02779000`，同一数字右移一个半字节 |

## 反复出现的失败模式

六个模式解释了 507 条中的大部分。及早识别它们比记住任何单条死路更值。

**1. 计算理论峰值然后格式化为测量。** 至少发生三次：`1769.47 GB/sec` 带宽数字（864 MHz x 4 x 4096 bits / 8 恰好）、旁边的 `12633.60 GFlops`，与 2026-07-13 计算表。最后一种情况下数字碰巧正确，使出处批评显得学究气。它不是学究气；同一过程在别处产生错数字。**在问一个数字是否合理之前，先问它在哪里被测量。**

**2. 名字恰是你想要的寄存器。** `SM_ISSUE_RATE_MODIFIER`、`RMOverrideSmSpeedSelect`、`CTRL_OPT_NVLINK`、`FUSE_HALF_FBPA_EN`、字面名为 `GEN2_PCIE` 的 `PTOP_FS4` 位。每个情况名字都准确，寄存器仍不是杠杆。**跨卡探测是最便宜的可用驳倒**：如果全速 A100 读相同值，该寄存器就不编码该限制。

**3. 读回一个从未被写的寄存器。** "直接写"理论测了四对写读回构成整洁模式，而每个"读回"都是未触碰的原厂值。`0xffffff8f`、`0x02449000` 与 `0x208` 是文档化原厂值。**始终在某个你知道可动的寄存器上以阳性对照确认写落地。**

**4. 单位混淆被呈现为实质分歧。** payload 偏移对 DMEM 地址（`+0x800`）、BAR0 偏移对 Falcon 孔径（`| 0x14000000`）、四分之一速率对有效显存时钟（432 / 729 / 1458 MHz）、每用户对聚合 token 速率（16 用户时 2.4 对 38.9）、半字节移位 CFG1 抄录。**当两个可信来源为同一事物打印不同数字时，先检查常量因子或偏移，再下结论说它们分歧。**

**5. 工具或工具链本身坏。** 4 GiB `cuMemGetInfo` 截断、把原生显存报告为折叠的 fold 工具链、别名过自己伙伴地址的稀疏探测、因指针类型不匹配瞬间返回的 `CUBLAS_COMPUTE_16F`、中止漏洞利用路径的 argparse 不匹配、清空金丝雀的栈生成器。**来自新工具的意外结果是工具 bug，直到对照运行另有说法。**

**6. 自信、格式良好、错误的 AI 输出。** 这条值得直说，因为它在每个领域复发：编造的 DMEM 图、带正确位号与晶振频率的编造板级拓扑、用在 GA100 上的 GP102 寄存器地址、16 位截断模型、"结构性墙"论证，以及花费约 110 美元、结论与真相相反的 FP 节流报告。语料也包含**正确且决定性**的 AI 辅助工作，包括计算解锁本身的复现。区别特征不是工具，而是声称是否带读回、对照或跨卡比较。

第七个模式值得收尾，因为它是健康的那一个。上面相当大一部分条目是**被提出者自己收回的**，常常就在几分钟内：FSP 理论、NVML 时钟理论、CPU-RM 上下文理论、90HX 持久性声称、80 GB 内存错误计数、PG199 容量估计、非安全 BAR0 否定结果、互斥 `r10` 踩踏理论、NVGI"无恢复路径"声称、`0xf700` payload 大小，与 `0x0F40` 写 gadget（在提出它的同一消息中自我更正）。快速自我更正正是为什么一个有 507 条死路的项目仍在约五周内发货了可用的 64 GB 解锁。
